## 1. 一句话定位

一个部署在边缘的**通用采集引擎**：南向按配置接任意设备协议，北向用统一物模型走 MQTT JSON，把「LoRaWAN 网关」和「RS485 融合终端」收敛成**同一个二进制、同一套配置模型**。

**不改代码、只改 YAML**，就能完成两类变更：

- **实例配置**（当场可改，改值即可）：加一台同类设备、改站号、改采集周期、改上报周期、改北向 Broker/Topic 前缀。
- **模型配置**（改 YAML，不动代码，但属模型变更，需按配置评审流程走）：换设备型号（新增/替换 profile 的点位映射）、调整 Topic 层级结构、调整 payload 的**声明式位域**（偏移/长度/类型/缩放；压缩或条件编码等复杂格式仍需写代码）。

**唯一需要写代码的变更**是：新增一种协议（新驱动）、新增一种北向传输（新通道）、更换云端字段语义（新适配器）—— 这三件事正是设计上预期要扩展的点。

## 2. 为什么这样抽象（依据，不是想象）

| 需求 1 | 需求 2 | 引擎吸收为 |
|---|---|---|
| LoRa 上行 / 下行（ChirpStack v4） | — | 驱动 `lorawan`（上行走 MQTT integration，下行走 gRPC，见 ADR-0002） |
| Modbus TCP 读写阀门 | RS485 读传感器 | 驱动 `modbus`（同一 PDU 实现，传输可为 TCP / 串口 RTU / RTU-over-TCP） |
| 电动阀物模型：属性/服务/事件/超时 | 「mqtt 协议传给平台」 | 适配器 `irrigation-v1` + 北向通道 `mqtt` |
| 网关本机有 ChirpStack，数据上云链路保留 | 无 | 引擎是**旁路**，只经 API，绝不抢占端口/会话 |

三条支撑事实：

1. **同一台电动阀可能经 LoRa 接入，也可能经 Modbus 接入**，但对云端必须是同一个物模型。→ 「设备」与「接入路径」必须分离，这是产品抽象的根。
2. **需求 1 要求保留 ChirpStack 原上云链路**。→ 引擎只能作为消费者，不能接管射频与网络服务器。
3. **需求 2 链路极窄（485 → MQTT）**。→ 证明北向与南向正交，窄链路就是最好的第一条垂直切片。

## 3. 目标与非目标

### 目标

- **G1** 单二进制、单 YAML 配置，在 `linux/arm64` 上 systemd 常驻运行。
- **G2** 南向：Modbus（TCP / 串口 RTU / RTU-over-TCP 三种传输）与 LoRaWAN（经 ChirpStack v4）两类驱动，可同时启用多条链路。
- **G3** 北向：MQTT JSON，属性上报 / 服务下发 / 服务回执 / 事件上报四类报文。
- **G4** 可靠性：指令至少一次 + 幂等；设备离线判定；北向断线补发（有界）。
- **G5** 可运维：结构化日志、只读健康/指标端点、配置校验子命令。
- **G6** 可联调：内置模拟器（Modbus 从站 / ChirpStack 桩 / MQTT 云端桩），无实物也能验收全链路。

### 非目标（明确不做，防止范围爆炸）

| 编号 | 不做 | 理由 |
|---|---|---|
| N1 | 云端后台页面、数据库 | 需求明确不做 |
| N2 | 修改 ChirpStack 源码 | 只做 API/集成层对接 |
| N3 | 硬件驱动开发 | 硬件已就绪 |
| N4 | 设备固件 OTA | 属设备侧职责 |
| N5 | 本地 Web UI / 配置界面 | 配置是运维资产，走文件 + Git |
| N6 | 多节点编排 / 云端配置下发 | v1 单节点自治，编排属云端 |
| N7 | **定时灌溉策略、轮灌计划、规则引擎** | 业务策略属云端；边缘只执行与反馈 |
| N8 | 主备双接入路径自动切换与对账 | v1 一台设备只声明一条路径 |
| N9 | 一机一密、远程凭据轮换 | v1 用配置内静态凭据，预留接口 |

> N7 是这类项目最常见的范围失控点：一旦边缘开始「自己做灌溉决策」，云端与边缘就会出现两套事实来源。产品边界必须画死。

## 5. 核心场景（泳道）

### 5.1 周期采集上行（Modbus 链路）

```
云端            MQTT通道          引擎(调度/状态/物模型)          Modbus驱动          链路/设备
                  │                       │                          │                   │
                  │                 按链路 tick                   │                   │
                  │                       │── ReadPoints ──────────> │── 03/04 ────────> │
                  │                       │<─ Samples(含quality) ─── │<─ 响应/超时 ───── │
                  │                       │ 合并为设备属性 + 变化比对 │                   │
                  │<── property.post ─────│ (snapshot / delta)       │                   │
                  │  (QoS1)               │                          │                   │
```

- 调度单位是**链路**，不是设备：一条 485 总线上的多台从站按队列串行，避免总线冲突。
- 上报周期分两档：**快照** `snapshot_interval`（默认 60 s，全量）、**增量** `delta`（变化去抖 2 s）。
- 每个属性**必带 `quality`**（good/stale/bad）。读失败不上报假值。

### 5.2 云端服务调用 → 阀门动作 → 分级确认（LoRa）

```
云端         MQTT通道      引擎(Invoker)      LoRaWAN驱动      ChirpStack        阀门
  │             │              │                 │               │              │
  │─invoke ────>│─ 解析/校验 ─>│                 │               │              │
  │             │              │ 幂等检查(seq)    │               │              │
  │             │              │── WritePoint ──>│── gRPC Enqueue ─>│             │
  │             │              │<─ CmdAccepted ──│<─ Enqueue OK ───│             │
  │             │              │  等待窗口+回执    │               │─ 上行触发 RX 窗口下发 ─>│
  │             │              │<──────── Driver.Events: txack ───│              │  (网关已发射)
  │             │              │<──────── Driver.Events: ack ─────│              │  (设备 MAC 确认，仅 confirmed 下行)
  │             │              │<──── Driver.Events: uplink(业务ACK字段) ─────│  (动作完成)
  │             │<─ service.reply(code=0) ────────│               │              │
```

**分级确认是本产品的核心可靠性语义：**

| 级别 | 含义（准确措辞） | 来源 | 判什么 |
|---|---|---|---|
| A `txack` | **网关已把下行帧发射出去**（不是「设备已收到」） | ChirpStack `txack` 事件 | 发射成功，不证明送达 |
| B `ack` | 设备 MAC 层确认收到（**仅 `confirmed` 下行才有**） | ChirpStack `ack` 事件 | 射频层送达 |
| C 业务 ACK | 阀门确实执行到目标开度 | 设备后续上行 payload 字段 | 业务完成 |

**只有 C 才算服务成功。** A 或 B 到而 C 未到，回执必须标明「未确认」与到达级别；具体 code、`stage` 字段与 C 级判定见 `REQ-INVOKE-03/04` 与 `docs/contracts/external.md`。

> **措辞纪律**：`txack` 只证明网关发射，不证明设备收到。
> `confirmed=false` 时没有 B 级，A 与 B 合并为「已发射」。关键服务（如 `set_opening`）应在 profile 中设 `confirmed=true` 以取得 B 级证据。
> 若 ChirpStack 版本或区域参数不允许 confirmed 下行，则 B 级永久缺失，只能靠 C 级判定 —— 部署文档须写明。
（payload 中业务 ACK 字段位置是 `ASSUMED`，见台账 A10。）

### 5.3 设备离线判定与恢复

- 每台设备维护最后成功时间，**只由新鲜观测推进**；A 级发射确认不算设备在线证据。
- 连续若干个设备周期没有新鲜观测即判离线；状态翻转时发一次离线事件。
- 恢复时发在线事件 + 一帧**全量快照**，云端无需自己补齐断档。
- 离线期间属性标记 `quality=stale`，`ts` 不更新。

阈值、周期口径与质量真值表见 `REQ-QUALITY-02..04`；参数键与默认值见 `docs/contracts/config.md`。

### 5.4 北向断线（store-and-forward）

```
MQTT 断开 → 事件进入有界队列；属性只保留「每设备最新快照」（覆盖写，不排队）
MQTT 恢复 → 先发全部事件（按时间序、可去重）→ 再发每设备最新快照
```

全量历史不缓存：网关存储只有几 GB，补发几小时历史既无业务价值，又有写满磁盘的风险。队列上限、淘汰与丢弃可观测性的规范见 `REQ-CACHE-01/02`。

### 5.5 配置热重载（SIGHUP）

改 `devices.yaml` / `profiles/` 后 `kill -HUP`：重新解析并**差别应用**——新增设备启动、移除设备停止、改周期的生效、改点位的重建映射。**解析失败则整体不应用并报错**，旧配置继续跑（不留半配置状态）。

进行中的操作：采集任务在新 tick 使用新周期；未完成的服务调用不取消，按受理时的参数走完；断线缓存保留；被移除设备上报一次移除事件后停止采集与下发。

完整行为（包括不可热重载的配置块）见 `REQ-OPS-01` 与 `docs/contracts/config.md`。

### 5.6 无实物联调

`collect-code simulate` 一个进程同时起 Modbus TCP 从站、RTU-over-TCP 从站、ChirpStack 桩、内嵌 MQTT broker + 云端桩。引擎跑在另一进程连它，跑完整的 5.1–5.5。契约见 `docs/contracts/simulator.md`。

## 6. 架构与契约（链接）

依赖方向只能向内：`cmd → app → core → interfaces`。驱动、通道、适配器与 Store 实现接口，由 `cmd`/`app` 装配；内核不 import 具体实现。

```text
                    ┌────────────── cmd/collect-code ──────────────┐
                    │ run | config-check | simulate | version      │
                    └──────────────────────┬───────────────────────┘
                                           │ 装配
        ┌──────────────────────────────────┼──────────────────────────────┐
        │                                  │                              │
┌───────▼────────┐              ┌──────────▼───────────┐        ┌─────────▼──────────┐
│ channels       │              │        core          │        │ drivers            │
│ implements     │◀───uses──────│ scheduler state      │───────▶│ implements Driver  │
│ Channel        │              │ invoker forward      │        │                    │
└────────────────┘              │ eventbus status      │        └────────────────────┘
                                └──────────┬───────────┘
                                           │ 只依赖
                                ┌──────────▼───────────┐
                                │  internal/interfaces │
                                └──────────────────────┘
```

接口签名与冻结注释见 `internal/interfaces/**`。组件职责、依赖方向与包布局见 `docs/architecture.md`。调度与新鲜度的规范见 `REQ-SCHED-01..04`、`REQ-QUALITY-01..05`；决策理由见 ADR-0001、ADR-0003、ADR-0004。

### 6.1 扩展点

- 南向 `Driver`：协议读写、能力声明、推送事件。
- 北向 `Channel`：发布/订阅与连接状态。
- 物模型 `UplinkAdapter` / `DownlinkAdapter`：报文编码、调用解析、payload 解码。
- 持久化 `Store`：幂等记录、设备状态与属性快照。

新增协议、通道或适配器只新增实现并在装配处接线；内核不因新增实现而改变。

### 6.2 内核组件

调度、状态、调用、转发、事件总线与健康状态的职责与明确边界见 `docs/architecture.md`。

### 6.3 调度与可靠性

调度算法、分级确认、幂等与队列治理的规范见 `docs/spec/spec.md` 的 `REQ-*`；理由见 ADR-0003、ADR-0004、ADR-0005。

## 11. 非功能要求

| 维度 | 要求 |
|---|---|
| 资源 | 常驻内存 ≤ 100 MB（64 设备 / 512 点位）；单核 CPU 占用 < 10% |
| 启动 | 冷启动 ≤ 3 s 进入可服务状态 |
| 采集精度 | 周期抖动 ≤ ±10%（负载正常时；真实时钟判据见 `docs/testing.md`） |
| 可靠性 | 单设备读写失败不影响其他设备；任一驱动 panic 必须被 recover 且不拖垮进程 |
| 可观测 | 每链路：成功/失败/超时计数；每设备：最后成功时间、质量分布 |
| 安全 | 凭据取自配置或环境变量，日志**必须脱敏**；不打印 payload 中的凭据 |
| 兼容 | Go 1.27（toolchain go1.27.4）；`CGO_ENABLED=0` 静态二进制，交叉编译 arm64/amd64；嵌入式存储用 `bbolt`（纯 Go，无 cgo） |

## 13. 风险与未决

| 风险 | 影响 | 缓解 |
|---|---|---|
| 无寄存器表、无 payload 规范 | 真实设备接入时需返工解码与映射 | 全部下沉配置 + 台账登记；只替换配置/夹具 |
| ChirpStack 版本与集成配置未知 | 下行可能完全不通 | 事实核实 + 启动自检 `config-check` 探活 |
| Class A 阀门响应慢 | 云端以为「指令失败」 | 分级确认 + 明确阶段语义 + 文档说明 |
| 网关存储小 | 缓存写满 | 有界容量 + 淘汰 + 丢弃可观测 |
| 485 现场干扰 | 采集抖动 | 重试/退避、质量字段、`link_down` 事件 |
| 客户云端字段规范后到 | 报文要改 | Adapter 可替换，报文层不渗入内核 |
| **阀门写寄存器语义未确认**（台账 B12） | 重发可能导致阀门反复动作 | 默认「一次 + 写后回读」，不重发；**列为实物联调 P0 阻塞项** |
| 队列合并与设备取队列的竞态 | 设备可能先执行旧值 | 纠正而非重放（ADR-0005）；合并常态保持队列最新 |
| 幂等终态未知 | 重启后必须拒绝执行，云端需换 `seq` | 合同写死；`seq` 位宽与重试窗口见 `docs/contracts/external.md` |

未决：客户侧资料缺口（P0/P1 清单）见 `docs/缺口台账.md` §F；平台侧事实已按要求核实，结论见 ADR-0002。
