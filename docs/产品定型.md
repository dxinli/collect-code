## 1. 一句话定位

一个部署在边缘的**通用采集引擎**：南向按配置接任意设备协议，北向用统一物模型走 MQTT JSON，把「LoRaWAN 网关」和「RS485 融合终端」收敛成**同一个二进制、同一套配置模型**。

**不改代码、只改 YAML**，就能完成两类变更：

- **实例配置**（当场可改，改值即可）：加一台同类设备、改站号、改采集周期、改上报周期、改北向 Broker/Topic 前缀。
- **模型配置**（改 YAML，不动代码，但属模型变更，需按配置评审流程走）：换设备型号（新增/替换 profile 的点位映射）、调整 Topic 层级结构、调整 payload 字段位域。

**唯一需要写代码的变更**是：新增一种协议（新驱动）、新增一种北向传输（新通道）、更换云端字段语义（新适配器）—— 这三件事正是设计上预期要扩展的点。

## 2. 为什么这样抽象（依据，不是想象）

| 需求 1 | 需求 2 | 引擎吸收为 |
|---|---|---|
| LoRa 上行 / 下行（ChirpStack v4） | — | 驱动 `lorawan`（上行走 MQTT integration，下行走 gRPC，见 ADR-0002） |
| Modbus TCP 读写阀门 | RS485 读传感器 | 驱动 `modbus`（TCP/RTU 共用编解码） |
| 电动阀物模型：属性/服务/事件/超时 | 「mqtt 协议传给平台」 | 适配器 `irrigation-v1` + 北向通道 `mqtt` |
| 网关本机有 ChirpStack，数据上云链路保留 | 无 | 引擎是**旁路**，只经 API，绝不抢占端口/会话 |

三条支撑事实：

1. **同一台电动阀可能经 LoRa 接入，也可能经 Modbus 接入**，但对云端必须是同一个物模型。→ 「设备」与「接入路径」必须分离，这是产品抽象的根。
2. **需求 1 要求保留 ChirpStack 原上云链路**。→ 引擎只能作为消费者，不能接管射频与网络服务器。
3. **需求 2 链路极窄（485 → MQTT）**。→ 证明北向与南向正交，窄链路就是最好的第一条垂直切片。

## 3. 目标与非目标

### 目标

- **G1** 单二进制、单 YAML 配置，在 `linux/arm64` 上 systemd 常驻运行。
- **G2** 南向：Modbus TCP、Modbus RTU/RS485、LoRaWAN（经 ChirpStack v4）三种驱动，可同时启用多条链路。
- **G3** 北向：MQTT JSON，属性上报 / 服务下发 / 服务回执 / 事件上报四类报文。
- **G4** 可靠性：指令至少一次 + 幂等；设备离线判定；北向断线补发（有界）。
- **G5** 可运维：结构化日志、只读健康/指标端点、配置校验子命令。
- **G6** 可联调：内置模拟器（Modbus 从站 / ChirpStack 桩 / MQTT 云端桩），无实物也能验收全链路。

### 非目标（明确不做，防止范围爆炸）

| 编号 | 不做 | 理由 |
|---|---|---|
| N1 | 云端后台页面、数据库 | 需求明确不做 |
| N2 | 修改 ChirpStack 源码 | 只做 API/集成层对接 |
| N3 | 硬件驱动开发 | 硬件已就绪 |
| N4 | 设备固件 OTA | 属设备侧职责 |
| N5 | 本地 Web UI / 配置界面 | 配置是运维资产，走文件 + Git |
| N6 | 多节点编排 / 云端配置下发 | v1 单节点自治，编排属云端 |
| N7 | **定时灌溉策略、轮灌计划、规则引擎** | 业务策略属云端；边缘只执行与反馈 |
| N8 | 主备双接入路径自动切换与对账 | 见 D9，v1 一台设备只声明一条路径 |
| N9 | 一机一密、远程凭据轮换 | v1 用配置内静态凭据，预留接口 |

> N7 是这类项目最常见的范围失控点：一旦边缘开始「自己做灌溉决策」，云端与边缘就会出现两套事实来源。产品边界必须画死。

## 5. 核心场景（泳道）

### 5.1 周期采集上行（Modbus 链路）

```
云端            MQTT通道          引擎(调度/状态/物模型)          Modbus驱动          链路/设备
                  │                       │                          │                   │
                  │                 按链路 tick                   │                   │
                  │                       │── ReadPoints ──────────> │── 03/04 ────────> │
                  │                       │<─ Samples(含quality) ─── │<─ 响应/超时 ───── │
                  │                       │ 合并为设备属性 + 变化比对 │                   │
                  │<── property.post ─────│ (snapshot / delta)       │                   │
                  │  (QoS1)               │                          │                   │
```

- 调度单位是**链路**，不是设备：一条 485 总线上的多台从站按队列串行，避免总线冲突。
- 上报周期分两档：**快照** `snapshot_interval`（默认 60 s，全量）、**增量** `delta`（变化去抖 2 s）。
- 每个属性**必带 `quality`**（good/stale/bad）。读失败不上报假值。

### 5.2 云端服务调用 → 阀门动作 → 两级回执（LoRa）

```
云端         MQTT通道      引擎(Invoker)      LoRaWAN驱动      ChirpStack        阀门
  │             │              │                 │               │              │
  │─invoke ────>│─ 解析/校验 ─>│                 │               │              │
  │             │              │ 幂等检查(seq)    │               │              │
  │             │              │── WritePoint ──>│── enqueue ───>│              │
  │             │              │<─ accepted ─────│<─ 202 ────────│              │
  │             │              │  等待回执窗口     │               │─ 下一个上行窗口下发 ─>│
  │             │              │<──────── Driver.Events: txack ───│              │  (射频送达)
  │             │              │<──── Driver.Events: uplink(业务ACK字段) ─────│  (动作完成)
  │             │<─ service.reply(code=0) ────────│               │              │
```

**两级回执是本产品的核心可靠性语义：**

| 级别 | 含义 | 来源 | 判什么 |
|---|---|---|---|
| L1 `txack` | 下行帧已被设备射频接收 | ChirpStack 事件 | 网络层送达 |
| L2 业务 ACK | 阀门确实执行到了目标开度 | 设备后续上行的 payload 字段 | 业务完成 |

只有 L2 才算服务成功。L1 到、L2 未到 → `code=5041 cmd_unconfirmed`，绝不是 `ok`。
（payload 中 ACK 字段位置是 `ASSUMED`，见台账 A10。）

### 5.3 设备离线判定与恢复

- 每台设备维护 `last_success_at`，**只由新鲜观测推进**（读到新鲜数据 / 收到带业务值的新上行）。L1 txack 只更新「下发链路可用」，不算设备在线证据（D16）。
- 超过 `offline_after`（Modbus 默认 3× 周期；LoRa 默认 3× 期望上报间隔）→ 状态变 `offline`，发 `device_offline` 事件（去重，只在状态翻转时发）。
- 恢复时发 `device_online` + 一帧**全量快照**，云端无需自己补齐断档。
- 离线期间属性标记 `quality=stale`，`ts` 不更新。

### 5.4 北向断线（store-and-forward）

```
MQTT 断开 → 事件进入有界队列（容量 1000，满则丢最旧并记 event_dropped）
         → 属性只保留「每设备最新快照」（覆盖写，不排队）
MQTT 恢复 → 先发全部事件（按时间序、可去重）→ 再发每设备最新快照
```

全量历史不缓存：网关存储只有几 GB，补发几小时历史既无业务价值，又有写满磁盘的风险。

### 5.5 配置热重载（SIGHUP）

改 `devices.yaml` / `profiles/` 后 `kill -HUP`：重新解析并**差别应用**——新增设备启动、移除设备停止、改周期的生效、改点位的重建映射。**解析失败则整体不应用并报错**，旧配置继续跑（不留半配置状态）。

进行中的操作按以下规则处理（评审 W7）：

| 进行中的对象 | 重载后的处理 |
|---|---|
| 采集任务 | 新 tick 用新周期；当前 tick 跑完即按新配置 |
| 服务调用（未完成） | **不取消**，按受理时的参数走完；幂等记录不因重载丢失 |
| 断线缓存 | 保留；被移除设备的事件仍补发（云端需要知道它曾存在） |
| 已移除设备 | 不再采集/下发，状态转为 `removed` 并上报一次 `device_removed` |

### 5.6 无实物联调

`collect-code simulate` 一个进程同时起：Modbus TCP 从站（多站号）、虚拟串口 RTU 从站、**ChirpStack 桩（gRPC Enqueue/GetQueue/FlushQueue + MQTT integration 事件发布）**、**MQTT 云端桩（订阅上行、发送下行 invoke）**。引擎跑在另一进程连它，跑完整的 5.1–5.5。

## 6. 架构与接口契约

### 6.1 南向：`Driver`

```go
type Driver interface {
    Name() string
    Open(ctx context.Context) error
    Close() error

    // 声明的能力，内核只据此决定「是否轮询」，不做协议分支判断
    Capabilities() Capabilities

    // 拉取型驱动（Modbus）返回点位；推送型驱动（LoRa）返回「最后一次观测」，
    // 允许空结果。Sample.At 是值实际获得的时刻，驱动不得伪造成 now。
    Read(ctx context.Context, req ReadRequest) ([]Sample, Outcome)
    // 写一个点位；只表示「已交给下层」，后续状态经命令事件回传
    Write(ctx context.Context, req WriteRequest) (CommandHandle, error)
    // 推送型驱动把回执/自发事件从这里交付；拉取型返回 nil
    Events() <-chan DriverEvent
    Status() LinkStatus    // up/degraded/down + 计数器
}

type Capabilities struct {
    Pollable  bool   // 内核调度器是否要给它排采集任务
    Verifiable bool  // 是否支持写后回读（决定能否达到 completed）
}

type Sample struct {
    PointKey string
    Value    any      // 数字/布尔/字符串
    Quality  Quality  // good|stale|bad —— 由驱动按自身观测情况给出初值
    At       time.Time // 值实际获得时刻
    Err      string
}

// Outcome 区分「部分成功 / 全部失败 / 不支持」，让内核正确更新每点质量
type Outcome int
const (
    OutcomeOK Outcome = iota      // 全部点位读到
    OutcomePartial                // 部分点位失败，失败点在 Sample 里带 bad
    OutcomeFailed                 // 整次读取失败（链路错）
    OutcomeUnsupported            // 推送型驱动无新观测
)

// CommandHandle 是显式状态机，取代原来的两个布尔
type CommandHandle struct {
    Ref   string       // 与后续 DriverEvent 关联
    State CommandState // 初始一般为 accepted（Modbus 可直达 completed）
}
type CommandState int
const (
    CmdAccepted  CommandState = iota // 已交给下层（LoRa: 已入队 / Modbus: 已发帧）
    CmdDelivered                     // 射频/网络层已送达（LoRa: txack）
    CmdCompleted                     // 设备确认执行（L2）
    CmdFailed
)

type DriverEvent struct {
    Kind    EventKind  // uplink | txack | device_status | driver_error
    Device  string
    Ref     string     // 与 CommandHandle.Ref 关联
    State   CommandState // Ref 非空时携带最新状态
    Sample  []Sample   // uplink 时解出或直传的点位
    Payload []byte     // 原始字节，交由 UplinkAdapter 解码（payload 编解码在适配器）
    At      time.Time
}
```

四条由接口形状强制、写进文档的规则（评审 S1/S3/W3/W4 的产物）：

1. **新鲜度只由内核算**。驱动从不自称 `good`；内核用 `Sample.At` 与 `freshness_window` 比较得出 `good/stale`。驱动给 `bad` 是例外（链路错），内核不降级为 `good`。
2. **`last_success_at` 只由新鲜观测推进**。一次 `Read` 若返回的全部样本都超龄，**不推进**在线判定。这样 LoRa 缓存旧值不会把离线设备谎报成在线。
3. **`Events()` 是 `Driver` 的一等方法**，不是可选接口。拉取型返回 `nil`，内核用 `select` 同时处理通道与 nil 通道，**不需要任何类型断言**。新增推送协议不再触碰内核。
4. **命令状态只能前进**（`accepted → delivered → completed`，或任意态 → `failed`）。倒退视为驱动缺陷，内核记录 `driver_error` 事件而不改状态。

> 关键取舍：**不让 LoRa 驱动假装成轮询驱动**。它声明 `Pollable=false`，内核不给它排采集任务；`Read` 仅作快照读取手段，结果永远按自身 `At` 判新鲜度。这样「一种形状、两种语义」既统一又不撒谎。

### 6.2 北向：`Channel`

```go
type Channel interface {
    Name() string
    Publish(ctx context.Context, msg Message) error
    Subscribe(ctx context.Context, filter string, h MessageHandler) error
    Status() LinkStatus
}

type Message struct {
    Topic   string
    Payload []byte     // JSON，由 Adapter 生成
    QoS     byte
    Retain  bool
    DedupKey string    // 断线重连后用于抑制重复补发
}
```

通道不理解业务字段：`Adapter` 产 `Payload`，通道只搬运。换 Kafka/HTTP 时只新增通道。

### 6.3 物模型：`UplinkAdapter` / `DownlinkAdapter`

上行编码与下行解析的变化原因不同（云端字段规范 vs 服务调用格式），所以拆成两个接口。一个适配器可以同时实现两者，也可以只实现其一。

```go
// 上行：属性/事件 → 报文。变化原因 = 云端字段规范
type UplinkAdapter interface {
    Name() string
    PropertyReport(d Device, props []Property, mode ReportMode) (Message, error)
    EventReport(d Device, ev Event) (Message, error)
    // LoRa 原始 payload → 属性。变化原因 = 设备 payload 编码规范
    DecodePayload(d Device, raw []byte) ([]Property, error)
}

// 下行：报文 → 服务调用；结果 → 回执。变化原因 = 服务调用格式
type DownlinkAdapter interface {
    Name() string
    ParseInvocation(topic string, payload []byte) (Invocation, error)
    ServiceReply(inv Invocation, res InvocationResult) (Message, error)
}
```

自研 `irrigation-v1` 同时实现两者，是默认装配。将来客户给了正式字段规范：
- 只变上行字段 → 新写一个 `UplinkAdapter`，下行不动；
- 上下行都变 → 两个都替换；
- 只变 LoRa payload 编解码 → 换 `DecodePayload` 的实现，北向完全不动。

**Topic 模板也是 Adapter 的配置**（`topics:` 段），不是代码常量。改 `v1/` 前缀或层级顺序只改配置。

### 6.3.1 调度器算法（评审 S5 的产物）

```
每链路一个 goroutine，持有 phase 对齐的 ticker：
  next = start + k*period          # 相位锁定，绝不 Sleep(period)
  每个 tick:
    快照当前任务表（避免重载时撕裂）
    顺序遍历该链路的设备，每设备一个独立的 read_deadline
    设备超时 → 该设备全部点位标 bad，立即 next 设备，不阻塞总线
    本轮超出 period → 记录 missed_tick，跳过到下一个对齐时刻（不补跑）
```

- **不补跑**：补跑会让后续 tick 连续拥挤，抖动反而放大。
- **单设备超时立即放弃**：一条 485 总线挂 8 个离线从站时，最坏耗时被 `8 × read_deadline` 封顶，而不是 `8 × 重试链` 无界。
- 抖动验收：正常负载下 `|实际 - 计划| ≤ 10% period`，且**不累积**（相位锁定保证）。

### 6.4 内核组件

| 组件 | 职责 | 明确不做 |
|---|---|---|
| `scheduler` | 相位锁定 tick、链路内串行、单设备 deadline、missed_tick | 不做重试策略（在 Driver/Invoker） |
| `state` | 设备状态机、属性快照、**新鲜度统一计算** | 不持久化全部历史 |
| `invoker` | 服务调用生命周期、幂等去重、超时与重发、下行队列治理 | 不解读业务参数（DownlinkAdapter 校验） |
| `forward` | 两级缓存、补发顺序、容量/TTL 淘汰 | 不保证跨重启补发（事件允许丢，见 D8） |
| `eventbus` | 进程内事件分发、去重键 | 不做规则/订阅表达式 |
| `status` | 健康端点（只读）、计数器 | 不做写操作、不做配置展示 |

## 9. 关键设计决策

| 编号 | 决策 | 理由 | 替代方案与为何不选 |
|---|---|---|---|
| D1 | 三个扩展点全部为**接口**，内核不 import 实现 | 组件化/接口化的硬要求；单测可用假实现 | 直接耦合具体库：换协议要改内核 |
| D2 | 装配只发生在 `cmd` | 唯一知道全部实现的地方，依赖方向清晰 | 各包自注册：隐蔽、难控初始化顺序 |
| D3 | 服务调用**至少一次 + 幂等 seq** | 阀门误动作是物理后果；去重是唯一现实解 | 至多一次：不可接受；强一致事务：边缘无此条件 |
| D4 | 幂等水位（每设备 last_seq + 近期窗口）**落盘** | 重启后不能重复执行同一条指令 | 仅内存：重启即失效 |
| D5 | LoRa 用**两级回执**（txack + 业务 ACK） | 射频送达 ≠ 阀门动了；混为一谈会谎报成功 | 只认 txack：谎报；只认业务 ACK：无送达信息 |
| D6 | LoRa 超时按**上报窗口数**算，不按固定秒 | Class A 只能等设备来上行；固定秒数必错 | 固定 30 s：Class A 下几乎必然误判超时 |
| D7 | 调度单位是**链路**，设备是链路内的任务 | 485/TCP 一条链路共享带宽与冲突域 | 按设备并发：总线冲突、重试互相踩踏 |
| D8 | 缓存分两级：事件有界队列 + 属性仅最新快照 | 存储有限；历史补发价值低、风险高 | 全量缓存：写满磁盘比断线更危险 |
| D9 | 一台设备**只声明一条接入路径**；双路径属 v2 | v1 避免对账一致性问题；需求也没有双路径 | 主备自动切换：需要一致性对账，范围失控 |
| D10 | 点位映射**只在配置**，不在代码 | 现场换型号/站号不能要重新发版 | 编进代码：每次小改都要重发固件 |
| D11 | 默认不监听任何 TCP；健康端点默认关闭，开启仅绑 `127.0.0.1:9100` | 网关端口紧张，ChirpStack 已占 8080；无 UI 需求 | 开 HTTP 管理接口：违背 N5，且是攻击面 |
| D12 | 时钟：有 NTP 用墙钟；无则用单调时钟排序，`ts` 由注入的 `Clock` 提供 | 网关常无 NTP，墙钟跳变会污染时序 | 直接用 `time.Now()`：跳变导致超时判定错乱 |
| D13 | 日志为 JSON 结构化，字段固定 | 现场排障靠 grep 字段，不靠自然语言 | 自由文本：不可聚合 |
| D15 | `Events()` 升为 `Driver` **一等方法**，不用可选接口/类型断言 | 否则内核得对 `EventSource` 断言，新增推送协议要改内核，违背 D1 | 可选接口：内核反向耦合（评审 S2） |
| D16 | 新鲜度由**内核**用 `Sample.At` 统一计算，驱动不自称 `good`；`last_success_at` 只由新鲜观测推进 | 否则 LoRa 缓存旧值会把离线设备谎报在线 | 驱动自报质量：协议各异、无法统一（评审 S1/S3） |
| D17 | 命令用显式状态机 `accepted→delivered→completed/failed`，状态只前进 | 两个布尔表达不了「已送达未执行」；Modbus 写响应 ≠ 物理到位 | 布尔对：状态空间不足（评审 S3） |
| D18 | 适配器拆 `UplinkAdapter` / `DownlinkAdapter`，`DecodePayload` 归上行侧 | 上行变因是字段规范，下行变因是调用格式；合并会让只改一侧也重写另一侧 | 单一 Adapter：两个变化原因（评审 S4） |
| D19 | 调度器**相位锁定**（`next = start + k*period`），missed_tick 不补跑，单设备独立 deadline | 简单 `Sleep(period)` 会累积漂移；离线从站会阻塞整条总线 | 顺序阻塞读：抖动无界、总线被一台设备拖死（评审 S5） |
| D20 | 幂等用 **append-only journal + 周期截断**，命令入队前先 append+fsync | 崩溃窗口必须小于「执行副作用」；JSON 整文件重写会磨损且损坏后不可恢复 | 每次重写 `state.json`：写放大 + 损坏无恢复（评审 S6/S9） |
| D21 | `seq` 按**设备**单调递增、由**云端**分配并保证在窗口内不回绕；边缘只做窗口内去重 | 若不同 service 复用 seq，去重会错杀合法指令 | 全局 seq：跨设备无意义；边缘自增：与云端无法对齐（评审 W5） |
| D22 | 每设备 **pending 下行上限**（默认 4）：超限时按「同 service 合并，保留最新」+ 淘汰最旧并发 `cmd_dropped` | Class A 离线时重发会把 ChirpStack 队列塞满，设备回来先执行最旧指令 | 无限制重发：覆盖新款开度、队列拥塞（评审 S7） |
| D23 | Modbus 写操作**默认「一次 + 写后回读验证」**，而非重发；重发仅在 `capabilities.Verifiable=false` 且客户确认寄存器写幂等时启用 | 若厂商寄存器是「写即动作」，重发等于让阀门反复动 | 一律至少一次重发：未确认前提下有物理风险（评审 S8） |
| D24 | 配置化拆两档：**实例配置**（加设备/站号/周期，免改代码）与**模型配置**（profile 与 Topic 模板，改 YAML 不改代码，但属「模型变更」需评审） | 把「换型号/改 Topic」含糊地说成「改个值」是不可兑现的承诺 | 宣称全部即时可改：名不副实（评审 S10） |

### D25（已定稿，事实核实后）：LoRa 接入方式

| 方向 | 方案 | 事实依据 |
|---|---|---|
| 上行 | 订阅 ChirpStack **MQTT integration**（只读 MQTT 客户端） | 默认 topic `application/{app_id}/device/{dev_eui}/event/{event}`；事件 `up/status/join/ack/txack/log/location/integration`；JSON 下 `data` 为 **base64** |
| 下行 | **gRPC** `DeviceService/Enqueue`（官方 Go 客户端 `chirpstack/api/go/v4`） | v4 已移除内嵌 REST；REST 由独立组件 `chirpstack-rest-api` 提供、默认 **8090**，现场很可能未安装 |
| 队列治理 | `GetQueue` + `FlushQueue` | 支撑 D22 的合并与淘汰，无需额外组件 |

**被否决**：

| 方案 | 否决理由 |
|---|---|
| REST 下行（`POST /api/devices/{devEui}/queue`，由 rest-api 提供） | 依赖现场额外安装 rest-api（8090），多一个组件与故障点 |
| `InternalService.StreamDeviceEvents` 作上行 | 读 Redis Stream，默认仅保留 **10 条**事件，重启/断线必丢帧 |
| 直连 Redis Streams 作主上行 | 耦合内部实现，需 Redis 凭据，版本升级易断 |
| retained `state_topic` 判在线 | `config.rs` / `integration/mqtt.rs` 在所有 v4 tag 均无此字段，**代码未实现** |

详见 `docs/adr/0002-chirpstack-integration-boundary.md`。类 A 下行的权威表述：*"Only after an uplink transmission by the device, ChirpStack is able to schedule a downlink transmission."* —— 这正是 D6（按窗口算超时）的直接依据。

## 10. 物模型与报文契约（自研 `irrigation-v1`）

> 字段名英文、文档中文。`msg_id` 全局唯一（雪花/ULID），用于云端幂等。

### 10.1 Topic

| 方向 | Topic | 说明 |
|---|---|---|
| 上行 | `v1/{product_key}/{device_sn}/property/post` | 属性（快照/增量） |
| 上行 | `v1/{product_key}/{device_sn}/service/reply` | 服务回执 |
| 上行 | `v1/{product_key}/{device_sn}/event/{event_id}` | 事件 |
| 下行 | `v1/{product_key}/{device_sn}/service/invoke` | 服务调用 |
| 上行 | `v1/{product_key}/$nodes/{node_id}/state` | **节点级** LWT（一条 MQTT 连接只有一个 Will）；`{"online":false,"node_id":"..."}` |

> Topic 是 `UplinkAdapter`/`DownlinkAdapter` 的配置模板，不是代码常量（D24）。改前缀或层级只改 YAML。
> 设备级离线不靠 LWT（一条连接无法为每台设备发遗嘱），靠 `device_offline` 事件 + 属性里的 `online` 字段。

### 10.2 属性上报

```json
{
  "msg_id": "01JCH7...",
  "type": "property.post",
  "mode": "snapshot",
  "product_key": "irrigation",
  "device_sn": "VALVE-0001",
  "device_type": "valve",
  "ts": 1763400000123,
  "online": true,
  "properties": [
    {"key": "opening",            "value": 42.5, "unit": "%",   "quality": "good",  "ts": 1763400000000},
    {"key": "target_opening",     "value": 50.0, "unit": "%",   "quality": "good",  "ts": 1763400000000},
    {"key": "medium_temperature", "value": 23.4, "unit": "℃",   "quality": "good",  "ts": 1763399999000},
    {"key": "pipe_pressure",      "value": 0.32, "unit": "MPa", "quality": "stale", "ts": 1763397600000},
    {"key": "fault_code",         "value": 0,    "unit": null,  "quality": "good",  "ts": 1763400000000}
  ]
}
```

- `mode`: `snapshot`（全量）｜`delta`（只有变化项）。
- `quality`: `good` | `stale` | `bad`。**必填**。
- 属性 `ts` 是该值**实际获得**的时间，不是发送时间；`stale` 时故意不前移。

### 10.3 服务调用 / 回执

```json
// 下行
{"msg_id":"01JCH8...","type":"service.invoke","device_sn":"VALVE-0001",
 "service_id":"set_opening","seq":17,"params":{"opening":50.0},
 "timeout_ms":600000,"issued_ts":1763400000000}

// 上行
{"msg_id":"01JCH9...","type":"service.reply","device_sn":"VALVE-0001",
 "service_id":"set_opening","seq":17,"code":0,"msg":"ok",
 "data":{"accepted":true,"confirmed":true,"opening":49.8},"elapsed_ms":512300}
```

| code | 含义 |
|---|---|
| 0 | 成功（L2 已确认） |
| 4001 | 参数非法（越界/类型/缺字段） |
| 4002 | 设备不存在或未启用 |
| 4003 | `seq` 重复 → **幂等命中，返回首次结果** |
| 4041 | 点位未映射 / 只读 |
| 5040 | 下发失败（驱动/Link 不可用） |
| 5041 | 已送达（L1）但未获业务确认（L2） |
| 5042 | 重发耗尽仍无回执 |

### 10.4 事件

```json
{"msg_id":"01JCHA...","type":"event","device_sn":"VALVE-0001","event_id":"cmd_timeout",
 "level":"warn","ts":1763400600000,
 "data":{"service_id":"set_opening","seq":17,"attempts":3},
 "dedup_key":"VALVE-0001:cmd_timeout:17"}
```

| event_id | 触发 |
|---|---|
| `device_offline` / `device_online` | 状态翻转 |
| `valve_fault` | 故障码位图变化且非 0 |
| `cmd_timeout` | 重发耗尽 |
| `cmd_rejected` | 设备侧拒绝（payload 返回错误码） |
| `event_dropped` | 缓存满丢事件（带丢的条数） |
| `link_down` / `link_up` | 南向链路状态翻转 |
| `cmd_dropped` | 下行队列超限或同 service 合并导致的丢弃 |
| `device_removed` | 配置重载移除设备（一次性） |
| `driver_error` | 驱动报告异常（状态倒退、协议错误） |
| `config_rejected` | SIGHUP 解析失败，旧配置继续运行 |

## 11. 非功能要求

| 维度 | 要求 |
|---|---|
| 资源 | 常驻内存 ≤ 100 MB（64 设备 / 512 点位）；单核 CPU 占用 < 10% |
| 启动 | 冷启动 ≤ 3 s 进入可服务状态 |
| 采集精度 | 周期抖动 ≤ ±10%（负载正常时） |
| 可靠性 | 单设备读写失败不影响其他设备；任一驱动 panic 必须被 recover 且不拖垮进程 |
| 可观测 | 每链路：成功/失败/超时计数；每设备：最后成功时间、质量分布 |
| 安全 | 凭据取自配置或环境变量，日志**必须脱敏**；不打印 payload 中的凭据 |
| 兼容 | Go ≥ 1.22；`CGO_ENABLED=0` 静态二进制，交叉编译 arm64/amd64 |

## 12. 验收标准（对齐需求文档交付要求）

1. 上行稳定：模拟器环境下连续 24 h，属性上报无中断、无假值；断线恢复后快照正确。
2. 下行可靠：服务调用在 L1/L2 三种组合下回执分类正确；重复 invoke 只执行一次。
3. 超时逻辑：Class A 模拟下，未获 ACK 按窗口超时、重发上限生效、`cmd_timeout` 事件正确。
4. 配置化：**实例配置**（加设备/改站号/改周期）改 YAML 即生效、无需重启（SIGHUP）；**模型配置**（换型号/改 Topic/改 payload 位域）改 YAML 即生效、无需改代码。两者都有 `config-check` 校验与回滚（坏配置不生效）。
5. 调度：正常负载下周期抖动 ≤ ±10% 且不累积；一条链路挂 8 个离线从站时，单个 tick 的耗时被单设备 deadline 封顶，不拖垮其他链路。
6. 幂等：同一 `seq` 重复 invoke 只执行一次；进程在「已受理未执行」处被 kill -9 后重启，不重复动作（journal 可重放验证）。
7. 下行队列治理：Class A 设备离线时连续下发 10 条 `set_opening`，重连后设备只执行最后一个目标值。
8. 交付物：源码（git 历史清晰）、`Makefile`/构建脚本、部署文档、报文样例、测试说明、模拟器使用说明。
9. 文档：Topic/字段/Modbus 映射/部署/排障五个章节齐全。

## 13. 风险与未决

| 风险 | 影响 | 缓解 |
|---|---|---|
| 无寄存器表、无 payload 规范 | 真实设备接入时需返工解码与映射 | 全部下沉配置 + 台账登记；只替换配置/夹具 |
| ChirpStack 版本与集成配置未知 | 下行可能完全不通 | 事实核实 + 启动自检 `config-check` 探活 |
| Class A 阀门响应慢 | 云端以为「指令失败」 | 两级回执 + `code=5041` 明确语义 + 文档说明 |
| 网关存储小 | 缓存写满 | 有界容量 + 淘汰 + `event_dropped` |
| 485 现场干扰 | 采集抖动 | 重试/退避、质量字段、`link_down` 事件 |
| 客户云端字段规范后到 | 报文要改 | Adapter 可替换，报文层不渗入内核 |

未决：客户侧资料缺口（P0/P1 清单）见 `docs/缺口台账.md` §F；平台侧事实已按要求核实，结论见 ADR-0002。
