# Spec：采集引擎行为契约

- Status: accepted
- Version: 3.2.0
- Supersedes: v2-draft（tag `spec-v2-draft`）
- Normative: §1–§9
- Change log: `docs/spec/CHANGELOG.md`

本文件只定义**行为**。外部报文与 code/event 见 `docs/contracts/external.md`；配置键与默认值见 `docs/contracts/config.md`；Store 语义见 `docs/contracts/store.md`；模拟器契约见 `docs/contracts/simulator.md`；决策理由见 `docs/adr/`；术语见 `GLOSSARY.md`。

规范词：**必须**表示强制要求，**不得**表示禁止，**应当**表示除非有记录在案的例外否则必须遵守。

## 1. 目的与范围

**REQ-SCOPE-01** 引擎必须以单个二进制运行于边缘节点，从 YAML 配置装配南向链路，并通过一个北向适配器发布统一物模型报文。它必须同时支持两类现场：

1. LoRaWAN 网关：旁路消费既有 ChirpStack 的上下行，不得改动或抢占 ChirpStack 的端口与会话。
2. RS485 融合终端：在一条总线上采集多台 Modbus 从站，并向上游发布。

引擎只执行采集、控制与反馈，不得在边缘实现灌溉策略、轮灌计划或规则引擎。v0.1–v1.0 范围内必须包含：Modbus 的 TCP、串口 RTU、RTU-over-TCP 三种传输；LoRaWAN 上下行；MQTT 北向；配置校验与 SIGHUP 重载；链路调度、设备状态、质量与新鲜度；服务调用幂等、分级确认与队列治理；北向断线有界缓存；结构化日志与只读健康端点；bbolt 状态库；内置模拟器；交付文档。范围外的项见 §9。

## 2. 系统不变量

**REQ-TIME-01** 内核与驱动必须只通过注入的时间抽象读取时间和等待；不得直接调用运行时时钟、定时器或睡眠函数。业务超时不得依赖运行时的上下文截止时间；上下文只用于取消传播。对外上报的时间戳必须来自同一注入时钟。

**REQ-SEAM-01** 南向驱动、北向通道、上行适配器与下行适配器必须经接口注入。内核不得 import 任何具体驱动、通道、适配器或持久化实现；装配只发生在命令入口。

**REQ-SEAM-02** 持久化只能经 `Store` 接口进入内核。生产实现只允许嵌入式 KV，且实现不得位于内核包内；测试实现必须与生产实现遵守同一份合同测试。

**REQ-QUALITY-01** 属性的最终质量只由内核计算。驱动可以报告观测初值 `bad`，内核不得把 `bad` 升级；通道只负责序列化，适配器不得改写质量。

**REQ-QUALITY-02** 设备的最后成功时间只由新鲜观测推进。超龄观测、推送型驱动的空结果、A 级发射确认与 B 级 MAC 确认都不得推进在线判定。

**REQ-QUALITY-03** 最终质量必须按下表判定：

| 输入 | 推进最后成功时间 | 最终质量 |
|---|---|---|
| 读取全部成功，且至少一个样本在有效陈旧阈值内，驱动未报 `bad` | 是 | 按“当前时间 − 样本时间 > 有效陈旧阈值”判 `good` 或 `stale` |
| 读取部分成功，且至少一个成功样本在阈值内 | 是，仅按新鲜样本 | 新鲜样本按上行规则；失败点 `bad` |
| 全部样本均超出阈值 | 否 | `stale`，样本时间不前移 |
| 读取整体失败 | 否 | 全部 `bad` |
| 推送型驱动无新观测 | 否 | 保持原值与质量 |
| 非法 payload 或解码失败 | 否 | `bad` |
| 仅 A 级或 B 级确认 | 否 | 不改变任何属性 |
| 业务上行且解码成功 | 是，按该上行的样本时间 | 同第一行 |

有效陈旧阈值取点位级阈值；点位未配置时取节点级新鲜度窗口（见 `docs/contracts/config.md`）。

**REQ-QUALITY-04** 连续若干个设备周期没有推进最后成功时间时，设备必须转为离线；离线期间属性保持 `stale` 且时间不前移。设备恢复时必须上报一次在线事件与一帧全量快照。设备周期的口径：轮询型为设备采集周期，推送型为期望上报间隔。

**REQ-QUALITY-05** 所有新鲜度、超时与离线边界必须使用严格大于比较；边界测试必须覆盖阈值减一纳秒、等于阈值、阈值加一纳秒（判据见 `docs/testing.md`）。

## 3. 采集调度

**REQ-SCHED-01** 每条链路必须使用相位锁定的计划时刻，计划时刻为“起点 + 整数倍周期”，不得用“每轮睡一个周期”累积漂移。迟到一个周期以上的 tick 必须记为 missed tick 并跳过，不得补跑。

**REQ-SCHED-02** 链路内设备必须串行处理；每台设备必须有自己的读取截止时间。设备超时后，其全部点位必须标 `bad`，并立即处理下一台设备，不得进入会阻塞总线的重试链。单个 tick 的最坏耗时必须被“设备数 × 单设备截止时间”封顶。

**REQ-SCHED-03** 一条链路的慢设备或离线设备不得拖死其他链路。链路状态变化必须可观测，并计入链路失败计数。

**REQ-SCHED-04** 采集周期属于设备：profile 提供默认值，设备可覆盖。链路 tick 必须取该链路所有设备采集周期的最大公约数，且不小于一秒；每个 tick 只处理到期的设备。上报周期属于节点，必须与采集周期解耦。

## 4. 服务调用语义

**REQ-INVOKE-01** 幂等键为 `(设备标识, seq)`。同一键的第一次受理才允许向下推进；重复键不得再次执行。受理语义是“至多一次”。`seq` 的分配、位宽、单调性与重试窗口见 `docs/contracts/external.md`。

**REQ-INVOKE-02** 幂等状态必须两阶段持久化：在产生任何外部副作用之前写入 `accepted`；在得到终态后写入 `final`。进程在 `accepted` 之后、`final` 之前崩溃时，重启后该键的终态视为未知，必须拒绝执行并要求调用方换新 `seq`，不得猜测性重放。已知终态的重复键必须回放首次结果。

**REQ-INVOKE-03** 回执必须分级：A 级表示网关已发射，B 级表示设备 MAC 已确认，C 级表示业务已完成。只有 C 级可以回成功码；A 或 B 级必须回“未确认”码并标明级别。发射确认或 MAC 确认本身永远不得视为业务成功。

**REQ-INVOKE-04** C 级判定必须在收到 A 或 B 级之后，由后续上行解码出的实际开度与引擎受理时记录的目标开度比较，且设备状态字表示“非运行中”。目标开度只由引擎在受理时写入状态，不得从设备 payload 解码。容差由服务配置决定。

**REQ-INVOKE-05** 失败码与重试边界必须遵循下表；code 的完整定义见 `docs/contracts/external.md`。

| 驱动 | 场景 | code | 重发 | 事件 |
|---|---|---|---|---|
| Modbus | 链路不可用或端口不可用 | 5040 | 否 | 链路故障事件 |
| Modbus | 帧已发出但设备在截止时间内无响应 | 5044 | 否 | 无，计入链路失败计数 |
| Modbus | 写入响应正常但回读超出容差 | 5043 | 否 | 无 |
| Modbus | 设备异常码表示参数非法 | 4001 | 否 | 无 |
| Modbus | 设备异常码表示设备内部错误 | 5044 | 否 | 无 |
| LoRa | 链路或 ChirpStack 不可用 | 5040 | 否 | 链路故障事件 |
| LoRa | 仅 A 级，或 A+B 级但无业务确认 | 5041，带阶段 | 是，至配置上限 | 耗尽后 `cmd_timeout` |
| LoRa | 重发耗尽仍无业务确认 | 5042 | — | `cmd_timeout` |
| LoRa | 业务确认已到但回读超出容差 | 5043 | 否 | 无 |

链路故障期间必须回 5040，不得消耗回执窗口，也不得产生 `cmd_timeout`。LoRa 的回执超时必须按设备上报窗口数计算，不得按固定秒数；窗口数与余量由配置决定。

## 5. 下行队列与缓存

**REQ-QUEUE-01** 同一设备同一服务的待下发调用必须始终合并，只保留最新目标；合并是常态，不是队列超限才触发。

**REQ-QUEUE-02** 每设备待下发条数必须有上限；超限时必须淘汰最旧条目并记录队列丢弃事件。合并只能撤销本引擎尚未被取走的条目，必须逐条精确操作；不得用整队清空代替合并。若旧条目已被取走或已下发，不得撤销，必须记为“下发后被取代”，等待其回执，随后以当前目标纠正。只有确实撤销了尚未下发的条目，或确实因超限放弃入队时，才记录队列丢弃事件；可能已下发的不确定性不得记为丢弃。

**REQ-QUEUE-03** “下发后被取代”不得触发历史重放。`set_opening` 的语义是“达到该开度”；纠正手段是再次下发当前目标，不是重发历史中间值。

**REQ-CACHE-01** 北向断线期间，事件必须进入有界队列，属性只保留每设备最新快照。恢复后必须先按时间顺序补发全部事件，再补发每设备最新快照。事件队列满时必须丢弃最旧事件并记录丢弃条数；丢弃事件本身必须可观测，不得被同一轮淘汰吞掉。

**REQ-CACHE-02** 不得缓存无限历史。事件丢失必须通过事件与计数器可观测；属性快照不得排队成历史序列。

## 6. 事件语义

**REQ-EVENT-01** 事件只在语义状态发生转移时产生，不得按每次采集重复产生。事件类型、级别与数据字段的枚举见 `docs/contracts/external.md`。设备故障码从零变非零、从一个非零值变为另一个非零值、从非零变回零，是三种不同的转移。

**REQ-EVENT-02** 一个事件实例由“设备 + 事件类型 + 实例序号”标识。实例序号必须在每次状态翻转时递增；同一实例的重发必须复用同一消息标识与去重键。状态再次翻转即新实例，不得被永久抑制。云端按去重键去重，这一责任必须在对接文档中写明。

**REQ-EVENT-03** 事件与属性是两条独立通道。事件不得替代属性快照；设备级在线状态必须通过属性与设备事件表达，节点级遗嘱消息只表示节点连接状态。

**REQ-UPLINK-01** LoRaWAN 上行去重必须优先使用 ChirpStack 提供的 `deduplicationId`；缺失时必须使用 `devEui` 与 `fCnt` 组合。去重窗口只存在于内存，容量固定为 1024，重启后不保证；当前版本不提供配置项。重复上行不得产生重复属性或事件。

## 7. 外部契约

Topic、报文 JSON、code、阶段、事件枚举、去重键、目标开度、`seq` 契约与节点遗嘱消息由 `docs/contracts/external.md` 定义。引擎必须按该合同发布与解析；本规范只约束行为语义，不重复字段定义。

## 8. 运维与命令行

**REQ-OPS-01** 收到 SIGHUP 时必须重新解析并校验整个配置包。解析或校验失败时，必须整体不应用、保留旧配置继续运行，并产生配置拒绝事件。成功时按差别应用：新增设备开始采集，移除设备停止采集与控制并上报一次移除事件，采集周期与点位映射按新配置生效。进行中的服务调用不得取消，必须按受理时的参数走完；断线缓存必须保留。链路、北向连接、节点标识、状态库路径与健康端点的变更属于需重启项，热重载不得静默应用。

**REQ-OPS-02** 健康端点默认关闭；开启后只能绑定配置的本地地址，不得监听其他接口。`/healthz` 只表示进程存活，`/status` 必须以固定结构反映持久化可用性、北向连接、各链路状态、每设备在线状态、队列深度与计数器。`/metrics` 必须暴露以下固定指标名与标签：

| 指标（含标签） | 类型 |
|---|---|
| `collector_link_ok{link}` | gauge |
| `collector_poll_total{link,result}` | counter |
| `collector_queue_depth{device}` | gauge |
| `collector_event_dropped_total` | counter |
| `collector_missed_ticks_total{link}` | counter |

指标名、类型与标签是契约，不得随意改名。标签取值：`result` ∈ {ok, fail, timeout}；`collector_link_ok` 取 0 或 1。启动与配置校验不得占用 ChirpStack 已使用的端口。

**REQ-OPS-03** 日志必须是 JSON 结构化，并在适用时包含设备、点位、`seq`、链路与原因字段。密码、令牌、授权头与 payload 原文必须脱敏；不得打印凭据明文。

**REQ-CLI-01** 必须提供以下子命令：常驻运行；配置解析、校验与生效摘要；模拟器；按设备一次性读取当前点位；按设备清空下行队列（必须显式二次确认）；版本与构建信息。一次性读取是推送型驱动读取路径的唯一调用方；调度器不得调用推送型驱动的读取。模拟器的 flag 与端点见 `docs/contracts/simulator.md`。

**REQ-SIM-01** 模拟器必须能在单个进程内提供 Modbus TCP 从站、RTU-over-TCP 从站、ChirpStack 桩、内嵌 MQTT broker 与云端桩，并暴露可观测的捕获、注入与控制接口。模拟值必须来自与被测系统相同的 profile 与缺口台账数据。模拟器必须自包含，不依赖容器、系统包管理器或外部服务；其传输实现必须用独立客户端验证，不得复用被测实现。具体契约见 `docs/contracts/simulator.md`。

## 9. 范围外

- 云端后台、数据库；修改 ChirpStack 源码；硬件驱动；固件 OTA。
- 本地 Web UI；多节点编排；云端配置下发。
- 定时灌溉策略、轮灌计划、规则引擎。
- 主备双接入路径自动切换与对账；一机一密、远程凭据轮换。
- LoRa payload 的压缩、条件或变长编码；v1 只支持声明式位域。
- MQTT QoS 2；TLS 双向认证；v1 只支持单向 TLS 与 CA 校验。
