# ADR-0005：下行队列治理不使用 FlushQueue——竞态窗口与最坏物理后果

- 状态：Accepted
- 日期：2026-11-17
- 相关：`docs/产品定型.md` D22/D14/D26、ADR-0002 决策 4、ADR-0004 决策 7、`docs/缺口台账.md` B12

## 背景

Class A 设备离线时，若对同一目标值反复下发，`ChirpStack` 的下行队列会堆积。官方行为是：队列项持久化，设备一旦上行触发接收窗口，就按 **FIFO** 下发，且 **mac-commands 优先于应用 payload**。这意味着堆积的旧指令会在设备上线后依次执行，最终覆盖掉新目标值——对阀门而言，可能出现「先开到 30%、再开到 70%、最后才到 10%」的物理动作序列。

`ChirpStack` 提供两个相关接口：`GetQueue`（读取当前队列）与 `FlushQueue`（整队清空）。

最直觉的做法是「`FlushQueue` 清空 + re-enqueue 新值」。第二轮评审指出这条路存在**不可消除的竞态**，本 ADR 记录分析结论与替代方案。

## 竞态分析

设我方要合并「旧目标 30%」与「新目标 10%」。用 flush 的做法是：

```
t0  GetQueue          → 看到 [30%]
t1  FlushQueue        → 清空
t2  Enqueue(10%)      → 重新入队
```

危险窗口在 `t1` 到 `t2` 之间，以及 `t1` 与设备接收窗口之间的交错：

| 交错 | 后果 | 严重度 |
|---|---|---|
| 设备在 `t0~t1` 上行，ChirpStack 立刻取走 30% 并下发 | 设备执行 30%；我方 flush 成功、记为 `cmd_dropped`；云端认为「10% 未下发成功」而重发 | **物理双动作**：设备先到 30% 再到 10%。若寄存器写非幂等（台账 B12 未确认），这是真实故障 |
| `t1~t2` 之间设备上行 | 空队列，设备收到 mac-command 或无事可做，**接收窗口被浪费** | 错过一个窗口周期；Class A 下等于多等一个上报间隔 |
| `t2` 之后设备上行 | 正常收到 10% | 无问题 |

关键点：**`FlushQueue` 是整队操作，无法表达「只撤销我这一条」**。它清掉的可能包括其它来源入队的条目（若同一 DevEUI 上还有别的系统在入队），而且返回值不足以让调用方判断「清掉的那些是否已下发」。

## 决策

1. **合并路径 = `GetQueue` + 逐条精确操作**，不用 `FlushQueue`：
   - `GetQueue` 读取当前队列，按我方入队时携带的 `ref`（写入队列项 `object` 字段的标记，或 `id` 回执）识别**我方条目**。
   - 只对「我方且 `isPending=true`」的条目做撤销，再 `Enqueue` 新值。
   - 若发现某条已被取走（`isPending=false` 或已不在队列中），**不撤销**，转为「已下发 → 等回执」，并记为 `superseded_after_send`。
2. **`FlushQueue` 仅保留给运维显式子命令**（`collect-code queue flush --device <sn>`），要求二次确认并写入日志；不参与自动合并。
3. **合并是常态，不是超限才做**（D22）：同设备同 `service_id` 永远只保留最新一条。这样设备上线时执行的一定是当前目标值，而不是历史中间值。
4. **可接受的最坏情形**：设备恰好在「新值入队前」取走了旧值。此时设备执行旧目标，我方在收到业务 ACK 后发现目标不一致，**以「下发新目标」纠正**，而不是重发旧指令。这条要在文档里写清：`set_opening` 的语义是「达到该开度」，纠正手段是再下发一次当前目标，不是重放历史。
5. **`cmd_dropped` 的语义收紧**：只在我方确实撤销了某条尚未下发条目时上报（`reason=superseded`），或队列超限我方放弃入队时上报（`reason=queue_full`）。**绝不**用 `cmd_dropped` 描述「可能已下发但不确定」的条目——那种情况归 `cmd_timeout` 或 `superseded_after_send`。
6. **不做跨进程强一致**：ChirpStack 是外部进程，我方的「读-判断-撤销」不是原子事务。本 ADR 承认这一点，用「纠正而非重放」的语义把竞态的最坏后果限制在「多一次正确动作」，而不是「多一次非幂等动作」。

## 后果

- 需要队列项携带我方标识。若 ChirpStack 版本的队列项字段不足以承载标识，`ref` 放在 `object`（`google.protobuf.Struct`）里作为应用层字段；不使用 `data` 的 payload 字节。
- 合并路径多一次 `GetQueue` RPC，频率等于服务调用频率而非采集频率，开销可接受。
- **v0.1 不受影响**：v0.1 只有 Modbus RTU 传感器，无下行队列。这条决策只在 v0.3（LoRa 下行）前必须先落地，且不需要为它提前编码。
- 若现场 ChirpStack 版本过老、`GetQueue` 行为不完整，降级为「不做合并、只做超限拒绝」，并在部署文档中标注该版本下的行为差异。

## 被否决的方案

- **`FlushQueue` + re-enqueue**：竞态不可消除，最坏导致物理双动作，且会误清其它来源的条目。
- **不做合并、只限制条数**：设备上线会按 FIFO 执行历史中间值，阀门出现无意义的多段动作。
- **本地维护「期望队列」并与远端对账**：需要额外一致性协议，且远端仍可能先取走；收益不抵复杂度。
- **依赖 `expiresAt`（v4.10.1+）自然过期**：可用作补充手段（缩短条目寿命），但不能替代合并——过期内设备仍可能上线取走旧值。
