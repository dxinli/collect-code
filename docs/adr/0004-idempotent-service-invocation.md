# ADR-0004：服务调用用「至多一次受理 + 幂等去重 + 分级确认」，幂等状态走 append-only journal

- 状态：Accepted
- 日期：2026-11-17
- 相关：`docs/产品定型.md` D3/D4/D20/D21/D22/D23/D26/D27、ADR-0005、`docs/缺口台账.md` B12

## 背景

对阀门的误动作是**物理后果**，不是数据错误。同时边缘节点没有事务性数据库，`kill -9` 与断电都很常见。

三个必须同时满足的约束：

1. 云端重发同一条服务调用（网络抖动、超时后用户重试）不能导致阀门动作两次。
2. 进程在「已受理、尚未执行」处崩溃，重启后不能重复执行。
3. Class A 设备离线期间不能无限重发把 ChirpStack 下行队列塞满（官方 FIFO 下发，队列满会丢帧）。

## 决策

1. **受理语义是「至多一次受理」**：`invoker` 收到一条服务调用，先做幂等判定；同一 `(device, seq)` 已存在则**不再下发**，按 journal 里的终态返回。首次受理才向下推进。
2. **幂等键是 `(device_sn, seq)`**，`seq` 为 **64 位**、按设备单调递增、由**云端**分配。边缘不做自增编号，只做窗口内去重。
3. **受理前先落 journal，执行后补终态**：两阶段写同一份 append-only journal。
   - `begin`：`{device, seq, service_id, ts, phase=accepted}`，`fsync` 后才调用驱动 `Write`。
   - `end`：`{device, seq, code, summary, phase=final}`。
   - 崩溃窗口落在「`begin` 已写、副作用未发生」或「副作用已发生、`end` 未写」两侧。**前者是安全的**（少执行）；后者导致终态未知 —— 重启后对该 `seq` 回 **`4004`（终态未知，请换新 `seq`）**，而不是猜测性重放。
4. **journal 为 append-only**，周期截断（保留最近 `idempotency_ttl`，默认 7 天）并在截断时重写压缩，同时物化每设备 `last_seq` 水位；`state.snapshot` 只存在线状态与快照，可由 journal + 观测重建。
5. **云端契约**（必须写进对接文档）：
   - 重试**必须换新 `seq`**；同 `seq` 只用于「同一条请求的重发」，且边缘不会重复执行。
   - 重试窗口必须 **小于幂等 TTL**（7 天），否则过期后同 `seq` 会被当成新请求再执行一次。
   - `seq` 需保证 64 位空间内单调递增、不回绕。
6. **分级确认**：`CmdAccepted → CmdDelivered → CmdCompleted`，或任意态 → `CmdFailed`。对应 LoRa 的 A 级（`txack`，网关已发射）/ B 级（`ack`，设备 MAC 确认，仅 `confirmed` 下行）/ C 级（业务 ACK）。只有 `CmdCompleted`（C 级）才回 `code=0`；到 A 或 B 级但未见业务确认 → `code=5041` 并在 `data.stage` 标明级别。
7. **重发策略按驱动能力分流**：
   - `Capabilities.SyncVerify=true`（Modbus）：**不重发**，改为「一次写入 + 写后回读验证」。因为厂商寄存器可能是「写即动作」，重发等于让阀门反复动作（台账 B12 未确认前必须保守）。
   - `SyncVerify=false` 且 `AsyncAck=true`（LoRa），且客户确认写语义幂等：允许重发，上限 3 次，每次间隔按**上报窗口数**计（D6），且受第 8 条（队列治理）约束。
8. **下行队列治理**（D22）：同设备同 `service_id` 的 pending 下行**始终合并、只保留最新**；每设备 pending 上限 4，超限淘汰最旧并记 `cmd_dropped(reason=queue_full)`。合并的实现用 `GetQueue` + 逐条精确撤销，**不用 `FlushQueue`**（竞态与最坏后果见 ADR-0005）。

## 后果

- 幂等表可重建：journal 是可重放的唯一真相；`state.snapshot` 丢失不导致重复动作。
- **终态已知才回放，未知则拒执行**：`4003`（回放终态）与 `4004`（终态未知，换新 `seq`）是两个不同语义，不能合并成一个码。
- **崩溃后可能「少执行」**：`begin` 已写而 `end` 未写时，重启后该 `seq` 不会被重放，而是回 `4004` 要求换新 `seq`。这是有意的取舍——宁可少动作，不可多动作。
- 写放大受控：每条受理两次小 append（`begin`/`end`）各一次 `fsync`，量级等于服务调用频率（不是采集频率），在网关上可接受。
- **「至多一次受理」不保证执行成功**，只保证不重复。执行成功靠分级确认与重发（仅 LoRa 且已确认写幂等的场景）。这是有意的取舍：宁可少动作，不可多动作。
- `seq` 窗口：云端保证 64 位空间内单调且不回绕。若边缘收到明显回退的 `seq`（远小于窗口下界），拒绝并回 `4001`，不做猜测性执行。

## 被否决的方案

- **纯内存幂等**：重启即失效，正是最危险的时刻。
- **先执行后落盘**：崩溃窗口落在「副作用已发生」，重启会重复动作。
- **全量 `state.json` 周期重写**：写放大高；损坏后无法恢复（评审 S6/S9）。
- **Modbus 也做「至少一次重发」**：在写入语义未确认前有物理风险。
- **不限队列的 LoRa 重发**：Class A 离线时队列塞满，设备上线先执行最旧指令。
- **引入嵌入式 KV（bbolt/sqlite）承载幂等表**：台账 E6 尚未确认客户是否允许。当前按「无数据库」硬约束设计 append-only journal。**若客户允许 KV，本 ADR 的决策 3/4 应重开评估**（事务性写会消除两阶段窗口，实现也大幅简化）。
