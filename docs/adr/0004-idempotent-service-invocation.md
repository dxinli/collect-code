# ADR-0004：服务调用用「至多一次受理 + 幂等去重 + 分级确认」，幂等状态走 append-only journal

- 状态：Accepted
- 日期：2026-11-17
- 相关：`docs/产品定型.md` D3/D4/D20/D21/D22/D23、`docs/缺口台账.md` B12

## 背景

对阀门的误动作是**物理后果**，不是数据错误。同时边缘节点没有事务性数据库，`kill -9` 与断电都很常见。

三个必须同时满足的约束：

1. 云端重发同一条服务调用（网络抖动、超时后用户重试）不能导致阀门动作两次。
2. 进程在「已受理、尚未执行」处崩溃，重启后不能重复执行。
3. Class A 设备离线期间不能无限重发把 ChirpStack 下行队列塞满（官方 FIFO 下发，队列满会丢帧）。

## 决策

1. **受理语义是「至多一次受理」**：`invoker` 收到一条服务调用，先做幂等判定；同一 `(device, seq)` 已存在则直接返回首次结果，**不再下发**。首次受理才向下推进。
2. **幂等键是 `(device_sn, seq)`**，`seq` 按设备单调递增、由**云端**分配。边缘不做自增编号，只做窗口内去重。
3. **受理前先落 journal**：`append({device, seq, service_id, ts})` 并 `fsync`，然后才调用驱动 `Write`。崩溃窗口因此落在「journal 已写、副作用未发生」一侧 —— 重启后只会「少执行」，不会「多执行」。
4. **journal 为 append-only**，周期截断（保留最近 `idempotency_ttl`，默认 7 天）并在截断时重写压缩；`state.snapshot` 只存在线状态与快照，可由 journal + 观测重建。
5. **分级确认**：`CmdAccepted → CmdDelivered → CmdCompleted`，或任意态 → `CmdFailed`。只有 `CmdCompleted` 才回 `code=0`；`CmdDelivered` 而未见业务确认 → `code=5041`。
6. **重发策略按驱动能力分流**：
   - `Capabilities.Verifiable=true`（Modbus）：**不重发**，改为「一次写入 + 写后回读验证」。因为厂商寄存器可能是「写即动作」，重发等于让阀门反复动作（台账 B12 未确认前必须保守）。
   - `Verifiable=false` 且客户确认写语义幂等（LoRa）：允许重发，上限 3 次，每次间隔按**上报窗口数**计（D6），且受第 7 条约束。
7. **下行队列治理**（D22）：每设备 pending 上限 4。超限时「同 `service_id` 合并、保留最新」，并淘汰最旧，发 `cmd_dropped`。LoRa 侧用 `GetQueue` / `FlushQueue` 与实际队列对账。

## 后果

- 幂等表可重建：journal 是可重放的唯一真相；`state.snapshot` 丢失不导致重复动作。
- 写放大受控：每条受理一次 `fsync`，量级等于服务调用频率（不是采集频率），在网关上可接受。
- **「至多一次受理」不保证执行成功**，只保证不重复。执行成功靠分级确认与重发（仅 LoRa 且已确认写幂等的场景）。这是有意的取舍：宁可少动作，不可多动作。
- `seq` 窗口：云端保证窗口内单调且不回绕。若边缘收到明显回退的 `seq`（远小于窗口下界），拒绝并回 `4001`，不做猜测性执行。

## 被否决的方案

- **纯内存幂等**：重启即失效，正是最危险的时刻。
- **先执行后落盘**：崩溃窗口落在「副作用已发生」，重启会重复动作。
- **全量 `state.json` 周期重写**：写放大高；损坏后无法恢复（评审 S6/S9）。
- **Modbus 也做「至少一次重发」**：在写入语义未确认前有物理风险。
- **不限队列的 LoRa 重发**：Class A 离线时队列塞满，设备上线先执行最旧指令。
