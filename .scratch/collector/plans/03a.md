## 1. 基线、前置与事实

### 1.1 已存在的接缝（只读确认）

- `Clock`（`internal/interfaces/clock.go`）：调度、deadline、日志时间的唯一入口。
- `Driver.Read(ctx, ReadRequest)`（`driver.go`）：`ReadRequest` 已有 `Device`、`Points`、`Deadline`；`Capabilities.Pollable` 用于跳过推送型链路（`REQ-CLI-01`）。
- `Sample`/`Outcome`/`Quality`（`types.go`）：超时时由调度器为配置点位生成 `QualityBad`；最终质量归 03b。
- `LinkStatus`（`types.go`）：04b 的驱动链路状态；03a 不实现状态机。
- `fakeclock`（`internal/testutil/fakeclock`）：支持 `Now/Advance/NewTicker/NewTimer/Sleep` 与 `FiredOrder`；**必须按周期分步 Advance**，一次 `Advance(24h)` 不会产生 1440 tick。
- `engine`（`internal/core/engine`）：目前只有生命周期；真实驱动尚不存在。
- `config`（`internal/config`）：`Link.ReadDeadlineMS`、`Timing.ReadDeadlineMS`、`Device.PollIntervalS`、`Profile.PollIntervalS` 是有效值来源。
- Store：03a 不 import、不调用。

### 1.2 FakeClock 的已知约束

`fakeclock` 的包注释明确：`Advance` 持有锁触发到期事件，组件在 tick 内注册的下一个 timer 会等到 `Advance` 返回；因此测试必须按周期逐步 `Advance` 并在每步等待组件完成。03a 的 24 小时测试必须写成 1440 次 `Advance(period)`，不能一次跳 24 小时。这是测试设计约束，不是 03a 的生产语义。

### 1.3 无实物前提

当前没有真实设备。03a 不引入任何硬件常量；`read_deadline`、采集周期都来自配置，默认值的来源见 `docs/缺口台账.md` G5（`read_deadline_ms`=300，ASSUMED）以及各 profile 的 `poll_interval_s`。测试中的 300 ms、60 s 等只是测试夹具，不是生产默认值。

### 5.2 公开类型与函数签名（设计稿）

```go
package scheduler

type Device struct {
    ID     string
    Period time.Duration // effective poll interval
    Points []string      // readable keys, used to synthesize bad samples on timeout
}

type Link struct {
    ID           string
    Driver       interfaces.Driver
    Devices      []Device
    ReadDeadline time.Duration
}

type Config struct { Links []Link }

type ReadResult struct {
    Link, Device        string
    Planned             time.Time
    Points              []string
    Samples             []interfaces.Sample
    Outcome             interfaces.Outcome
    TimedOut            bool
    StartedAt, FinishedAt time.Time
}

type TickInfo struct {
    Link      string
    Planned   time.Time
    Index     uint64 // (Planned - anchor) / TickPeriod, starting at 1
    Missed    uint64 // ticks skipped immediately before this one
    ReadCount int
    At        time.Time
}

// Observer must not block and must be safe for concurrent calls. It may be nil.
type Observer interface {
    ObserveRead(ReadResult)
    ObserveTick(TickInfo)
}

type LinkStats struct {
    ID           string
    Pollable     bool
    TickPeriod   time.Duration
    Devices      int
    Ticks        uint64
    MissedTicks  uint64
    Reads        uint64
    ReadTimeouts uint64
    ReadFailures uint64
    LastTickAt   time.Time
    LastError    string
}

func New(clock interfaces.Clock, log *slog.Logger, cfg Config, obs Observer) (*Scheduler, error)
func (s *Scheduler) Run(ctx context.Context) error
func (s *Scheduler) StartedAt() time.Time
func (s *Scheduler) Stats() []LinkStats
```

设计取舍：

- `Observer` 放在 `scheduler` 包，不放进 `internal/interfaces`。它不是外部协议缝隙，而是内核内部组件边界；`internal/core/*` 子包互相 import 是允许的（`check-deps.sh` 只禁止 core import 具体实现）。03b 的 state 组件 import `scheduler.ReadResult` 即可。
- `Observer` 允许 nil：03a 的纯调度测试与未来只做日志的运行不需要下游。nil 时不调用。
- `Stats` 使用切片而非 map，保持配置中的链路顺序，便于测试与 18 的稳定标签顺序。
- `Scheduler` 不持有 Store、不持有配置、不构造驱动。

### 5.3 相位、锚点与“不累积”

`New` 时记录 `anchor = clock.Now()`；`Run` 不重新取。若 `Run` 启动时已晚于 `anchor+period`，首个 tick 按 §5.4 记为迟到/跳过；生产在 `New` 后立即 `Run`。

链路 `L` 的第 `k` 个计划时刻恒为 `planned(k) = anchor + k*P`（`k=1,2,...`），首个 tick 在 `anchor+P`。这样：假时钟推进 24 h（60 s 周期）恰好 `k=1..1440`；相邻计划间隔恒为 `P`；每轮新建 `clock.NewTimer` 而非 `Ticker`，符合 `interfaces.Timer`“每个 deadline 新建 Timer”的约定。

每链路循环（伪代码）：

```go
next := anchor.Add(link.TickPeriod)
timer := clock.NewTimer(next.Sub(clock.Now()))
for {
    select {
    case <-ctx.Done(): timer.Stop(); return
    case <-timer.C():
    }
    now := clock.Now()
    runAt, missed := advance(now, next, link.TickPeriod)
    if missed > 0 { recordMissed(link, missed, next, now) } // Stats + 日志
    next = runAt.Add(link.TickPeriod)
    timer = clock.NewTimer(next.Sub(clock.Now())) // 先装下一 timer，再处理本 tick
    readCount := runDueDevices(ctx, link, runAt)
    if ctx.Err() != nil { timer.Stop(); return }
    recordTick(link, runAt, missed, readCount, clock.Now())
    if observer != nil { observer.ObserveTick(TickInfo{...}) }
}
```

要点：`runAt` 迟到严格小于 `P`；`next = runAt + P` 仍由锚点推出，不是 `now + P`，所以不累积。timer 在读取前就为下一 tick 注册，慢 tick 不会忘记下一计划时刻；若 `next.Sub(now) <= 0`，`NewTimer` 立即到期，下一轮按 missed 处理。`runDueDevices` 串行处理到期设备，ctx 取消即返回。

### 5.4 missed tick 判定

```go
func advance(now, planned time.Time, period time.Duration) (runAt time.Time, missed uint64) {
    if now.Before(planned.Add(period)) { return planned, 0 }
    delta := now.Sub(planned) // >= period
    missed = uint64(delta / period)
    return planned.Add(time.Duration(missed) * period), missed
}
```

| `now - planned` | `missed` | 本轮 `runAt` |
|---|---|---|
| `P - 1ns` | 0 | `planned`（迟到不足一周期，照常运行） |
| `P` | 1 | `planned + P`（原 tick 跳过） |
| `P + 1ns` | 1 | `planned + P`（迟到 1ns） |
| `2P + 1ns` | 2 | `planned + 2P`（跳过两个旧 tick） |
| `2.5P` | 2 | `planned + 2P`（只运行最新 tick，不补跑） |

“迟到一个周期以上”含等号：`now >= planned + P` 即 missed；一次唤醒只运行最新一个 tick，中间旧 tick 全部计入 missed，不补跑。`MissedTicks` 累加，日志记录本次 `skipped` 与累计 `missed_total`。一次 missed 一条日志：`msg="missed tick"`、`event=missed_tick`、`link`、`skipped`、`planned`（被跳过的第一个计划时刻）、`now`、`missed_total`。

### 5.5 设备周期、链路 tick 与到期选择

链路 tick `P_link = gcd(所有设备有效周期)`；有效周期由装配层按 §5.11 计算（device 覆盖 profile）。`P_link < 1s` 时 `New` 报错（`REQ-SCHED-04`）；pollable 链路无设备也报错；非 pollable 链路不算 tick、不校验周期、不启动 goroutine。

到期判定：`elapsed = planned - anchor`，`elapsed % device.Period == 0` 时设备到期。因为 `P_link` 整除每个设备周期，`elapsed = k*P_link`。例子：

| 设备周期 | 链路 tick | 执行 tick |
|---|---|---|
| 60 s | 60 s | 每 60 s |
| 60 s + 90 s | 30 s | 30 s 只跑 90 s 设备；60 s 跑 60 s 设备；90 s 只跑 90 s 设备；180 s 两者都跑 |
| 5 s + 60 s | 5 s | 每 5 s 跑 5 s 设备；每 60 s 两者都跑 |
| 7 s + 11 s | 1 s | 每 1 s 跑其中一个或两个（按整除） |

每个 tick 只遍历到期设备；未到期设备不产生 `Read`、不计入 `Reads`。单 tick 最坏耗时 = 到期设备数 × `ReadDeadline`；链路内串行，不会并发 `Read`。

### 5.6 单设备 read deadline

**目标**：驱动即使不返回，调度器也不能被拖死；到期后该设备全部配置点位标 `bad`，立即处理下一台。

**传递方式**：

1. 读取开始前取 `started := clock.Now()`，计算 `deadline := started.Add(link.ReadDeadline)`。
2. 调用 `driver.Read(readCtx, interfaces.ReadRequest{Device, Points, Deadline: deadline})`。`ReadRequest.Deadline` 是给驱动的业务截止时间，驱动应据此中止 I/O；它不是 `context.WithTimeout`。
3. 调度器同时用 `clock.NewTimer(link.ReadDeadline)` 做**硬上限**。这是调度器自己的兜底，不依赖驱动是否老实遵守 deadline。
4. `readCtx` 用 `context.WithCancel(ctx)` 派生，只用于取消传播；到期或 tick 取消时调用 `cancel()`，让守规矩的驱动尽快退出。
5. `Read` 在独立 goroutine 中执行，结果写入容量为 1 的 channel；即使调度器已放弃等待，goroutine 也能完成发送并退出。调度器**不等待**被放弃的 goroutine，否则 deadline 就失效了。

伪代码：

```go
started := clock.Now()
deadline := started.Add(lk.ReadDeadline)
readCtx, cancel := context.WithCancel(ctx) // 不是 WithTimeout
defer cancel()
timer := clock.NewTimer(lk.ReadDeadline)
defer timer.Stop()
done := make(chan readOutcome, 1) // 容量 1：被放弃的读不会阻塞发送
go func() {
    samples, outcome := lk.Driver.Read(readCtx, interfaces.ReadRequest{
        Device: dev.ID, Points: points, Deadline: deadline,
    })
    done <- readOutcome{samples: samples, outcome: outcome, at: clock.Now()}
}()

select {
case <-ctx.Done():
    return ReadResult{}, false
case r := <-done:
    return resultFrom(r), true
case <-timer.C():
    select { case r := <-done: return resultFrom(r), true; default: }
    // 为每个配置点位生成 QualityBad 样本；OutcomeFailed/TimedOut=true。
    return timeoutResult(points), true
}
```

规则：deadline 是硬上限，timer 触发时结果未就绪即超时；同时就绪的竞争用“timer 触发后非阻塞检查一次 done”消除。超时样本 `QualityBad`、`At` 取同一注入时钟、`Err="read deadline exceeded"`，顺序同 `Device.Points`；`Outcome=OutcomeFailed`、`TimedOut=true`，不重试、不等待、不把剩余点位留到下一 tick。被放弃的 goroutine 之后返回只写容量 1 的 channel，结果丢弃。驱动必须遵守 `ReadRequest.Deadline` 与 `ctx.Done()`；调度器兜底只保证自己不被拖死，Go 无法强制终止驱动 goroutine。不得用 `context.WithTimeout/WithDeadline`。

`runDueDevices` 按配置顺序逐个调用 `readDevice`，前一台返回或超时后才开始下一台；测试用并发计数断言同链路最大并发为 1。

### 5.7 并发、取消与生命周期

- `Run(ctx)` 为每个 pollable 链路启动一个 goroutine，`sync.WaitGroup` 等待全部退出；非 pollable 链路不启动。每条链路一个 goroutine 串行处理设备，不同链路并发，慢链路不阻塞其他链路（`REQ-SCHED-03`）。
- `ctx.Done()` 后等待链路 goroutine 返回并返回 `nil`；`Run` 只能调用一次，第二次返回 `scheduler: already run`。
- 调度器不调用 `Driver.Open/Close`，不消费 `Driver.Events()`；每条链路有自己的驱动，装配层不得跨链路共享同一实例。
- `Observer` 同步调用，可能跨链路并发，必须非阻塞且并发安全。`Stats()` 在锁下复制快照；更新计数时不调用 observer，避免回调死锁。
- 取消时 `readDevice` 返回 `ok=false`、不产生结果，`cancel()` 传播给驱动；测试必须释放阻塞 handler，避免泄漏。

### 5.8 可观测字段与日志

`LinkStats` 字段：`ID`、`Pollable`、`TickPeriod`（非 pollable 为 0）、`Devices`（以上 `New` 时确定）；`Ticks`（实际运行，含迟到、不含跳过）、`MissedTicks`（累计跳过）、`Reads`（含超时）、`ReadTimeouts`、`ReadFailures`（非超时 `OutcomeFailed`）、`LastTickAt`、`LastError`（成功读取后清空）。

- 超时单独计入 `ReadTimeouts`，不重复计入 `ReadFailures`；两者都计入 `Reads`；`OutcomePartial` 不计入失败。
- `ReadFailures` 是调度器读取计数，用于 `REQ-SCHED-03` 可观测性；`LinkStatus` 状态机归 04b。
- 计数器不持久化；重启/热重载后归零。
- 日志字段：missed tick 为 `event=missed_tick`、`link`、`skipped`、`planned`、`now`、`missed_total`；deadline 为 `event=read_deadline`、`link`、`device`、`reason=deadline_exceeded`、`deadline`。时间取 `clock.Now()`，格式化 `UTC().Format(time.RFC3339Nano)`。使用 `internal/logging` 的 `KeyLink/KeyDevice/KeyReason`，不发明别名（`REQ-OPS-03`）。

### 5.9 与 engine / app 的装配关系

**推荐方案（§10 决策 1-A）**：03a 不修改 `engine`/`app` 的运行逻辑，调度器作为独立的并列内核组件存在，公开 `Run(ctx)`。

理由：当前没有真实驱动可装配，把假驱动放进 `app.run` 会污染生产路径；为一个没有真实消费者的组件提前冻结组件注册/错误汇聚 API 也不合适；03a 验收可在 `scheduler` 包内用 FakeClock + fake driver 完成。真正的装配点是 04b（Modbus 驱动可用）或 07（端到端）。若保持 `engine` 不动，把 `engine.go` 顶部注释“the scheduler attaches inside Run in 03a”改为“the scheduler is a peer component wired when drivers exist”。

**备选方案（§10 决策 1-B）**：在 `engine` 增加 `Component`/`Attach` 监管器；代价是新增生命周期 API 与组件错误/关闭策略，超出 ticket 范围。

### 5.10 为什么不修改 `internal/interfaces`

现有接缝已覆盖全部需求：`Clock.Now/NewTimer`（时间/timer）、`Capabilities().Pollable`（是否轮询）、`Read(ctx, ReadRequest{Device, Points, Deadline})`（按设备读点位）、`Sample.Quality/Err/At`（超时初值）、`Driver.Status()/LinkStatus`（04b 链路状态）。

不需要新增方法或字段：`ReadRequest.Deadline` 已存在，不需要 `context.WithTimeout`；`ctx` 取消就是取消传播，不需要“取消读”句柄；`Observer`/`ReadResult` 是内核组件数据，不是外部缝隙，03b 可 import `internal/core/scheduler`；完成时间由调度器在 goroutine 返回时用注入时钟取，不需要驱动返回。

因此本计划**默认不修改** `internal/interfaces` 的任何签名。如果独立评审认为必须修改（例如要求驱动返回可中断句柄），按 `AGENTS.md` 停止实现，另列 A/B 交用户拍板，不得在 03a 默认改接口。

### 5.11 配置映射契约（供 04b/07 装配；03a 只消费 `Config`）

03a 推荐**不** import `internal/config`（§10 决策 2-A）。装配层负责把四层配置转换成 `scheduler.Config`，规则如下（写入本计划作为后续 ticket 的契约）：

| 项 | 规则 | 缺失时 |
|---|---|---|
| 设备有效采集周期 | `device.poll_interval_s` 非空则用它；否则 `profile.poll_interval_s` | 两者都空：装配层报错，不发明默认值（§10 决策 4-A） |
| 链路 tick | 该链路所有设备有效周期的 GCD；`New` 再次校验 ≥1 s | pollable 链路无设备：`New` 报错 |
| 链路读截止 | `link.read_deadline_ms` 非空则用它；否则 `timing.read_deadline_ms` | 必须 >0；否则 `New` 报错 |
| 设备点位 | 该 pollable 驱动可读点位的 key 列表；Modbus 具体集合由 04b 按 profile 决定 | 空点位列表：`New` 报错（超时无法标 bad） |
| 链路驱动 | 每个链路一个 `interfaces.Driver` 实例 | nil：`New` 报错 |
| 推送型链路 | `Capabilities().Pollable == false`：不调度，不读，不要求周期/点位 | 仍要求 driver 非 nil |
| 设备顺序 | 配置中的设备顺序 | — |
| 周期修改 | 只能通过重建调度器（17 热重载）生效 | — |

`read_deadline_ms` 的默认值 300 ms 是 `docs/缺口台账.md` G5 的 ASSUMED 值，存在于配置默认值中；调度器自身不得写死 300 ms 或任何其他硬件数值。测试中的 300 ms 是测试夹具，不是生产默认值。上报周期（`timing.snapshot_interval_s`）属于节点，03a 不读取、不复用为采集周期；两者保持解耦（`REQ-SCHED-04`）。

### 6.3 24 小时快进的写法

不使用 `clock.Advance(24*time.Hour)`，而是：

```go
for i := 1; i <= 1440; i++ {
    clock.Advance(60 * time.Second)
    info := waitTick(t, tickCh) // ObserveTick 的带缓冲 channel
    if want := start.Add(time.Duration(i) * 60 * time.Second); !info.Planned.Equal(want) {
        t.Fatalf("tick %d planned = %s, want %s", i, info.Planned, want)
    }
}
```

- `waitTick` 用 `select` + `time.After(2*time.Second)` 做失败保护；这是测试真实时间保护，不是调度逻辑，也不使用 `time.Sleep`。
- `ObserveTick` 在 timer 已注册、tick 已处理、Stats 已更新之后调用，测试收到它就可以安全地推进下一次。
- 24 h 测试的驱动立即返回，不产生 deadline timer 触发；`clock.FiredOrder()` 只应包含计划 tick 的 timer。
- 最后取消 Run，等待 goroutine 退出，再 `clock.Close()`。

### 6.4 边界与失败场景

period±1ns 用 `advance` 表驱动；deadline 边界先 `Advance(D-1ns)` 断言无结果、再 `Advance(1ns)` 断言超时；missed tick 用真实循环制造“处理超过一个周期”；设备串行用并发计数与调用顺序；取消、链路隔离、推送型不读、`-race` 分别由 `TestCancelStopsScheduler`、`TestLinksRunIndependently`、`TestPushLinkIsNotPolled`、`TestObserverConcurrentLinks` 覆盖。

### 6.5 测试自身不使用 `time.Sleep`

- 调度逻辑完全不使用 `time.Sleep`；`make time-check` 是静态门禁。
- 测试用 channel/`ObserveTick`/`Started()` 同步；`time.After` 只作为失败保护（2 s 上限），不用于推进调度。
- 24 h 测试的 1440 次推进由 fakeclock 驱动，不消耗真实 24 小时。

| 风险/未知 | 缓解 |

| FakeClock 一次 `Advance(24h)` 不产生 1440 tick | 按包注释分步 Advance，每步等 `ObserveTick`；`TestRunPhaseLocked24Hours` 明确 1440 次 |

## 10. 需要用户拍板的 A/B

### 决策 1：engine/app 装配

- **A（推荐）**：调度器作为独立组件公开 `Run(ctx)`；`engine`/`app` 运行逻辑不动，只改 `engine` 的错误注释；真实装配推迟到 04b/07。影响：diff 小、假驱动不进生产；调度器暂不进入二进制。
- **B**：在 `engine` 增加 `Component`/`Attach` 监管器，03a 用 stub 测试 attach；`app` 仍无真实驱动。影响：新增生命周期 API 与组件错误/关闭策略，超出 03a 验收。

**推荐 A。**

### 决策 2：是否在 03a 做配置→计划映射

- **A（推荐）**：`scheduler.Config` 由调用方显式构造；03a 不 import `internal/config`；映射规则写入 §5.11，由 04b/07 实现。影响：不提前决定 profile 点位到驱动可读集合的映射；映射集成测试晚一个 ticket。
- **B**：新增 `scheduler.PlanFromConfig(bundle)`，import `internal/config` 并测试四层转换。影响：现在就要决定 Modbus/payload 点位口径与缺失周期策略，可能与 04b 的驱动语义冲突。

**推荐 A。**

### 决策 3：deadline 超时的 bad 点位由谁生成

- **A（推荐）**：调度器按 `Device.Points` 生成 `QualityBad` 样本，`ReadResult.TimedOut=true`；03b 只消费、不升级 `bad`。影响：03a 验收自包含；装配层必须提供点位 key；`REQ-SCHED-02`“全点 bad”由调度器兑现。
- **B**：调度器只报告 `TimedOut` 与点位 key，由 03b 生成 bad。影响：03a 无法完整断言“点位标 bad”，该验收被部分转移到 03b。

**推荐 A。**

### 决策 4：有效采集周期缺失时怎么办

- **A（推荐）**：`New` 返回错误，装配层启动失败。影响：严格遵循 `REQ-SCHED-04`“周期属于设备，profile 提供默认值”；可能暴露 01b 未强制“周期必须存在”的缺口（后续 config ticket 可补）。
- **B**：回退到 `timing.snapshot_interval_s` 或代码常量。影响：引入未经规范授权的语义和 ASSUMED 常量，并使上报周期与采集周期耦合。

**推荐 A。**

### 决策 5：首个 tick 是否立即执行

- **A（推荐）**：首个 tick 在 `anchor + period`；24 h 恰好 1440 tick。影响：启动后等一个周期才首次采集；与 `docs/testing.md` 的 1440 判据一致。
- **B**：`anchor` 立即执行一次，再按周期调度。影响：24 h 内共 1441 次读取，需要额外区分“立即 tick”与“计划 tick”；启动瞬间可能有总线突发。

**推荐 A。**

### 决策 6：Observer/ReadResult 放在哪个包

- **A（推荐）**：放在 `internal/core/scheduler`；03b 的 state import 它，`internal/interfaces` 不变。影响：形成 `core/state -> core/scheduler` 依赖（check-deps 允许 core 子包互引）；外部缝隙保持纯净。
- **B**：加入 `internal/interfaces`。影响：冻结的外部接口包引入内核内部数据模型，需修改 02a 冻结面并解释规范/合同。

**推荐 A。**

### 决策 7：链路失败计数与 LinkStatus 的归属

- **A（推荐）**：03a 只暴露调度器读取计数（`ReadTimeouts/ReadFailures`）；`LinkStatus` 状态机由 04b 负责，18 组合两者。影响：不重复状态机；`REQ-SCHED-03` 的“可观测”由 `Stats` 覆盖，“链路状态”由 04b 覆盖。
- **B**：03a 在调度器内维护 `LinkState`（up/degraded/down）。影响：与 04b 的 `Driver.Status()` 重复，可能出现两套不一致状态，且需要采样/恢复阈值。

**推荐 A。**
