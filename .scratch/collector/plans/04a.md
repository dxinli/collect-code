## 2. 硬约束的落地方式

### 2.1 时间只能从注入 `Clock` 进入

- 非 `_test.go` 的 `internal/drivers/**` 禁止出现 `time.Now/Since/Until/NewTicker/NewTimer/Tick/After/AfterFunc/Sleep` 与 `context.WithTimeout/WithDeadline`；`make time-check` 机械执行。
- 生产代码只使用 `time.Time`、`time.Duration`、`time.Time{}`（零值）等类型；截止时间由 `Client` 持有的 `interfaces.Clock.Now()` 推导。
- **context 只用于取消传播**：`Client.Do` 在入口检查 `ctx.Err()`，并用 `context.AfterFunc(ctx, ...)` 在取消时把 `Conn` 的 deadline 设为 `clock.Now()`（立即到期）以解除阻塞读；绝不用 `context.WithTimeout/WithDeadline` 做业务超时。
- 真实网络/串口 I/O 的截止由 `Conn.SetDeadline` 承担；ADR-0003 已说明“真实网络 I/O 的超时由底层库控制，测试用内存对端”。假时钟测试用脚本化 `Conn` 断言 deadline 的推导，而不是靠真实 `net.Conn` 的墙钟。
- `Client.New` 拒绝 nil `Clock`；测试覆盖。

### 2.2 依赖方向

- `scripts/check-deps.sh` 对 `internal/drivers` 的传递闭包禁止 `internal/core`、`internal/channels`、`internal/adapters`、`internal/store`、`internal/testutil`、`internal/clock/realclock`、`internal/sim`、bbolt。

### 3.2 PDU 导出面

`pdu` 是纯函数包：不读 I/O、不看时间、不 import `interfaces`。所有多字节整数使用 **大端**（Modbus 标准），16 位寄存器元素保持 `uint16`；32 位/浮点解码是 04b 的职责，PDU 不解释寄存器组合。

```go
package pdu

type FuncCode uint8

const (
    FuncReadHoldingRegisters   FuncCode = 0x03
    FuncReadInputRegisters     FuncCode = 0x04
    FuncWriteSingleRegister    FuncCode = 0x06
    FuncWriteMultipleRegisters FuncCode = 0x10
)

const (
    MaxReadRegisters   = 125 // 0x7D
    MaxWriteRegisters  = 123 // 0x7B
    MaxPDUSize         = 253
    ExceptionFlag      = 0x80
)

type ExceptionCode uint8

const (
    ExceptionIllegalFunction       ExceptionCode = 0x01
    ExceptionIllegalDataAddress    ExceptionCode = 0x02
    ExceptionIllegalDataValue      ExceptionCode = 0x03
    ExceptionServerDeviceFailure   ExceptionCode = 0x04
    ExceptionAcknowledge           ExceptionCode = 0x05
    ExceptionServerDeviceBusy      ExceptionCode = 0x06
    ExceptionMemoryParity          ExceptionCode = 0x08
    ExceptionGatewayPathUnavailable ExceptionCode = 0x0A
    ExceptionGatewayTargetFailed   ExceptionCode = 0x0B
)

type ExceptionClass uint8

const (
    ExceptionClassRejected ExceptionClass = iota // 参数非法/设备拒绝
    ExceptionClassInternal                       // 设备内部错误
)

func (c ExceptionCode) String() string
func (c ExceptionCode) Class() ExceptionClass

type Request interface {
    Function() FuncCode
    encode() ([]byte, error) // sealed: 仅包内实现
}

type Response interface {
    Function() FuncCode
    encode() ([]byte, error) // sealed
}

type ReadRegistersRequest struct {
    Func     FuncCode // 03 或 04
    Address  uint16
    Quantity uint16
}

type ReadRegistersResponse struct {
    Func      FuncCode // 03 或 04
    Registers []uint16
}

type WriteSingleRegisterRequest struct {
    Address uint16
    Value   uint16
}

type WriteSingleRegisterResponse struct {
    Address uint16
    Value   uint16
}

type WriteMultipleRegistersRequest struct {
    Address uint16
    Values  []uint16 // Quantity 由 len(Values) 派生
}

type WriteMultipleRegistersResponse struct {
    Address  uint16
    Quantity uint16
}

type ExceptionResponse struct {
    Func FuncCode        // 原始功能码（不含 0x80）
    Code ExceptionCode
}

func (e *ExceptionResponse) Error() string

func EncodeRequest(req Request) ([]byte, error)
func DecodeRequest(raw []byte) (Request, error)
func EncodeResponse(resp Response) ([]byte, error)
func DecodeResponse(raw []byte) (Response, error)
func ValidateResponse(req Request, resp Response) error
```

**编码/解码规则**：

| 功能码 | 请求 PDU | 响应 PDU | 校验 |
|---|---|---|---|
| 03 / 04 | func, addr(2), qty(2) | func, byteCount(1), data(2×qty) | byteCount == 2×qty；总长 ≤ 253 |
| 06 | func, addr(2), value(2) | func, addr(2), value(2) | 回显 addr/value 必须等于请求 |
| 16 | func, addr(2), qty(2), byteCount(1), data(2×qty) | func, addr(2), qty(2) | byteCount == 2×qty；回显 addr/qty 必须等于请求 |
| 异常 | — | func\|0x80, code(1) | func 必须等于请求功能码；code 任意 |

**边界**：

| 项 | 规则 |
|---|---|
| 读数量 | 1..125（0x7D）；0、126 及以上 → `ErrInvalidQuantity` |
| 写多数量 | 1..123（0x7B）；0、124 及以上 → `ErrInvalidQuantity` |
| 写单 | 恰好 1 个 uint16，0..65535 全部合法 |
| 地址 | `uint16`；`address + quantity - 1` 不得溢出 0xFFFF，否则 `ErrInvalidAddress` |
| PDU 长度 | 1..253；超长或空 → `ErrMalformed` |
| 功能码 | 仅 03/04/06/16；其他 → `ErrUnsupportedFunction`（异常响应的 0x80 位单独处理） |
| 单位 | PDU 不携带 unit id；unit 属于 ADU/framing |

**异常分类**（`ExceptionCode.Class()`）：

| 异常码 | 含义 | Class | 04b/09 关系 |
|---|---|---|---|
| 01 | 非法功能 | Rejected | 4001 |
| 02 | 非法数据地址 | Rejected | 4001 |
| 03 | 非法数据值 | Rejected | 4001 |
| 04 | 从站设备故障 | Internal | 5044 |
| 05 | 确认（长操作） | Internal | 5044（同步引擎无法等待长操作） |
| 06 | 从站设备忙 | Internal | 5044 |
| 08 | 存储奇偶错 | Internal | 5044 |
| 0A | 网关路径不可用 | Internal | 5044 |
| 0B | 网关目标设备无响应 | Internal | 5044 |
| 未知 | — | Internal | 5044，保留原始码 |

> 05/06/08/0A/0B/未知的分类是规范未逐条列出的边界，需用户确认（§4.7）。无论 Rejected/Internal，读路径都只落到 `Partial`+对应点 `bad`（04b）；写路径才映射到 4001/5044（09）。

### 3.3 CRC16

- 算法：CRC-16/MODBUS，反射多项式 `0xA001`（即 `0x8005` 反射），初值 `0xFFFF`，无最终异或；对“unit + PDU”逐字节计算。
- 线上字节序：**低字节在前**（`crc & 0xFF`, `crc >> 8`）。
- 参考实现放在 `framing/crc16.go`，导出 `func CRC16(data []byte) uint16`；`pdu` 不依赖 CRC。
- 校验向量（测试固定；已用独立位级实现计算）：

| 输入（hex） | CRC 值 | 线上字节 |
|---|---|---|
| `31 32 33 34 35 36 37 38 39`（"123456789"） | `0x4B37` | `37 4B` |
| `01 03 00 00 00 02` | `0x0BC4` | `C4 0B` |
| `01 03 00 00 00 0A` | `0xCDC5` | `C5 CD` |
| `01 04 00 00 00 01` | `0xCA31` | `31 CA` |
| `01 06 00 02 00 32` | `0xDFA9` | `A9 DF` |
| `01 10 00 02 00 02 04 00 32 00 64` | `0x52D2` | `D2 52` |
| `01 03 04 00 32 00 64` | `0x175A` | `5A 17` |
| `01 04 02 FF FF` | `0x80B8` | `B8 80` |
| `01 10 00 02 00 02` | `0x08E0` | `E0 08` |
| `01 83 02` | `0xF1C0` | `C0 F1` |

### 3.4 Framing：MBAP、RTU、RTU-over-TCP

```go
package framing

type Frame struct {
    TransactionID uint16 // 仅 MBAP 使用；RTU 为 0
    UnitID        uint8
    PDU           []byte
}

type Framer interface {
    Name() string
    Encode(f Frame) ([]byte, error)
    DecodeRequest(r io.Reader) (Frame, error)
    DecodeResponse(r io.Reader, req pdu.Request, expectTxn uint16) (Frame, error)
}

func NewMBAP() Framer
func NewRTU() Framer
```

#### MBAP（Modbus TCP）

```text
+----------+----------+----------+----------+----------+
| txn id 2 | proto 2  | len 2    | unit 1   | PDU ...  |
+----------+----------+----------+----------+----------+
```

- `proto` 必须为 `0x0000`。
- `len` = unit(1) + PDU 长度，范围 2..254；ADU 总长 8..260（6 字节头 + len；最小合法帧为 unit+func，即 len=2）。
- `DecodeRequest` 读满 7 字节（含 unit）后读 `len-1` 字节 PDU；`DecodeResponse` 额外校验 `TransactionID == expectTxn`。
- 分片：所有读取用 `io.ReadFull` 精确读，天然支持“一次 Read 只来 1 字节”。
- 粘包：每次只消费一帧的精确长度，剩余字节留在底层流中，下一次 `Decode*` 读取下一帧；测试用 `bytes.Buffer` 放两帧验证。
- 校验失败：proto 非 0、len 越界、帧被截断、事务号不匹配 → `ErrMalformedFrame`/`ErrShortFrame`/`ErrTransactionMismatch`（全部 `errors.Is(err, pdu.ErrProtocol)`）。

#### RTU（串口与 RTU-over-TCP）

```text
+----------+----------+----------+----------+----------+
| unit 1   | PDU ...  | CRC low  | CRC high |          |
+----------+----------+----------+----------+----------+
```

- ADU 总长 4..256；CRC 对 unit+PDU 计算，线上低字节在前。
- **请求解码**（供测试从站）按功能码推断长度：
  - 03/04/06：固定 8 字节（unit+func+addr2+qty/value2+CRC2）。
  - 16：先读 unit+func+addr2+qty2+byteCount1，再读 `2×byteCount` 数据 + CRC2；校验 `byteCount == 2×qty`。
  - 未知功能码：读满 unit+func 后返回 `ErrUnsupportedFunction`；测试从站可据此回异常 01（此时剩余字节不由本帧消费）。
- **响应解码**（供客户端）使用 `req` 推断长度：
  - `func|0x80`：固定 5 字节（unit+func+code+CRC2）。
  - 03/04：读 unit+func+byteCount，再读 `byteCount` 数据 + CRC2；校验 `byteCount == 2×req.Quantity`。
  - 06/16：固定 8 字节。
- 任何长度不足、CRC 错误、功能码与请求不匹配、字节数不匹配 → `ErrShortFrame`/`ErrBadCRC`/`ErrMalformedFrame`，均归为协议错误。
- RTU 无事务号；请求/响应只能靠严格串行（`Client` 互斥）与功能码/长度匹配。

#### RTU-over-TCP

- 不新增 framing：同一 RTU ADU 直接跑在 TCP 流上，**没有** MBAP，CRC 不变。
- 连接建立用 `DialTCP`；`Client` 注入 `framing.NewRTU()`。
- 不实现额外帧间静默/3.5 字符间隔；理由与 ASSUMED 见 §3.8、§9.3。

**三种传输如何切换**：`NewClient(conn, framer, clock)` 的 `framer` 参数是唯一开关；`NewTCPClient`/`NewRTUOverTCPClient` 只是“拨号 + 选择 framer”的便捷函数；串口 RTU 由调用方提供 `Conn` 后 `NewRTUClient`。PDU 编解码完全不感知 framing。

### 3.5 传输抽象与注入形状

```go
package modbus

type Conn interface {
    io.ReadWriteCloser
    SetDeadline(t time.Time) error
}
```

- `net.Conn` 直接满足；`net.Pipe` 返回的 `net.Conn` 也满足；未来串口 opener 只需返回满足此接口的对象。
- 选择 `SetDeadline` 而不是 `io.ReadWriter`：截止时间是驱动层的硬需求，且 `net.Conn`/串口实现天然支持；避免在驱动里另造计时 goroutine。
- 注入点：
  - `NewClient(conn Conn, framer framing.Framer, clock interfaces.Clock) (*Client, error)`：最底层，04b 与测试使用。
  - `DialTCP(ctx, addr string) (Conn, error)`：生产 TCP；错误包装 `interfaces.ErrLinkDown`。
  - `NewTCPClient(ctx, addr, clock)` / `NewRTUOverTCPClient(ctx, addr, clock)`：便捷构造，内部 `DialTCP` + `NewClient`。
  - `NewRTUClient(conn Conn, clock)`：串口或任意注入流。
- `DialTCP` 只用 `ctx` 做取消传播，不设置 `net.Dialer.Timeout`/`Deadline`；连接尝试的超时与重试归 04b/装配层用注入 `Clock` 管理（04a 不把运行时计时器引入驱动）。
- 04b 复用方式：一个链路/设备一个 `Client`（由 04b 决定），`Client` 内部串行化；04b 负责 profile → PDU 的映射与错误 → Outcome 的映射。
- 06a 复用方式：06a 是服务端，使用自己的 listener/conn 与独立 server 实现；**不复用** `Client`，也不把 `modbustest` 当生产从站。

### 3.6 Client 交换、超时与取消

```go
type Client struct { /* conn, framer, clock, mu, nextTxn, closed */ }

func NewClient(conn Conn, f framing.Framer, clock interfaces.Clock) (*Client, error)

func (c *Client) ReadHoldingRegisters(ctx context.Context, unitID uint8,
    address, quantity uint16, timeout time.Duration) ([]uint16, error)
func (c *Client) ReadInputRegisters(ctx context.Context, unitID uint8,
    address, quantity uint16, timeout time.Duration) ([]uint16, error)
func (c *Client) WriteSingleRegister(ctx context.Context, unitID uint8,
    address, value uint16, timeout time.Duration) error
func (c *Client) WriteMultipleRegisters(ctx context.Context, unitID uint8,
    address uint16, values []uint16, timeout time.Duration) error
func (c *Client) Do(ctx context.Context, unitID uint8,
    req pdu.Request, timeout time.Duration) (pdu.Response, error)
func (c *Client) Close() error
```

**交换流程**（`Do`）：

1. 持锁（同一 `Client` 同时只允许一个在途交换；对 MBAP 保证事务号与响应匹配，对 RTU 保证没有并发帧）。
2. 检查 `closed`、nil req、unit 0（广播地址，见 §4.11）、PDU 参数。
3. `timeout > 0` 时：`deadline := c.clock.Now().Add(timeout)`，调用 `conn.SetDeadline(deadline)`；`timeout <= 0` 表示无截止（保留接口 `Deadline` 零值语义）。
4. 用 `context.AfterFunc(ctx, func(){ _ = conn.SetDeadline(c.clock.Now()) })` 注册取消传播；交换结束后 `stop()`，若返回 false（回调已启动）则等待回调完成，再清空 deadline（`time.Time{}`），避免“清空后回调又设了过期 deadline”的竞态。
5. 编码 PDU → `framing.Frame{TransactionID: nextTxn, UnitID: unitID, PDU: raw}` → `framer.Encode` → 写满 `Conn`。
6. `framer.DecodeResponse(conn, req, txn)` 读取一帧；校验响应 `UnitID == unitID`。
7. `pdu.DecodeResponse(frame.PDU)`；`pdu.ValidateResponse(req, resp)`。
8. 若响应是 `*pdu.ExceptionResponse`，转换为 `*ExceptionError` 返回；否则返回正常响应。
9. 交换结束后解除取消钩子并清空 deadline；返回错误。

**事务号**：`nextTxn` 从 1 开始，每次 `Do` 递增（0xFFFF 后回绕到 1）；RTU 不使用但同样递增，测试可断言不影响 framing。

**超时**：

- 业务截止只来自 `clock.Now() + timeout`，再交给 `Conn.SetDeadline`；不使用 `context.WithTimeout/WithDeadline`。
- 读阻塞在 deadline 上由底层返回 `os.ErrDeadlineExceeded`/`net.Error.Timeout()`；映射为 `interfaces.ErrDeviceNoResponse`（5044）。
- 写失败、连接被关闭、读之前的 EOF → `interfaces.ErrLinkDown`（5040）。
- 读到一半的 EOF/短读 → 协议错误 `framing.ErrShortFrame`（5044 语义）。
- `ctx` 取消 → 返回 `fmt.Errorf("modbus: exchange canceled: %w", ctx.Err())`，不伪装成设备无响应。

**为什么用 `context.AfterFunc` 而不是自建 goroutine**：它是标准库的取消钩子，不引入业务计时器；回调只做一次 `SetDeadline`，无共享可变状态（`Conn` 的 deadline 操作本身是并发安全的）。测试用 `-race` 与 goroutine 退出断言覆盖。

### 3.7 错误分类与 REQ-INVOKE-05 的关系

**分层原则**：`pdu`/`framing` 只报“协议/帧”错误；根包 `modbus` 做 I/O 与接口哨兵映射；04b 决定读路径的 Outcome；09 决定写路径的最终 code。

```go
// pdu/errors.go
var (
    ErrProtocol            = errors.New("modbus: protocol error")
    ErrMalformed           = fmt.Errorf("modbus: malformed PDU: %w", ErrProtocol)
    ErrUnsupportedFunction = fmt.Errorf("modbus: unsupported function: %w", ErrProtocol)
    ErrArgument            = errors.New("modbus: invalid argument")
    ErrInvalidQuantity     = fmt.Errorf("modbus: invalid quantity: %w", ErrArgument)
    ErrInvalidAddress      = fmt.Errorf("modbus: invalid address range: %w", ErrArgument)
)

// framing/errors.go
var (
    ErrBadCRC             = fmt.Errorf("modbus: bad CRC: %w", pdu.ErrProtocol)
    ErrShortFrame         = fmt.Errorf("modbus: short frame: %w", pdu.ErrProtocol)
    ErrFrameTooLong       = fmt.Errorf("modbus: frame too long: %w", pdu.ErrProtocol)
    ErrMalformedFrame     = fmt.Errorf("modbus: malformed frame: %w", pdu.ErrProtocol)
    ErrTransactionMismatch = fmt.Errorf("modbus: transaction id mismatch: %w", pdu.ErrProtocol)
)

// modbus/errors.go
type ExceptionError struct {
    Exception *pdu.ExceptionResponse
    Class     error // interfaces.ErrDeviceRejected 或 interfaces.ErrDeviceInternal
}
func (e *ExceptionError) Error() string
func (e *ExceptionError) Unwrap() []error // {e.Exception, e.Class}

var (
    ErrUnitMismatch = fmt.Errorf("modbus: response unit id mismatch: %w", pdu.ErrProtocol)
    ErrBroadcastUnit = errors.New("modbus: broadcast unit id is not valid for a response exchange")
)

func IsProtocolError(err error) bool // errors.Is(err, pdu.ErrProtocol)
func ExceptionFrom(err error) (*pdu.ExceptionResponse, bool)
```

**映射表**：

| 现象 | 04a 返回 | 04b 读路径 | 04b/09 写路径 code |
|---|---|---|---|
| 连接拒绝、端口不可用、写失败、读前 EOF、连接被关闭 | `%w interfaces.ErrLinkDown` | `OutcomeFailed`，全部点 `bad` | 5040 |
| 帧已发出，截止时间内无响应/超时 | `%w interfaces.ErrDeviceNoResponse` | `OutcomeFailed`，全部点 `bad` | 5044 |
| 坏 CRC、短帧、MBAP 长度/proto 错、响应功能码不匹配、事务号/unit 不匹配 | `pdu.ErrProtocol` 族 | `OutcomeFailed`，全部点 `bad` | 5044 |
| 异常码 01/02/03 | `*ExceptionError`，`Class=ErrDeviceRejected` | `OutcomePartial`，对应点 `bad` | 4001 |
| 异常码 04/05/06/08/0A/0B/未知 | `*ExceptionError`，`Class=ErrDeviceInternal` | `OutcomePartial`，对应点 `bad` | 5044 |
| 本地数量/地址越界（调用方 bug） | `pdu.ErrInvalidQuantity`/`ErrInvalidAddress` | 视为调用失败，全部点 `bad` | 4001（兜底；不应到达设备） |
| `Client` 已关闭 | `interfaces.ErrClosed` | 视为链路不可用 | 5040 |

说明：

- “非法功能码”有两种含义，计划都覆盖：本地编码/解码遇到未知功能码 → `ErrUnsupportedFunction`（协议错误）；设备以异常码 01 拒绝请求 → `*ExceptionError`（有效响应，`ExceptionClassRejected`，写路径 4001）。二者不得混为同一个错误。
- 坏 CRC/短帧是“没有获得有效响应”，写路径归 5044，读路径归 `OutcomeFailed`；不归 4001。
- 异常码是**有效响应**，不是协议错误；`IsProtocolError` 对它返回 false，04b 用 `ExceptionFrom` 取码。
- 5043 不由 04a/`Write` 返回；写后回读容差归 09。
- 5040/5044/4001 的最终判定归 04b/09；04a 只保证哨兵可 `errors.Is`、异常可 `errors.As`。

### 3.8 串口 RTU 的实现范围与缺口

- 04a **实现 RTU framing 与 CRC**，但**不实现 termios/波特率/奇偶校验/串口设备打开**：
  - `docs/testing.md` 明确“串口 termios 与波特率留实物联调”。
  - 无实物，无法验证 ioctl、read timeout、RS485 方向控制；提前实现只会把未验证代码塞进生产路径。
  - 推荐做法：`Conn` 是打开结果；`NewRTUClient(conn, clock)` 接受任何满足 `Conn` 的流。生产串口 opener 在 20/实物联调 ticket（或后续单独 ticket）实现，并提供给 04b/装配层。
  - 测试用 `net.Pipe` 作为“字节流”验证 RTU framing；不打开 `/dev/tty*`。
- 因此 04a 的“串口 RTU”验收是 **framing + 注入传输**，不是“能打开真实串口”。这与 ticket 的“三种传输 framing 可切换”一致；真实串口连通性属于 20。
- 影响：04b 在生产上要读 `modbus-rtu` 链路时，需要装配层注入串口 `Conn`；在 20 之前不能声称真实串口可用。此缺口需写入 04b/20 的交接说明。

### 3.11 并发、事务号与重同步

- `Client` 用 `sync.Mutex` 串行化整个交换；对调用方并发安全。
- MBAP：事务号每请求递增，响应事务号必须匹配；不匹配 → `ErrTransactionMismatch`（协议错误）。
- RTU：没有事务号，依赖严格串行；**超时后底层流可能残留迟到的响应**，04a 不做自动清空/重同步，只保证不发第二个并发帧。04b 在超时后必须自行关闭并重建 `Conn`/`Client`（或实现明确的 flush 策略），否则下一次交换可能读到上一次的迟到帧。此项写入 04b 交接与风险（§9.1）。
- 04a 不实现重试、退避、链路状态或调度；这些归 04b/03a。

### 3.12 日志与可观测性

推荐 **A：04a 不打日志**。

- 库层返回带上下文（功能码、地址、数量、异常码、错误类别）的 `error`，由 04b/内核决定日志字段与脱敏。
- 不在库内 import `log/slog`，不打印 PDU/寄存器原文，避免噪声与敏感数据；`REQ-OPS-03` 的日志责任在装配/内核。
- 备选 B 及代价见 §4.10。

## 4. 需要拍板的边界（A/B + 推荐）

> 每项给出 A/B、推荐、理由、影响。标注 **[用户拍板]** 的项需要用户在计划评审时明确选择；其余为工程决策，若用户不反对按推荐执行。

### 4.1 串口实现范围：完整 termios vs 抽象 opener + 留实物联调 **[用户拍板]**

- **A（推荐）**：只做 RTU framing + `Conn` 注入；不实现 termios/波特率；真实串口 opener 留给 20/实物联调。
- **B**：在 04a 用 `golang.org/x/sys/unix` 完整实现 termios、波特率、奇偶校验、读超时。
- **推荐 A**。理由：`docs/testing.md` 明确留实物联调；无实物时 B 的代码不可验证，且把平台细节引入本 ticket。影响：04b 的 `modbus-rtu` 生产路径需要装配层提供串口 `Conn`；在 20 前只能验证 framing/pipe，不能声称真实串口可用。
- 若选 B：必须新增 `golang.org/x/sys/unix` 直接依赖（见 §4.2），增加 Linux build-tag/串口测试替身，并把波特率/校验/超时数值登记缺口台账（已有 C2/C3）。

### 4.2 外部依赖：零新增 vs 引入 `x/sys/unix` **[用户拍板，依赖 §4.1]**

- **A（推荐）**：零新增；`go.mod`/`go.sum` 不变，`golang.org/x/sys` 继续 indirect。
- **B**：`golang.org/x/sys/unix` 变为直接依赖，用于 termios。
- **推荐 A**。理由：保持静态构建/arm64 简单，避免为未验证的串口代码承担依赖升级与平台测试成本；x/sys 本身兼容 `CGO_ENABLED=0`，但版本钉住与 arm64 验证仍是额外工作。影响：选 B 必须更新 `go.mod`/`go.sum`，在 `make check` 的双架构静态构建与 `verify-static` 中重新证明，并在计划 v2 记录。

### 4.3 传输抽象：自定义 `Conn` vs `io.ReadWriter` vs 只用 `net.Conn` **[工程决策]**

- **A（推荐）**：`Conn = io.ReadWriteCloser + SetDeadline(time.Time) error`，`Framer` 注入。
- **B**：只用 `io.ReadWriter`，另行传 deadline 函数；或只接受 `net.Conn`。
- **推荐 A**。理由：`net.Conn`/`net.Pipe` 直接满足；未来串口 opener 只需实现同一接口；deadline 是一等能力，避免在驱动内再造计时 goroutine；测试可写脚本化 `Conn`。影响：`Conn` 是 04a 的稳定导出面之一，04b 直接复用；06a 服务端不使用它。

### 4.4 04a/04b 切分：协议库 vs 半驱动 **[用户拍板]**

- **A（推荐）**：04a 只交付 PDU/framing/Client/测试；04b 实现 `interfaces.Driver`、批量读、质量、链路状态。
- **B**：04a 同时实现一个最小 `Driver`（Read 单点/写单点），04b 再扩展批量/质量。
- **推荐 A**。理由：ticket 验收只要求 PDU/framing/坏帧/测试从站；B 会提前引入 profile、Outcome、LinkStatus 语义，抢占 04b 范围，并迫使 04a 处理配置模型。影响：04b 从 `Client` 开始，不需要改 04a 的协议层；04a 的 PR 更小、可独立回滚。

### 4.5 config/app 装配：04a 不接线 vs 提前接线 **[用户拍板]**

- **A（推荐）**：04a 不修改 `internal/config`/`internal/app`/`cmd`；不做 `Driver` 注册。
- **B**：04a 让 `app` 从 `links.yaml` 构造 Modbus `Client` 并启动一个最小读取循环。
- **推荐 A**。理由：没有 04b 的批量读/错误→Outcome 映射时，B 只能做半成品；会改生产启动路径与既有 app 测试，收益低。影响：04a 只被测试引用；04b 负责装配与接线。

### 4.6 04a 的驱动级 API 是否由 04b 直接使用 **[用户拍板]**

- **A（推荐）**：04b 直接使用 `modbus.Client` + `pdu` 类型 + `framing`；04a 冻结小型导出面。
- **B**：04a 只导出原始 `[]byte`/frame，04b 自己再包一层请求/响应类型。
- **推荐 A**。理由：避免 04b 重复实现长度、CRC、异常、边界校验；`Do` 与便捷方法是 04b 的自然输入；异常类型可让 04b 把“对应点 bad”映射到具体批次。影响：04a 的 API 需要经过本计划评审后保持稳定；04b 不得要求改签名，若确需扩展按新计划评审。

### 4.7 异常码分类：01/02/03 → 4001；其余 → 5044 **[用户拍板]**

- **A（推荐）**：01/02/03 = `ExceptionClassRejected`（4001）；04/05/06/08/0A/0B/未知 = `ExceptionClassInternal`（5044）。
- **B**：只有 01/02/03 与 04 明确分类；05/06/08/0A/0B/未知作为“未分类异常”，由 04b/09 另行决定。
- **推荐 A**。理由：`REQ-INVOKE-05` 只给“参数非法→4001 / 设备内部错误→5044”两类；未知异常若不归 5044 会落到 4001 兜底，语义更差。0B 虽是“目标无响应”，仍属有效异常响应，归 5044。影响：05（长操作 ACK）在同步引擎中会被当作失败；若未来支持长操作，需新 ticket。若用户认为 0B 更像 `ErrDeviceNoResponse`，可在 v2 调整，但最终 code 仍是 5044。

### 4.8 PDU 导出面：具体 sealed 类型 vs 通用接口/反射 **[工程决策]**

- **A（推荐）**：具体请求/响应结构体 + sealed `Request`/`Response` 接口 + `Encode/Decode` 函数。
- **B**：完全泛化的 `PDU interface{ MarshalBinary() }` + 注册表，允许外部功能码扩展。
- **推荐 A**。理由：04a 只需 03/04/06/16；具体类型让 04b 的类型断言/字段访问简单；sealed 防止外部实现绕过校验。影响：新增功能码需要改 `pdu` 包（新 ticket），符合“不要为未需求的功能码做插件化”的原则。

### 4.9 错误映射位置：04a 分层分类 vs 全部下沉 04b **[用户拍板]**

- **A（推荐）**：`pdu`/`framing` 报协议错误；根包 `modbus` 映射 I/O → `ErrLinkDown`/`ErrDeviceNoResponse`、异常 → `ErrDeviceRejected`/`ErrDeviceInternal`；04b 只做 Read/Write 语义映射。
- **B**：04a 只返回原始错误，所有哨兵映射由 04b 完成。
- **推荐 A**。理由：ticket 明确要求“坏帧归为协议错误”；04a 是最接近字节的一层，能可靠区分超时/EOF/坏 CRC/异常；04b 的映射表因此是机械的。影响：04a 的 `ExceptionError` 与 `IsProtocolError` 成为 04b 的稳定输入；09 仍拥有最终 code 表。

### 4.10 RTU-over-TCP 细节：裸 RTU vs 额外封装/帧间静默 **[工程决策]**

- **A（推荐）**：TCP 流上直接跑 RTU ADU；无 MBAP；CRC 不变；`DialTCP` + `NewRTU()`；请求严格串行；不额外插帧间静默。
- **B**：为 RTU-over-TCP 定义独立封装（例如加长度/事务头），或在客户端插入固定帧间延迟。
- **推荐 A**。理由：现场“串口服务器”通常就是裸 RTU 透传；B 不是标准 Modbus，且固定延迟需要新的时间数值/ASSUMED。影响：若现场网关要求 3.5 字符/自定义封装，20 联调时再按缺口台账增加配置/驱动分支；04a 不预埋。

### 4.11 广播 unit id 0：`Do` 拒绝 vs 允许 **[工程决策]**

- **A（推荐）**：`framing` 可编码 unit 0；`Client.Do` 拒绝 unit 0（`ErrBroadcastUnit`），因为交换等待响应而广播永不响应。
- **B**：允许广播写并依赖超时失败。
- **推荐 A**。理由：引擎只按设备单播读写，不发送广播；拒绝能尽早暴露配置错误，避免无谓的 300–500ms 超时。影响：`config.Address.UnitID=0` 的配置在 04b 装配时应被拒绝或报警（04b 负责）；04a 的 framing 层不阻止，保留未来广播写的可能。

### 4.12 并发策略：Client 内部串行 vs 多请求在途 **[工程决策]**

- **A（推荐）**：一个 `Client` 同时只允许一个在途交换（互斥）；调用方可并发调用，但实际串行。
- **B**：MBAP 允许多个在途请求，按事务号分发响应。
- **推荐 A**。理由：RTU 物理上不支持并发；TCP 并发会显著增加响应分发/超时清理复杂度，且 04b 的验收是“单从站超时后继续其他从站”，不是“同时多帧”。影响：04b 的并发断言应理解为“各设备各自有截止时间、超时不无限阻塞后续设备”，而不是同一 TCP 连接上真正并行；若需要真并行，04b 可为不同设备建多个 `Client`/连接，或在后续 ticket 扩展。

### 4.13 日志/可观测性：04a 不打日志 vs 注入 logger **[工程决策]**

- **A（推荐）**：04a 只返回带上下文的错误，不 import `log/slog`，不打印 PDU/寄存器。
- **B**：`NewClient` 接收 `*slog.Logger`，记录每次请求/响应摘要。
- **推荐 A**。理由：避免库层日志策略与脱敏责任；04b/18 决定指标与日志字段；减少测试噪声。影响：调试依赖错误文本与 04b/18 的观测；若需要帧级排障，可在后续以显式调试开关加入，不默认打印 payload。

### 4.14 汇总：需要用户确认的项

| 编号 | 决策 | 推荐 | 是否需用户明确 |
|---|---|---|---|
| 4.1 | 串口实现范围 | A：只做 framing + 注入 | 是 |
| 4.2 | 外部依赖 | A：零新增 | 是（随 4.1） |
| 4.4 | 04a/04b 切分 | A：库 + 测试 | 是 |
| 4.5 | config/app 装配 | A：不接线 | 是 |
| 4.6 | 04b 直接使用 04a API | A：是 | 是 |
| 4.7 | 异常码分类 | A：01/02/03→4001，其余→5044 | 是 |

| 4.3/4.8/4.10/4.11/4.12/4.13 | 工程决策 | 见各节 | 否（除非反对） |

## 9. 风险、假设与缺口台账

### 9.1 风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| RTU 长度推断错误（请求/响应/异常） | 分片/粘包、坏帧误判 | golden ADU + 每个功能码长度表 + 分片/粘包测试 |
| CRC 字节序错误 | 对端全部拒绝 | 固定 CRC 向量 + 线上低字节断言 |
| 假时钟与真实 socket deadline 混用 | 测试不确定或误报 | 脚本化 `Conn` 断言 deadline 推导；真实 loopback 只做连通性，不做紧时序断言 |
| `context.AfterFunc` 与清空 deadline 竞态 | 偶发过期 deadline/读失败 | 回调完成后再清空；`-race` + 取消测试 |
| RTU 超时后迟到响应污染下一次交换 | 04b 读到错误帧 | 04a 严格串行但不自动重同步；04b 超时后重建 `Conn`/`Client`（写入交接） |
| 04a 范围蔓延到 04b | 返工、评审困难 | §1.3 非目标；`Driver`/批量/质量/链路状态明确划走 |
| `modbustest` 被生产包误 import | 违反依赖边界/二进制膨胀 | 只允许 `_test.go` 引用；提交前 grep 自查；代码评审 |
| 05/06/08/0A/0B/未知异常分类与规范字面不完全一致 | 写路径 code 误判 | §4.7 显式拍板；保留原始异常码，09 可再判定 |
| 串口无法真实验证 | 生产 `modbus-rtu` 不可用 | §4.1 推荐 A；20 实物联调补 opener；缺口台账登记 |
| 新增依赖影响静态构建 | arm64/verify-static 失败 | §4.2 推荐零新增；若选 B 重新跑双架构构建并记录 |
| 真实 TCP 连接在测试中挂起 | CI 超时 | 测试用 channel/Close 释放；仅失败保护使用短 `time.After` |

### 9.2 假设

- Modbus 功能码/数量上限/异常码/CRC-16/MODBUS 为协议标准事实，不属于硬件 ASSUMED；ASSUMED 仅涉及现场网关/串口行为。
- `Conn.SetDeadline` 的语义与 `net.Conn` 一致；未来串口实现必须提供同等语义。
- `context.AfterFunc` 在 Go 1.27 可用；它只做取消传播，不引入业务计时器。
- `time.Time{}` 可作为“清空 deadline”的零值；测试不依赖清空后的真实计时。
- 真实串口 opener、RTU-over-TCP 网关帧间时序、现场波特率/校验属于实物联调（20）；04a 只验证 framing 与协议层。

### 9.3 缺口台账需要登记的新 ASSUMED

建议新增一条（仅在用户批准 §4.10 推荐案时）：

| ID | 项 | 当前取值（ASSUMED） | 依据 / 假设 | 需向客户索取 | 影响 |
|---|---|---|---|---|---|
| C10 | RTU-over-TCP 网关帧间时序 | 网关接受连续的请求-响应，无需额外 3.5 字符静默；客户端严格串行发送 | 常见串口服务器透传行为；无实物 | 现场网关型号、手册、是否要求帧间延迟 | 04a 的节奏控制；20 实物联调与可能的配置项 |

- 不新增代码常量；若将来加入帧间延迟，必须先把数值登记到台账并由配置驱动。
- 现有 C2/C3（串口设备名/波特率/校验）已覆盖串口参数缺口，04a 推荐案不新增同类项。
- 若 §4.1 选 B，还需登记串口读超时/ioctl 行为的 ASSUMED 及替代点；本计划不预填。
