## 2. 硬约束的落地方式

### 2.1 时间只能从注入 `Clock` 进入

- 非 `_test.go` 的 `internal/drivers/**` 禁止出现 `time.Now/Since/Until/NewTicker/NewTimer/Tick/After/AfterFunc/Sleep` 与 `context.WithTimeout/WithDeadline`；`make time-check` 机械执行。
- 生产代码只使用 `time.Time`、`time.Duration`、`time.Time{}`（零值）等类型；`Client` 接收绝对 `deadline time.Time`（与 `interfaces.ReadRequest.Deadline` 一致），用 `interfaces.Clock.Now()` 判断是否已过期；不自行把 timeout 转成 deadline。
- 非零且 `!deadline.After(clock.Now())` 时立即返回 `interfaces.ErrDeviceNoResponse`，不发送帧；这正是 REQ-SCHED-02 的“设备截止时间”在驱动侧的含义。
- **context 只用于取消传播**：`Client.Do` 在入口、注册取消钩子后、I/O 前检查 `ctx.Err()`；用 `context.AfterFunc` + 显式 done channel 在取消时把 `Conn` deadline 设为 `clock.Now()`（立即到期）以解除阻塞读；读完返回 deadline 错误时先查 `ctx.Err()`，取消返回 `ctx.Err()`。绝不用 `context.WithTimeout/WithDeadline` 做业务超时。
- 真实网络/串口 I/O 的截止由 `Conn.SetDeadline` 承担；ADR-0003 已说明“真实网络 I/O 的超时由底层库控制，测试用内存对端”。假时钟测试用脚本化 `Conn` 断言绝对 deadline 的透传，而不是靠真实 `net.Conn` 的墙钟。
- `NewClient` 拒绝 nil/typed-nil `Conn`、`Framer`、`Clock`；`Do` 对 nil `ctx` 返回参数错误；测试覆盖。

### 2.2 依赖方向

- `scripts/check-deps.sh` 对 `internal/drivers` 的传递闭包禁止 `internal/core`、`internal/channels`、`internal/adapters`、`internal/store`、`internal/testutil`、`internal/clock/realclock`、`internal/sim`、bbolt。
- 因此生产包只允许 import 标准库、`internal/interfaces`、`internal/drivers/modbus/**` 自身子包；测试文件可 import `internal/testutil/fakeclock`（`.Deps` 不含 `_test.go` 的 import）。
- 04a 不 import `internal/config`；配置到库参数的映射归 04b/装配层。

### 2.3 构建与依赖

- `CGO_ENABLED=0`，`linux/amd64` 与 `linux/arm64` 静态构建；`make build-all verify-static` 必须通过。
- `make check` 的 `build-all` 只构建 `cmd`，不会自动证明未接线的 `internal/drivers/modbus` 可跨架构编译；因此额外显式执行：

- 推荐**不新增依赖**：`go.mod`/`go.sum` 不变；`golang.org/x/sys` 保持 indirect（见 §4.1/§4.2）。
- 不新增外部/网络数据库、不做 Web 后台；保持单二进制 + YAML + systemd。

### 3.2 PDU 导出面

`pdu` 是纯函数包：不读 I/O、不看时间、不 import `interfaces`。所有多字节整数使用 **大端**（Modbus 标准），16 位寄存器元素保持 `uint16`；32 位/浮点解码是 04b 的职责，PDU 不解释寄存器组合。

```go
package pdu

type FuncCode uint8

const (
    FuncReadHoldingRegisters   FuncCode = 0x03
    FuncReadInputRegisters     FuncCode = 0x04
    FuncWriteSingleRegister    FuncCode = 0x06
    FuncWriteMultipleRegisters FuncCode = 0x10
)

const (
    MaxReadRegisters   = 125 // 0x7D
    MaxWriteRegisters  = 123 // 0x7B
    MaxPDUSize         = 253
    ExceptionFlag      = 0x80
)

type ExceptionCode uint8

const (
    ExceptionIllegalFunction       ExceptionCode = 0x01
    ExceptionIllegalDataAddress    ExceptionCode = 0x02
```

编码/解码前置校验：

- `ReadRegistersRequest.Func` 仅允许 03/04，其他值 → `ErrUnsupportedFunction`。
- `EncodeRequest`/`EncodeResponse` 生成后必须满足 `len(PDU) <= 253`，否则 `ErrMalformed`。
- unit id 不属于 PDU；PDU 层不拒绝 unit 0（传输语义由 04b/装配校验，见 §4.11）。

**编码/解码规则**：

| 功能码 | 请求 PDU | 响应 PDU | 校验 |
|---|---|---|---|
| 03 / 04 | func, addr(2), qty(2) | func, byteCount(1), data(2×qty) | byteCount == 2×qty；总长 ≤ 253 |
| 06 | func, addr(2), value(2) | func, addr(2), value(2) | 回显 addr/value 必须等于请求 |
| 16 | func, addr(2), qty(2), byteCount(1), data(2×qty) | func, addr(2), qty(2) | byteCount == 2×qty；回显 addr/qty 必须等于请求 |
| 异常 | — | func\|0x80, code(1) | func 必须等于请求功能码；code 任意 |

**边界**：

| 项 | 规则 |
|---|---|
| 读数量 | 1..125（0x7D）；0、126 及以上 → `ErrInvalidQuantity` |
| 写多数量 | 1..123（0x7B）；0、124 及以上 → `ErrInvalidQuantity` |
| 写单 | 恰好 1 个 uint16，0..65535 全部合法 |
| 地址 | `uint16`；`address + quantity - 1` 不得溢出 0xFFFF，否则 `ErrInvalidAddress` |
| PDU 长度 | 1..253；超长或空 → `ErrMalformed` |
| 功能码 | 仅 03/04/06/16；其他 → `ErrUnsupportedFunction`（异常响应的 0x80 位单独处理） |
| 单位 | PDU 不携带 unit id；unit 属于 ADU/framing |

**异常分类**（`ExceptionCode.Class()`）：

| 异常码 | 含义 | Class | 04b/09 关系 |
|---|---|---|---|
| 01 | 非法功能 | Rejected | 4001 |
| 02 | 非法数据地址 | Rejected | 4001 |
| 03 | 非法数据值 | Rejected | 4001 |
| 04 | 从站设备故障 | Internal | 5044 |
| 05 | 确认（长操作） | Internal | 5044（同步引擎无法等待长操作） |
| 06 | 从站设备忙 | Internal | 5044 |
| 08 | 存储奇偶错 | Internal | 5044 |
| 0A | 网关路径不可用 | Internal | 5044 |
| 0B | 网关目标设备无响应 | Internal | 5044 |
| 00 / 保留 / 未知 | — | Internal | 5044，保留原始码 |

> 05/06/08/0A/0B/00/未知的分类是规范未逐条列出的边界，需用户确认（§4.7）。读路径不是一律 `Partial`：04b 按 `REQ-QUALITY-03` 判定——同一批中至少一个成功样本才 `OutcomePartial`，全批失败则 `OutcomeFailed`+全部点 `bad`；写路径才映射到 4001/5044（09）。04b ticket 的措辞需按此解释。

### 3.3 CRC16

- 算法：CRC-16/MODBUS，反射多项式 `0xA001`（即 `0x8005` 反射），初值 `0xFFFF`，无最终异或；对“unit + PDU”逐字节计算。
- 线上字节序：**低字节在前**（`crc & 0xFF`, `crc >> 8`）。
- 参考实现放在 `framing/crc16.go`，导出 `func CRC16(data []byte) uint16`；`pdu` 不依赖 CRC。
- 校验向量（测试固定；已用独立位级实现计算）：

| 输入（hex） | CRC 值 | 线上字节 |
|---|---|---|
| `31 32 33 34 35 36 37 38 39`（"123456789"） | `0x4B37` | `37 4B` |
| `01 03 00 00 00 02` | `0x0BC4` | `C4 0B` |
| `01 03 00 00 00 0A` | `0xCDC5` | `C5 CD` |
| `01 04 00 00 00 01` | `0xCA31` | `31 CA` |
| `01 06 00 02 00 32` | `0xDFA9` | `A9 DF` |
| `01 10 00 02 00 02 04 00 32 00 64` | `0x52D2` | `D2 52` |
| `01 03 04 00 32 00 64` | `0x175A` | `5A 17` |
| `01 04 02 FF FF` | `0x80B8` | `B8 80` |
| `01 10 00 02 00 02` | `0x08E0` | `E0 08` |
| `01 83 02` | `0xF1C0` | `C0 F1` |

### 3.4 Framing：MBAP、RTU、RTU-over-TCP

```go
package framing

type Frame struct {
    TransactionID uint16 // 仅 MBAP 使用；RTU 为 0
    UnitID        uint8
    PDU           []byte
}

type Framer interface {
    Name() string
    // PDUErrorsAreRecoverable 表示 PDU 解码/回显校验失败后流边界是否仍可信：
    // MBAP 为 true（完整 ADU 已按 len 消费），RTU 为 false（必须重建）。
    PDUErrorsAreRecoverable() bool
    Encode(f Frame) ([]byte, error)
    DecodeRequest(r io.Reader) (Frame, error)
    DecodeResponse(r io.Reader, req pdu.Request, expectTxn uint16) (Frame, error)
}

func NewMBAP() Framer
func NewRTU() Framer
```

#### MBAP（Modbus TCP）

```text
+----------+----------+----------+----------+----------+
| txn id 2 | proto 2  | len 2    | unit 1   | PDU ...  |
+----------+----------+----------+----------+----------+
```

- `proto` 必须为 `0x0000`。
- `len` = unit(1) + PDU 长度，范围 2..254；ADU 总长 8..260（6 字节头 + len；最小合法帧为 unit+func，即 len=2）。
- `DecodeRequest` 读满 7 字节（含 unit）后读 `len-1` 字节 PDU；`DecodeResponse` 额外校验 `TransactionID == expectTxn`。
- 分片：所有读取用 `io.ReadFull` 精确读，天然支持“一次 Read 只来 1 字节”。
- 粘包：每次只消费一帧的精确长度，剩余字节留在底层流中，下一次 `Decode*` 读取下一帧；测试用 `bytes.Buffer` 放两帧验证。
- **可恢复性区分**：
  - `len` 合法且已消费完整 ADU 后发现的错误（proto 非 0、txn 不匹配、PDU 功能码/字节数/回显不匹配）→ `ErrMalformedFrame`/`ErrTransactionMismatch`，流边界仍可信，**不**标记 `ErrUnrecoverable`；调用方可继续下一帧。
  - `len < 2`、`len > 254`、头/体截断（`ErrShortFrame`）→ 无法确定帧边界，返回 `errors.Join(ErrUnrecoverable, 具体错误)`；调用方必须关闭并重建 `Conn`/`Client`。
- 所有上述错误都满足 `errors.Is(err, pdu.ErrProtocol)`。

#### RTU（串口与 RTU-over-TCP）

```text
+----------+----------+----------+----------+----------+
| unit 1   | PDU ...  | CRC low  | CRC high |          |
+----------+----------+----------+----------+----------+
```

- ADU 总长 4..256；CRC 对 unit+PDU 计算，线上低字节在前。
- **请求解码**（供测试从站）按功能码推断长度：
  - 03/04/06：固定 8 字节（unit+func+addr2+qty/value2+CRC2）。
  - 16：先读 unit+func+addr2+qty2+byteCount1；**在读数据前**校验 `qty` 在 1..123、`byteCount` 为偶数且 `byteCount <= 246`（2×123）且 `byteCount == 2×qty`；再读 `byteCount` 数据 + CRC2。
  - 未知功能码：读满 unit+func 后返回 `errors.Join(ErrUnrecoverable, pdu.ErrUnsupportedFunction)`；RTU 流边界不可信，测试从站/客户端不得假装还能回异常 01 并继续解析。
- **响应解码**（供客户端）使用 `req` 推断长度：
  - `func|0x80`：固定 5 字节（unit+func+code+CRC2）。
  - 03/04：读 unit+func+byteCount，**在读数据前**校验 `req.Quantity` 在 1..125、`byteCount` 为偶数且 `byteCount <= 250`（2×125）且 `byteCount == 2×req.Quantity`；再读 `byteCount` 数据 + CRC2。
  - 06/16：固定 8 字节。
- 任何长度不足、CRC 错误、功能码与请求不匹配、byteCount/qty 越界或不匹配：RTU 一律返回 `errors.Join(ErrUnrecoverable, 具体错误)`，并满足 `errors.Is(err, pdu.ErrProtocol)`。**RTU 的任何解码错误都表示流边界不可信，调用方必须关闭并重建 `Conn`/`Client`，不得继续解析。**
- RTU 无事务号；`Encode` 明确忽略 `Frame.TransactionID`；请求/响应只能靠严格串行（`Client` 互斥）与功能码/长度匹配。

#### RTU-over-TCP

- 不新增 framing：同一 RTU ADU 直接跑在 TCP 流上，**没有** MBAP，CRC 不变。
- 连接建立用 `DialTCP`；`Client` 注入 `framing.NewRTU()`。
- 不实现额外帧间静默/3.5 字符间隔；理由与 ASSUMED 见 §3.8、§9.3。

**三种传输如何切换**：`NewClient(conn, framer, clock)` 的 `framer` 参数是唯一开关；`NewTCPClient`/`NewRTUOverTCPClient` 只是“拨号 + 选择 framer”的便捷函数；串口 RTU 由调用方提供 `Conn` 后 `NewRTUClient`。PDU 编解码完全不感知 framing。

### 3.5 传输抽象与注入形状

```go
package modbus

type Conn interface {
    io.ReadWriteCloser
    SetDeadline(t time.Time) error
}
```

- `net.Conn` 直接满足；`net.Pipe` 返回的 `net.Conn` 也满足；未来串口 opener（`04c-serial-opener` 或 04b）只需返回满足此接口的对象。
- 选择 `SetDeadline` 而不是 `io.ReadWriter`：截止时间是驱动层的硬需求，且 `net.Conn`/串口实现天然支持；避免在驱动里另造计时 goroutine。
- 注入点：
  - `NewClient(conn Conn, framer framing.Framer, clock interfaces.Clock) (*Client, error)`：最底层，04b 与测试使用。
  - `DialTCP(ctx, addr string) (Conn, error)`：生产 TCP；错误包装 `interfaces.ErrLinkDown`。
  - `NewTCPClient(ctx, addr, clock)` / `NewRTUOverTCPClient(ctx, addr, clock)`：便捷构造，内部 `DialTCP` + `NewClient`。
  - `NewRTUClient(conn Conn, clock)`：串口或任意注入流。
- `NewClient` 对 `conn`/`framer`/`clock` 做 nil 与 typed-nil 检查（反射判断接口内的 nil 指针），失败返回错误。
- `DialTCP` 只用 `ctx` 做取消传播，不设置 `net.Dialer.Timeout`/`Deadline`；连接尝试的超时与重试归 04b/装配层用注入 `Clock` 管理（04a 不把运行时计时器引入驱动）。
- unit id 0 不由 04a 拒绝：`Do` 原样编码/发送，04b/装配按 RTU/TCP 校验（§4.11）。
- 04b 复用方式：一个链路/设备一个 `Client`（由 04b 决定），`Client` 内部串行化；`Client` 方法接收绝对 `deadline`；04b 负责 profile → PDU 的映射与错误 → Outcome 的映射。
- 06a 复用方式：06a 是服务端，使用自己的 listener/conn 与独立 server 实现；**不复用** `Client`，也不把 `modbustest` 当生产从站。

### 3.6 Client 交换、超时与取消

```go
type Client struct {
    conn      Conn
    framer    framing.Framer
    clock     interfaces.Clock
    mu        sync.Mutex
    nextTxn   uint16
    closed    atomic.Bool
    closeOnce sync.Once
}

func NewClient(conn Conn, f framing.Framer, clock interfaces.Clock) (*Client, error)

// deadline 零值表示无 per-call deadline；非零是绝对时刻，发送任何帧前
// 先用注入 Clock 判断是否已过期。
func (c *Client) ReadHoldingRegisters(ctx context.Context, unitID uint8,
    address, quantity uint16, deadline time.Time) ([]uint16, error)
func (c *Client) ReadInputRegisters(ctx context.Context, unitID uint8,
    address, quantity uint16, deadline time.Time) ([]uint16, error)
func (c *Client) WriteSingleRegister(ctx context.Context, unitID uint8,
    address, value uint16, deadline time.Time) error
func (c *Client) WriteMultipleRegisters(ctx context.Context, unitID uint8,
    address uint16, values []uint16, deadline time.Time) error
func (c *Client) Do(ctx context.Context, unitID uint8,
    req pdu.Request, deadline time.Time) (pdu.Response, error)
func (c *Client) Close() error // 幂等；直接关闭底层 Conn，不等待在途 Do
```

**交换流程**（`Do`）：

1. 持锁（同一 `Client` 同时只允许一个在途交换；对 MBAP 保证事务号与响应匹配，对 RTU 保证没有并发帧）。
2. 检查 nil `ctx` → `pdu.ErrArgument`；检查本地 `closed` → `interfaces.ErrClosed`；nil req / PDU 参数；**检查 `ctx.Err()`（取消优先于已过期 deadline）**。
3. 绝对 deadline：`deadline.IsZero()` 表示无 per-call 截止；非零且 `!deadline.After(c.clock.Now())` 时立即返回 `interfaces.ErrDeviceNoResponse`，**不发送任何帧**（REQ-SCHED-02 的设备截止语义）。
4. `c.conn.SetDeadline(deadline)`（零值即清空/无截止）；返回错误时视为链路不可用（本地 closed → `ErrClosed`，否则 `ErrLinkDown`），不继续发送。注册取消传播，使用显式 done channel：
   ```go
   done := make(chan struct{})
   stop := context.AfterFunc(ctx, func() {
       defer close(done)
       _ = c.conn.SetDeadline(c.clock.Now())
   })
   defer func() {
       if !stop() {
           <-done // 回调已启动：等它完成，避免清空 deadline 后又被设成过期
       }
       _ = c.conn.SetDeadline(time.Time{})
   }()
   ```
5. 注册后、写 I/O 前再次检查 `ctx.Err()`；已取消则返回包装后的 `ctx.Err()`。
6. 编码 PDU → `framing.Frame{TransactionID: nextTxn, UnitID: unitID, PDU: raw}` → `framer.Encode` → 写满 `Conn`；短写返回 `io.ErrShortWrite`。写完后、读 I/O 前再检查一次 `ctx.Err()`。
7. `framer.DecodeResponse(conn, req, txn)` 读取一帧；校验响应 `UnitID == unitID`。读取阻塞时由 AfterFunc 设过期 deadline 解除；读错误后（步骤 9）先查 `ctx.Err()`。
8. `pdu.DecodeResponse(frame.PDU)`；`pdu.ValidateResponse(req, resp)`。
9. 任何 I/O/解码错误先处理优先级：`ctx.Err() != nil` → 返回包装后的 `ctx.Err()`；本地 `closed` → `interfaces.ErrClosed`；否则按 §3.7 分类（协议错误用 `protocolFailure` 包装；不可恢复时底层错误已带 `framing.ErrUnrecoverable`，`errors.Join` 会保留）。**PDU 解码/回显校验错误**按 `framer.PDUErrorsAreRecoverable()` 决定：false（RTU）补 `framing.ErrUnrecoverable`；true（MBAP）不补。不要用 `Name()` 字符串比较判断传输。
10. 若响应是 `*pdu.ExceptionResponse`，转换为 `*ExceptionError` 返回；否则返回正常响应。

**事务号**：`nextTxn` 从 1 开始，每次 `Do` 递增（0xFFFF 后回绕到 1）；RTU 不使用但同样递增，测试可断言不影响 framing。

**超时**：

- 绝对 `deadline` 直接交给 `Conn.SetDeadline`；不使用 `context.WithTimeout/WithDeadline`，也不在 `Client` 内做 `clock.Now().Add(timeout)`。
- 非零 deadline 已过期 → 发送前返回 `interfaces.ErrDeviceNoResponse`（5044），不产生帧。
- 读阻塞在 deadline 上由底层返回 `os.ErrDeadlineExceeded`/`net.Error.Timeout()`；若 `ctx` 未取消，映射为 `interfaces.ErrDeviceNoResponse`（5044）；若 `ctx` 已取消，返回 `ctx.Err()`。
- 写失败、短写、连接被对端关闭、读之前的 EOF → `interfaces.ErrLinkDown`（5040）。
- 读到一半的 EOF/短读 → 协议错误 `framing.ErrShortFrame`（5044 语义），并按 framing 规则标记 `ErrUnrecoverable`。
- `ctx` 取消 → 返回 `fmt.Errorf("modbus: exchange canceled: %w", ctx.Err())`，不伪装成设备无响应；取消与超时同时发生时取消优先。

**Close**：

- `Close` 用 `sync.Once` + `atomic.Bool` 标记本地 closed，并直接 `conn.Close()`；**不获取交换互斥锁、不等待在途 `Do`**，因此幂等且能立即解除阻塞 I/O。
- 在途 `Do` 的 I/O 被 `conn.Close()` 打断后，先检查本地 closed，返回 `interfaces.ErrClosed`；只有非本地关闭的 I/O 错误才返回 `interfaces.ErrLinkDown`。

**为什么用 `context.AfterFunc` + done channel**：它是标准库的取消钩子，不引入业务计时器；回调只做一次 `SetDeadline`，无共享可变状态（`Conn` 的 deadline 操作本身是并发安全的）。`stop()` 返回 false 只表示回调已启动，**不表示已等待完成**，所以必须 `<-done`。测试用 `-race`、在途 Close 与 goroutine 退出断言覆盖。

### 3.7 错误分类与 REQ-INVOKE-05 的关系

**分层原则**：`pdu`/`framing` 只报“协议/帧”错误；根包 `modbus` 做 I/O 与接口哨兵映射；04b 决定读路径的 Outcome；09 决定写路径的最终 code。

| 连接拒绝、端口不可用、写失败、短写、读前 EOF、连接被对端关闭 | `%w interfaces.ErrLinkDown` | `OutcomeFailed`，全部点 `bad` | 5040 |
| 帧已发出，截止时间内无响应/超时 | `%w interfaces.ErrDeviceNoResponse` | `OutcomeFailed`，全部点 `bad` | 5044 |
| 坏 CRC、短帧、MBAP 长度/proto 错、响应功能码不匹配、事务号/unit 不匹配 | `errors.Join(协议错误, interfaces.ErrDeviceNoResponse[, framing.ErrUnrecoverable])`；`IsProtocolError` 为 true | `OutcomeFailed`，全部点 `bad` | 5044 |
| RTU 解码错误或 MBAP `len` 非法/截断（`ErrUnrecoverable`） | 上一行的 join 中带 `framing.ErrUnrecoverable` | 同协议错误；**04b 必须关闭并重建 `Conn`/`Client`** | 5044；04b 重建链路 |
| 异常码 01/02/03 | `*ExceptionError`，`Class=ErrDeviceRejected` | 有成功样本→`Partial`+对应点 `bad`；全批失败→`Failed`+全点 `bad` | 4001 |
| 异常码 04/05/06/08/0A/0B/00/未知 | `*ExceptionError`，`Class=ErrDeviceInternal` | 有成功样本→`Partial`+对应点 `bad`；全批失败→`Failed`+全点 `bad` | 5044 |
| 本地数量/地址越界（调用方 bug） | `pdu.ErrInvalidQuantity`/`ErrInvalidAddress` | 视为调用失败，全部点 `bad` | 4001（兜底；不应到达设备） |
| `Client` 已关闭 | `interfaces.ErrClosed` | 视为链路不可用 | 5040 |

说明：

- **协议错误的双重哨兵**：`pdu`/`framing` 本身不 import `interfaces`；根包 `Client` 在返回前用 `errors.Join` 让协议错误同时满足 `errors.Is(err, pdu.ErrProtocol)` 与 `errors.Is(err, interfaces.ErrDeviceNoResponse)`。若帧边界已不可信，再带 `framing.ErrUnrecoverable`。不修改 `internal/interfaces`。
- **RTU 错位**：RTU 的任何解码错误（坏 CRC、短帧、未知功能码、功能码不匹配、byteCount 越界）都带 `ErrUnrecoverable`；`pdu.DecodeResponse`/`ValidateResponse` 在 RTU 模式下返回的协议错误也由 `Client` 补 `ErrUnrecoverable`。调用方必须关闭并重建，不能继续解析。MBAP 只有 `len` 非法/截断不可恢复；proto/txn/PDU 错在完整 ADU 已消费后仍可恢复（§3.4）。
- **非法功能码**有两种含义：本地编码/解码遇到未知功能码 → `ErrUnsupportedFunction`（协议错误）；设备以异常码 01 拒绝请求 → `*ExceptionError`（有效响应，`ExceptionClassRejected`，写路径 4001）。二者不得混为同一个错误。
- **异常不是一律 Partial**：`REQ-QUALITY-03` 决定最终 Outcome。04b 只有在同一批存在成功样本时才报 `Partial`；该批整体失败（含全部请求都返回异常）报 `Failed`+全部点 `bad`。04b ticket 的“异常码 → Partial”措辞需按此解释。
- 坏 CRC/短帧是“没有获得有效响应”，写路径归 5044，读路径归 `OutcomeFailed`；不归 4001。
- 异常码是**有效响应**，不是协议错误；`IsProtocolError` 对它返回 false，04b 用 `ExceptionFrom` 取码。异常码 0x00/保留码按未知处理（Internal/5044），保留原始值。
- 5043 不由 04a/`Write` 返回；写后回读容差归 09。
- **04b 的映射义务**：`ErrLinkDown`/`ErrClosed` → 5040；`ErrDeviceNoResponse`/任何协议错误/内部异常码 → 5044；01/02/03 异常 → 4001；5043 只由 09 写后回读判定。
- 本地编码参数错误（`ErrInvalidQuantity`/`ErrInvalidAddress`，以及 `EncodeRequest` 对不支持的本地功能码）不加入 `ErrDeviceNoResponse`；它们是调用方 bug，04b 不应产生。`ErrUnsupportedFunction` 只有在作为线路解码结果由 `Client` 返回时才走协议错误双哨兵。
- unit 0 不在 04a 拒绝：04b/装配按传输校验（RTU 0=广播；TCP unit 0 可作为合法标识，§4.11）。

### 3.8 串口 RTU 的实现范围与缺口

- 04a **实现 RTU framing 与 CRC**，但**不实现 opener/termios/波特率/奇偶校验/串口设备打开**：
  - `docs/testing.md` 的“串口 termios 与波特率留实物联调”指**验证**留到实物；不表示代码由 20 承接。20 的 diff 只允许 config/testdata，不能实现 opener。
  - 无实物，无法验证 ioctl、read timeout、RS485 方向控制；提前实现只会把未验证代码塞进生产路径。
  - 代码归属见 §4.16：推荐另开 `04c-serial-opener`（04a 之后、04b 的 `modbus-rtu` 生产路径之前）；或并入 04b；04a 不实现。
  - 04a 只定义 `Conn` 是打开结果；`NewRTUClient(conn, clock)` 接受任何满足 `Conn` 的流。测试用 `net.Pipe` 作为“字节流”验证 RTU framing；不打开 `/dev/tty*`。
- 因此 04a 的“串口 RTU”验收是 **framing + 注入传输**，不是“能打开真实串口”。这与 ticket 的“三种传输 framing 可切换”一致。
- 影响：04b 的 `modbus-rtu` 生产路径在 opener ticket（04c 或 04b 自身）落地前**阻塞**；TCP 与 RTU-over-TCP 不受影响。20 只做实物联调验证。

### 3.9 04a 是否做 config/app 装配

按 §4.5 推荐 A：04a 只交付库与测试，不修改 `internal/config`/`internal/app`/`cmd`，不实现 `interfaces.Driver`。04b 负责把 `config.Link`/`config.Device`/profile 映射到 `modbus.Client` 并接线。理由与备选见 §4.5。

### 3.10 测试内置最小从站（in-test）

推荐 **A：`internal/drivers/modbus/modbustest` 普通包，test-support only**；若评审更看重“零生产目录表面”，选 B：全部放 `_test.go`（代价是 04b 无法跨包复用）。两种方案都必须用可执行断言证明生产闭包不引用它（见 §6.6）。

```go
package modbustest

type Unit struct {
    Holding map[uint16]uint16
    Input   map[uint16]uint16
}

type Request struct {
    TransactionID uint16
    UnitID        uint8
    Func          pdu.FuncCode
    Address       uint16
    Quantity      uint16
    Values        []uint16
}

type Slave struct { /* mu, units, requests, exception injection */ }

func New(units map[uint8]*Unit) *Slave
func (s *Slave) ServeConn(conn io.ReadWriteCloser, f framing.Framer) error
func (s *Slave) ServeTCP(ctx context.Context, ln net.Listener, f framing.Framer) error
func (s *Slave) Requests() []Request
func (s *Slave) Units() []uint8
func (s *Slave) SetException(unitID uint8, fn pdu.FuncCode, code pdu.ExceptionCode)
```

- 支持：多 unit 路由；03/04 读取；06 写单；16 写多；地址越界回异常 02；不存在的 unit 回异常 0B；请求日志线程安全。
- **未知功能码**：MBAP 下可回异常 01（MBAP 有长度边界，流仍可继续）；RTU 下 `framing.DecodeRequest` 返回带 `ErrUnrecoverable` 的错误，测试从站/客户端**不得假装还能回异常 01**，必须关闭并重建。
- 不使用 `internal/sim`，不提供 HTTP/故障控制；坏 CRC/短帧由客户端测试用脚本化 `Conn` 直接注入原始字节，不放进从站。
- 与 06a 的关系：`modbustest` 是 04a/04b 测试对端，**不是** 06a 的模拟器；06a 必须在 `internal/sim` 内独立实现从站语义，并用独立客户端验证，不得声称复用 `modbustest` 即满足 06a 验收。`TestSlaveServesMultiUnit` 的“未知 unit 回 0B”是测试对端约定，06a 不得照搬。
- 复用限制：`modbustest` 不 import 父包 `modbus`，避免与根包外部测试的 import cycle；它只依赖 `pdu`/`framing`。`doc.go` 写明 test-support only；生产闭包不引用它，用 §6.6 的 `go list -deps` 断言证明。

### 3.11 并发、事务号与重同步

- `Client` 用 `sync.Mutex` 串行化整个交换；对调用方并发安全。
- `Close` 用 `sync.Once` + `atomic.Bool`，不获取交换锁、不等待在途 `Do`；直接关底层 `Conn` 解除阻塞 I/O。在途 `Do` 的 I/O 错误先检查本地 closed → `interfaces.ErrClosed`；对端断开才 `ErrLinkDown`。
- MBAP：事务号每请求递增，响应事务号必须匹配；完整 ADU 已消费后的 txn/proto/PDU 错**可恢复**，流边界仍可信，下一次交换可继续。`len` 非法/截断带 `ErrUnrecoverable`，必须关闭重建。
- RTU：没有事务号，依赖严格串行；**任何解码错误**（坏 CRC、短帧、未知功能码、功能码不匹配、byteCount 越界）都带 `ErrUnrecoverable`，04a 不做自动清空/重同步。04b 在任何 `ErrUnrecoverable` 以及超时后必须关闭并重建 `Conn`/`Client`，迟到响应不能带入下一次交换。
- 04a 不实现重试、退避、链路状态或调度；这些归 04b/03a。

### 3.12 日志与可观测性

按 §4.13 推荐 A：04a 不打日志，只返回带上下文（功能码、地址、数量、异常码、错误类别）的 `error`；不 import `log/slog`，不打印 PDU/寄存器。`REQ-OPS-03` 的日志责任在装配/内核。理由与备选见 §4.13。

## 4. 需要拍板的边界（A/B + 推荐）

> 每项给出 A/B、推荐、理由、影响。标注 **[用户拍板]** 的项需要用户在计划评审时明确选择；其余为工程决策，若用户不反对按推荐执行。

### 4.1 串口实现范围：完整 termios vs 抽象 opener + 另开 opener ticket **[用户拍板]**

- **A（推荐）**：只做 RTU framing + `Conn` 注入；不实现 opener/termios/波特率；opener 归 §4.16（推荐另开 `04c-serial-opener`），20 只做实物验证。
- **B**：在 04a 用 `golang.org/x/sys/unix` 完整实现 termios、波特率、奇偶校验、读超时。
- **推荐 A**。理由：`docs/testing.md` 的“留实物联调”是验证归属；无实物时 B 的代码不可验证，且把平台细节引入本 ticket。影响：04b 的 `modbus-rtu` 生产路径在 opener ticket 落地前阻塞；04a 只能验证 framing/pipe，不能声称真实串口可用。
- 若选 B：必须新增 `golang.org/x/sys/unix` 直接依赖（见 §4.2），增加 Linux build-tag/串口测试替身，并把波特率/校验/超时数值登记缺口台账（已有 C2/C3）。

### 4.2 外部依赖：零新增 vs 引入 `x/sys/unix` **[用户拍板，依赖 §4.1]**

- **A（推荐）**：零新增；`go.mod`/`go.sum` 不变，`golang.org/x/sys` 继续 indirect。
- **B**：`golang.org/x/sys/unix` 变为直接依赖，用于 termios。
- **推荐 A**。理由：保持静态构建/arm64 简单，避免为未验证的串口代码承担依赖升级与平台测试成本；x/sys 本身兼容 `CGO_ENABLED=0`，但版本钉住与 arm64 验证仍是额外工作。影响：选 B 必须更新 `go.mod`/`go.sum`，在 `make check` 的双架构静态构建与 `verify-static` 中重新证明，并在计划 v3 记录用户决策。

### 4.3 传输抽象：自定义 `Conn` vs `io.ReadWriter` vs 只用 `net.Conn` **[工程决策]**

- **A（推荐）**：`Conn = io.ReadWriteCloser + SetDeadline(time.Time) error`，`Framer` 注入。
- **B**：只用 `io.ReadWriter`，另行传 deadline 函数；或只接受 `net.Conn`。
- **推荐 A**。理由：`net.Conn`/`net.Pipe` 直接满足；未来串口 opener 只需实现同一接口；deadline 是一等能力，避免在驱动内再造计时 goroutine；测试可写脚本化 `Conn`。影响：`Conn` 是 04a 的稳定导出面之一，04b 直接复用；06a 服务端不使用它。

### 4.4 04a/04b 切分：协议库 vs 半驱动 **[用户拍板]**

- **A（推荐）**：04a 只交付 PDU/framing/Client/测试；04b 实现 `interfaces.Driver`、批量读、质量、链路状态。
- **B**：04a 同时实现一个最小 `Driver`（Read 单点/写单点），04b 再扩展批量/质量。
- **推荐 A**。理由：ticket 验收只要求 PDU/framing/坏帧/测试从站；B 会提前引入 profile、Outcome、LinkStatus 语义，抢占 04b 范围，并迫使 04a 处理配置模型。影响：04b 从 `Client` 开始，不需要改 04a 的协议层；04a 的 PR 更小、可独立回滚。

### 4.5 config/app 装配：04a 不接线 vs 提前接线 **[用户拍板]**

- **A（推荐）**：04a 不修改 `internal/config`/`internal/app`/`cmd`；不做 `Driver` 注册。
- **B**：04a 让 `app` 从 `links.yaml` 构造 Modbus `Client` 并启动一个最小读取循环。
- **推荐 A**。理由：没有 04b 的批量读/错误→Outcome 映射时，B 只能做半成品；会改生产启动路径与既有 app 测试，收益低。影响：04a 只被测试引用；04b 负责装配与接线。

### 4.6 04a 的驱动级 API 是否由 04b 直接使用 **[用户拍板]**

- **A（推荐）**：04b 直接使用 `modbus.Client` + `pdu` 类型 + `framing`；04a 冻结小型导出面。
- **B**：04a 只导出原始 `[]byte`/frame，04b 自己再包一层请求/响应类型。
- **推荐 A**。理由：避免 04b 重复实现长度、CRC、异常、边界校验；`Do` 与便捷方法是 04b 的自然输入；异常类型可让 04b 把“对应点 bad”映射到具体批次。影响：04a 的 API 需要经过本计划评审后保持稳定；04b 不得要求改签名，若确需扩展按新计划评审。

### 4.7 异常码分类：01/02/03 → 4001；其余 → 5044 **[用户拍板]**

- **A（推荐）**：01/02/03 = `ExceptionClassRejected`（4001）；04/05/06/08/0A/0B/未知 = `ExceptionClassInternal`（5044）。
- **B**：只有 01/02/03 与 04 明确分类；05/06/08/0A/0B/未知作为“未分类异常”，由 04b/09 另行决定。
- **推荐 A**。理由：`REQ-INVOKE-05` 只给“参数非法→4001 / 设备内部错误→5044”两类；未知异常若不归 5044 会落到 4001 兜底，语义更差。0B 虽是“目标无响应”，仍属有效异常响应，归 5044。影响：05（长操作 ACK）在同步引擎中会被当作失败；若未来支持长操作，需新 ticket。若用户认为 0B 更像 `ErrDeviceNoResponse`，可在 v2 调整，但最终 code 仍是 5044。

### 4.8 PDU 导出面：具体 sealed 类型 vs 通用接口/反射 **[工程决策]**

- **A（推荐）**：具体请求/响应结构体 + sealed `Request`/`Response` 接口 + `Encode/Decode` 函数。
- **B**：完全泛化的 `PDU interface{ MarshalBinary() }` + 注册表，允许外部功能码扩展。
- **推荐 A**。理由：04a 只需 03/04/06/16；具体类型让 04b 的类型断言/字段访问简单；sealed 防止外部实现绕过校验。影响：新增功能码需要改 `pdu` 包（新 ticket），符合“不要为未需求的功能码做插件化”的原则。

### 4.9 错误映射位置：04a 分层分类 vs 全部下沉 04b **[用户拍板]**

- **A（推荐）**：`pdu`/`framing` 报协议错误；根包 `modbus` 映射 I/O → `ErrLinkDown`/`ErrDeviceNoResponse`、异常 → `ErrDeviceRejected`/`ErrDeviceInternal`；04b 只做 Read/Write 语义映射。
- **B**：04a 只返回原始错误，所有哨兵映射由 04b 完成。
- **推荐 A**。理由：ticket 明确要求“坏帧归为协议错误”；04a 是最接近字节的一层，能可靠区分超时/EOF/坏 CRC/异常；04b 的映射表因此是机械的。影响：04a 的 `ExceptionError` 与 `IsProtocolError` 成为 04b 的稳定输入；09 仍拥有最终 code 表。

### 4.10 RTU-over-TCP 细节：裸 RTU vs 额外封装/帧间静默 **[工程决策]**

- **A（推荐）**：TCP 流上直接跑 RTU ADU；无 MBAP；CRC 不变；`DialTCP` + `NewRTU()`；请求严格串行；不额外插帧间静默。
- **B**：为 RTU-over-TCP 定义独立封装（例如加长度/事务头），或在客户端插入固定帧间延迟。
- **推荐 A**。理由：现场“串口服务器”通常就是裸 RTU 透传；B 不是标准 Modbus，且固定延迟需要新的时间数值/ASSUMED。影响：若现场网关要求 3.5 字符/自定义封装，20 只记录假设与配置验证；需要代码时另开 ticket，不在 20 的 config/testdata diff 内实现；04a 不预埋。

### 4.11 unit id 0：04a 原样传递 vs 04a 拒绝 **[工程决策]**

- **A（推荐）**：04a 原样传递 unit 0；04b/装配按传输校验：RTU 0=广播（需要响应的读/写应拒绝），TCP unit 0 可作为合法标识。
- **B**：仅 RTU 在 04a 拒绝 unit 0，TCP 原样传递。
- **C**：04a 一律拒绝（旧方案，已删除）。
- **推荐 A**。理由：unit 0 的语义依赖传输与设备；04a 只是字节层，不应把 RTU 广播语义强加给 TCP；04b 有链路/设备上下文，能给出明确诊断。影响：04a 不定义广播专用错误；04b 必须校验；测试只验证 unit 0 原样编码/发送。

### 4.12 并发策略：Client 内部串行 vs 多请求在途 **[工程决策]**

- **A（推荐）**：一个 `Client` 同时只允许一个在途交换（互斥）；调用方可并发调用，但实际串行。
- **B**：MBAP 允许多个在途请求，按事务号分发响应。
- **推荐 A**。理由：RTU 物理上不支持并发；TCP 并发会显著增加响应分发/超时清理复杂度，且 04b 的验收是“单从站超时后继续其他从站”，不是“同时多帧”。影响：04b 的并发断言应理解为“各设备各自有截止时间、超时不无限阻塞后续设备”，而不是同一 TCP 连接上真正并行；若需要真并行，04b 可为不同设备建多个 `Client`/连接，或在后续 ticket 扩展。

### 4.13 日志/可观测性：04a 不打日志 vs 注入 logger **[工程决策]**

- **A（推荐）**：04a 只返回带上下文的错误，不 import `log/slog`，不打印 PDU/寄存器。
- **B**：`NewClient` 接收 `*slog.Logger`，记录每次请求/响应摘要。
- **推荐 A**。理由：避免库层日志策略与脱敏责任；04b/18 决定指标与日志字段；减少测试噪声。影响：调试依赖错误文本与 04b/18 的观测；若需要帧级排障，可在后续以显式调试开关加入，不默认打印 payload。

## 9. 风险、假设与缺口台账

### 9.1 风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| RTU 长度推断/byteCount 越界错误 | 分片/粘包、坏帧误判、错误内存分配 | 先校验 qty/byteCount 上界与偶数；golden ADU + 分片/粘包测试；所有 RTU 解码错误带 `ErrUnrecoverable` |
| CRC 字节序错误 | 对端全部拒绝 | 固定 CRC 向量 + 线上低字节断言 |
| 假时钟与真实 socket deadline 混用 | 测试不确定或误报 | 脚本化 `Conn` 断言绝对 deadline 透传；真实 loopback 用 `realclock` 或零 deadline，不做紧时序断言 |
| `context.AfterFunc` 与清空 deadline 竞态 | 偶发过期 deadline/读失败 | 显式 done channel：`if !stop() { <-done }` 后再清空；`-race` + 取消测试 |
| 在途 `Do` 与 `Close` 的互斥/阻塞 | Close 卡住或无法解除阻塞 | Close 不取交换锁，`sync.Once` + `atomic.Bool` + 直接关 Conn；在途 Do 返回 `ErrClosed`；专项测试 |
| MBAP 可恢复错误被误标不可恢复（或相反） | 不必要重建或错误复用错位流 | §3.4 明确 len/截断 vs 完整 ADU 的区分；`TestMBAPRecoverableErrorKeepsStreamAligned`、`TestMBAPInvalidLengthIsUnrecoverable` |
| RTU 任何解码错误/超时后迟到响应污染下一次交换 | 04b 读到错误帧 | 04a 严格串行且 RTU 错误带 `ErrUnrecoverable`；04b 在任何 `ErrUnrecoverable` 或超时后重建 `Conn`/`Client`（写入交接） |
| 04a 范围蔓延到 04b | 返工、评审困难 | §1.3 非目标；`Driver`/批量/质量/链路状态明确划走 |
| `modbustest` 被生产包误 import | 违反依赖边界/二进制膨胀 | test-support only；`go list -deps` 断言生产闭包不含 `modbustest`（不加 `|| true`）；代码评审 |
| 05/06/08/0A/0B/00/未知异常分类与规范字面不完全一致 | 写路径 code 误判 | §4.7 显式拍板；保留原始异常码，09 可再判定；读路径按成功样本决定 Partial/Failed |
| 串口 opener 无人承接 | 生产 `modbus-rtu` 不可用 | §4.16 推荐 A：另开 `04c-serial-opener`；04b 的 `modbus-rtu` 在 04c 前阻塞；20 只做实物验证 |
| 新增依赖影响静态构建 | arm64/verify-static 失败 | §4.2 推荐零新增；若选 B 重新跑双架构构建并记录 |
| 真实 TCP 连接在测试中挂起 | CI 超时 | 测试用 channel/Close 释放；仅失败保护使用短 `time.After` |

### 9.2 假设

- Modbus 功能码/数量上限/异常码/CRC-16/MODBUS 为协议标准事实，不属于硬件 ASSUMED；ASSUMED 仅涉及现场网关/串口行为。
- `Conn.SetDeadline` 的语义与 `net.Conn` 一致；未来串口实现（04c/04b）必须提供同等语义。
- `context.AfterFunc` 在 Go 1.27 可用；它只做取消传播，不引入业务计时器；`stop()` 返回 false 时必须用 done channel 等待回调。
- `time.Time{}` 可作为“清空 deadline”的零值；测试不依赖清空后的真实计时。
- `Client` 只接收绝对 deadline（内核/04b 用注入 Clock 计算），并用同一 Clock 判断是否过期；不在 Client 内做 `Now().Add(timeout)`。
- `errors.Join` 的多错误语义可同时满足 `pdu.ErrProtocol`、`interfaces.ErrDeviceNoResponse` 与 `framing.ErrUnrecoverable`；错误文本不作为断言依据。
- 串口 opener 由 `04c-serial-opener`（推荐）或 04b 实现；20 只做实物联调验证（diff 只允许 config/testdata）。RTU-over-TCP 网关帧间时序与现场波特率/校验属于实物验证。

### 9.3 缺口台账需要登记的新 ASSUMED

**已获用户批准（2026-11-23）**，新增一条（随 §4.10 推荐案）：

| ID | 项 | 当前取值（ASSUMED） | 依据 / 假设 | 需向客户索取 | 影响 |
|---|---|---|---|---|---|
| C10 | RTU-over-TCP 网关帧间时序 | 网关接受连续的请求-响应，无需额外 3.5 字符静默；客户端严格串行发送 | 常见串口服务器透传行为；无实物 | 现场网关型号、手册、是否要求帧间延迟 | 04a 的节奏控制；20 实物联调与可能的配置项 |

- 不新增代码常量；若将来加入帧间延迟，必须先把数值登记到台账并由配置驱动。
- C10 只描述网关节奏假设，**不替代** `ErrUnrecoverable` 的关闭/重建策略；它与 `04c-serial-opener`/网关型号、20 实物验证关联。

- 20 只做实物验证，不承接 opener 代码；其 diff 只允许 config/testdata。
