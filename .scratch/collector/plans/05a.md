### 0.3 B1–B6 修正设计摘要（可直接实现）

- **B1 LWT 观测**：L2 不再用普通订阅者断言 retain。原因：mochi 对 MQTT 3.1.1 转发时强制 `out.FixedHeader.Retain=false`（`server.go` 约 1024–1035），且 `broker_disconnect` 会踢掉普通订阅者。改为：
  1. 触发 `broker_disconnect`；
  2. 读 `GET /_sim/captured`；
  3. 找 LWT topic，断言 `topic`、`payload` 字节、`qos`、`retain`（capture 保留原始 `pk.FixedHeader`）；依据 `SIM-CAPTURE-01`。
  L1 仍用假 transport 断言 `SetBinaryWill` 参数。L2-03/L2-08 按此改写。
- **B2 Close 优雅**：`transport.Close()` 使用 paho `Disconnect(disconnectQuiesce=250ms)` 并等待返回；不再使用 `Disconnect(0)`。L2-04 以 `-count=20` 验证 capture 中无 LWT；若仍偶发，升级为等待 paho 的 Disconnect 完成信号/改用显式 DISCONNECT 包，而不是退回 0。
- **B3 在途 Publish/Close 错误**：统一优先级 `closed > transport 不可用 > 消息形状 > 其他`。`token.Done` 后：
  1. 通道 closed → `ErrClosed`；
  2. `transport.IsConnected()==false` 或 token error 是 paho `ErrNotConnected` → `ErrNotConnected`（覆盖在途 generic “connection lost before Publish completed”）；
  3. ctx 已取消 → `ctx.Err()`；
  4. 其他错误 `%w` 包装。
  断线 + QoS2 返回 `ErrNotConnected`；传输可用 + QoS2 才返回 `ErrUnsupported`。L1-15/L1-18、L2-10 覆盖。
- **B4 Subscription 竞态**：
  - `deliver`：`sendMu.RLock()` → 复查 `done` → 持 RLock 发送（含 250 ms 上限）→ `RUnlock`；
  - `Close`：`close(done)` → 从父表移除（短暂锁、释放）→ `sendMu.Lock()` → `close(ch)` → `Unlock`。
  这样 Close 关 `ch` 时必须等所有 sender 释放 RLock；`done` 先解除阻塞 sender。L1-12 用并发阻塞 deliver + Close/Channel.Close `-race -count=20`。
- **B5 Connect 取消清理**：`Dial(ctx)` 在 ctx 取消后：
  1. 启动 cleanup goroutine；
  2. 等 `ConnectToken.Done()` 或 `Clock.NewTimer(connectTimeout)`；
  3. token 成功 → `client.Disconnect(250ms)`，确保 broker 侧连接关闭；
  4. 失败/超时 → 记录并丢弃；
  5. `cleanupWG` 计入 `Close` 的等待，最坏 `connectTimeout + 250ms`。
  L2-11 用 silent-CONNACK listener + 短测试 connectTimeout 验证连接被关闭、对端无残留。
- **B6 TLS 零值**：仅当 `Enabled=false` 且 (`CAFile != ""` 或 `InsecureSkipVerify == true`) 时报错；`Enabled=false` + `CAFile=""` + `InsecureSkipVerify=false` 必须成功。L1-17 覆盖零值成功、非零失败、Enabled=true 构造、scheme 白名单/规范化。

### 4.3 连接生命周期状态机

状态：

- `closed`：终态；由 `Close` 设置。
- `connected`：当前 `transport != nil` 且 paho 连接可用。
- `connecting`：`run` 正在 dial/等待 CONNACK。
- `waiting`：退避 timer 等待下一次尝试。

`New` 的行为：

1. 完成 §4.2 的全部校验；
2. 构造 `Channel`，初始 `Status{Connected:false, LastError:"", ChangedAt: clock.Now()}`；
3. 启动唯一 `run` goroutine；
4. **不等待首次连接**，立即返回。理由：边缘设备可能在云端不可达时启动；REQ-CACHE-01/02 要求断线期间仍能运行并把事件交给缓存层；若 `New` 阻塞/失败，进程无法进入采集循环。

`run` 的主循环：

```text
attempt = 0
loop:
  if closed: return
  tr, err := dialer.Dial(connectCtx, cfg)   // Dial 内部负责 B5 的取消清理
  if err:
     setStatus(false, err)
     log warn(attempt, backoff)
     delay = backoff(attempt)
     sleep via Clock.NewTimer(delay), select closed
     attempt++
     continue
  attempt = 0
  subscribeRegistered(tr)          // 首轮 SUBACK；失败的 filter 进入重试集
  setStatus(true, "")              // I1：Connected 只在首轮订阅尝试完成后置 true
  select:
    case err := <-tr.Lost():       // paho OnConnectionLost
       setStatus(false, err); tr.Close()
    case <-subRetryCh:             // I8：连接存续期间重试失败 filter；无失败时为 nil
       retryFailedSubscriptions(tr)
    case <-closedCh:
       tr.Close(); return
```

要点：

- 连接成功后 `attempt` 归零；若连接立刻又断，下一次退避从 `min` 开始（flapping 的已知代价，见 §10）。
- **I1**：`Connected=true` 表示“transport 已连接且首轮重订阅已尝试完成”，不表示所有 SUBACK 都成功。SUBACK 失败的 filter 进入 `failedSubs` 集，由 `subscribeRetry=5s` 的 Clock timer 在连接存续期间重试；成功后移出集合。这样 L2 等待 `Connected=true` 后注入下行不会落在“首轮 SUBSCRIBE 还没发出”的窗口。动态 `Subscribe` 在已连接时仍等待本次 SUBACK；在未连接时按 Q4 登记并等待下一轮。
  - `subRetryCh` 仅在 `failedSubs` 非空时指向当前 timer 的 `C()`；为空时为 `nil`，使 `select` 不会空转。重试成功/连接丢失时 `Stop` 并置 nil。
- `dialer.Dial` 接收 `context.Context`；`Close` 取消该 ctx，避免 `Close` 被一次网络 dial 拖住。
- **B5 取消清理**：paho `Connect()` 在后台 goroutine 执行，ctx 取消时可能已经连上并启动 comms workers。适配层不能只丢弃引用；在 ctx 取消后启动一个有界清理 goroutine：
  1. `select { <-token.Done(), <-Clock.NewTimer(connectTimeout).C() }`；
  2. 若 token 成功（连接晚于取消建立），调用 `client.Disconnect(disconnectQuiesce=250ms)`，确保 broker 侧连接关闭且不留下持续 LWT；
  3. 若 token 失败或清理超时，记录并丢弃；paho 自身的 ConnectTimeout 也会结束失败路径；
  4. 清理 goroutine 计入 `cleanupWG`，`Close` 等待 `runDone` + `cleanupWG`（最坏约 `connectTimeout + disconnectQuiesce`）。
- 每次连接尝试创建**新的 paho Client**（而不是复用同一个 client）。理由：`CleanSession=true` + 新 client 使本地 router/订阅状态与 broker 会话一起清空，重连后只由我们显式重订阅，不会残留已关闭 filter 的 route；也避免 paho 断线后状态机的复用细节。
- **I14 锁顺序**：`Channel.mu` 保护 `closed`、`transport`、`subs`、`status`；调用 `transport` 的网络方法时不持锁。`Close` 只在 `mu` 下快照订阅/transport，释放后逐个 `sub.Close()`，不得持父锁调用子关闭。
- `transport.Lost()` 由 `OnConnectionLost` 非阻塞投递（容量 1，重复丢失丢弃后来的 error）；同一回调先置 transport 的 `lost` 原子标志，再投递，供 B3 的在途 Publish 映射使用；回调不得阻塞 paho 的 goroutine。
- **I14/N10**：`SetConnectTimeout` 同时设置 paho 的 Dialer.Timeout（源码事实）；B5 只处理“Connect 成功晚于 ctx 取消”的泄漏，不把成功路径当成失败路径。

### 4.5 节点级 LWT（topic / retain / payload 精确值）

- topic：`topics.RenderTopic(WillTopicTemplate, vars)`。
  - 默认模板：`v1/{product_key}/$nodes/{node_id}/state`。
  - 非默认测试：`custom/v2/{product_key}/nodes/{node_id}/offline` + `product_key=farm-a` + `node_id=gateway-001` → `custom/v2/farm-a/nodes/gateway-001/offline`。
  - `$nodes` 是字面量，不是占位符；渲染器只识别 `{...}`。
- payload：固定结构，字段顺序 `online`、`node_id`：
  - `{"online":false,"node_id":"gateway-001"}`。
  - 用 `json.Encoder` + `SetEscapeHTML(false)` 生成，去掉末尾换行；测试逐字节断言。
  - **N3**：逐字节断言是比 `EXT-LWT-01` 的 JSON 语义更严格的实现选择；同时增加 JSON 语义断言（解码后 `online=false`、`node_id` 正确），避免未来字段顺序/空白变化被误判为协议错误。
  - 该 payload 只表示 MQTT 连接断开；设备级离线仍由 `device_offline` 事件与属性 `online` 表达（`REQ-EVENT-03`、`EXT-LWT-01`）。
- retain：**推荐 false**（Q5）。契约未定义“在线”消息；retain=true 而没有在线 counterpart 会让晚订阅者永久看到离线状态。若用户要求 retain=true，必须同时定义在线状态消息并走 spec-delta（Q5=B）。
- QoS：`Options.QoS`（默认 1；配置 V45 保证 0/1）。
- 构造时机：`New` 时渲染并校验；paho 在每次 CONNECT 时携带。`Close` 走 graceful DISCONNECT（非零 quiesce，见 §4.9），不触发 LWT；只有异常断开（broker 踢、网络断、KeepAlive 超时）才触发。
- **B1 观测方式**：L2 不用独立订阅者断言 retain。mochi 对 MQTT 3.1.1 普通订阅者转发时强制 `retain=false`，且 `broker_disconnect` 会踢掉独立订阅者；改用 `GET /_sim/captured` 的 inline capture，它保留原始 `pk.FixedHeader.Retain/Qos` 与 payload，精确断言 topic/retain/QoS/payload（`SIM-CAPTURE-01`）。
- **I6 后果**：LWT 绑定到 CONNECT 的 client id；同 client id 的 takeover 会让 broker 为旧连接发 LWT（mochi `server.go` 的 takeover/cleanup 路径）。在 Q5=A（retain=false、无在线消息）下：
  - takeover 可能让云端短暂/持续看到“旧连接离线”的 LWT，而**没有**由本服务发布的在线恢复消息；
  - LWT 只能作为“连接断开”的 best-effort 提示，**不得**被云端当作在线状态对账的唯一来源；
  - 设备级在线仍应通过属性 `online` 与 `device_offline`/`device_online` 事件恢复。若客户要求可靠的节点在线状态，选择 Q5=B（retain=true + 在线消息）并先完成 spec-delta。
- 测试使用唯一 client id，避免 takeover 串扰；若专门测 takeover，必须显式断言旧连接的 LWT 与新连接的在线恢复策略（Q5 决策）。

### 4.6 重连退避、抖动、重订阅与并发

退避：

- `min`/`max` 来自 `northbound.mqtt.reconnect.min_backoff_s`/`max_backoff_s`（默认 1 s / 30 s）。
- `base(n) = min * 2^n`，封顶 `max`；`n` 从 0 开始，连接成功后归零。
- 确定性抖动：
  - `jitter(n)` 由 `fnv64a(clientID + "\x00" + strconv.Itoa(n))` 映射到 `[0,1)`；
  - `delay = base/2 + jitter*base/2`，再 clamp 到 `[min, max]`；
  - 这样首次重试为 `min`，之后在 `[min, 2min]`、`[2min, 4min]`… 内抖动，且永不超过 `max`。
  - 不引入 `math/rand` 全局状态；同一节点、同一 attempt 的延迟可复现，避免整批边缘设备同时重连。
- 实现使用 `interfaces.Clock.NewTimer(delay)` + `select { timer.C(), closedCh }`；不使用 `Clock.Sleep`（Close 无法打断）。退出前 `timer.Stop()`。
- 测试用同包 unexported `jitterFunc` 注入固定 0 / 0.5 / 0.999，断言精确 delay；生产用 FNV 版本，测试其范围/封顶/确定性。

重订阅：

- `Channel` 维护 `subs map[string]*subscription`（一个 filter 一个订阅；重复 `Subscribe` 返回错误，见 §4.8）。
- 连接成功后，`subscribeRegistered(tr)` 对每个已登记 filter 调 `transport.Subscribe(ctx, filter, Options.QoS, sub.deliver)`，等待 SUBACK。
  - paho 的 `SubscribeToken.Result()[filter] == 0x80` 表示 broker 拒绝；paho 不一定设置 token error，必须显式检查。
  - 单条 SUBACK 失败只更新 `Status.LastError` 并记日志；不撕连接。
  - **I8 重试**：失败的 filter 进入 `failedSubs`；连接存续期间用 `subscribeRetry=5s` 的 `Clock.NewTimer` 重试（`retryFailedSubscriptions`），成功后移出并 stop timer；连接丢失时清空/停止。这样长期稳定连接下不会永久失效，也不再“只能等下一次重连”。
  - `Subscribe` 与 `subscribeRegistered`/`retryFailedSubscriptions` 用一个 `subOpMu` 串行化 SUBACK 操作，避免同一 filter 被并发 SUBSCRIBE 两次。
- 连接丢失后，旧 transport 丢弃；新 transport 重新订阅全部 filter；旧订阅对象的 `C()` 不关闭（它们跨连接存活），继续接收新连接的消息。
- `Subscription.Close()` 只做本地注销/关闭通道；不发送 UNSUBSCRIBE（v0.1 取舍，见 §4.8）。新连接不再重订阅已关闭的 filter。

并发：

- `mu` 保护状态；`subOpMu` 串行 SUBACK；`subscription.sendMu` 保护“投递 vs 关闭”的竞态。
- `Publish` 只快照 `transport` 指针，不持锁等待；`Close` 可并发关闭 transport，paho 会把在途操作返回错误。
- `Status()` 加锁复制，不返回内部引用。

### 4.7 Publish 语义（断线快速失败、typed error、不阻塞、不 panic）

**统一错误优先级（B3）**：`closed` > transport 不可用 > 消息形状 > 其他。理由：冻结注释要求“传输不可用时必须返回 `ErrNotConnected`/`ErrClosed`”，调用方（16a/16b）靠它分类断线；因此在断线时，即使消息 QoS/topic 也非法，也返回 `ErrNotConnected`，而不是 `ErrUnsupported`/plain invalid。消息形状错误只在传输可用时返回。

顺序：

1. `closed` → `fmt.Errorf("mqtt channel: %w", interfaces.ErrClosed)`（终态优先）。
2. 快照 `transport`；为 nil、`transport.IsConnected()==false` 或 transport 的 `lost` 原子标志已置位 → **立即** `fmt.Errorf("mqtt channel: publish %q: %w", topic, interfaces.ErrNotConnected)`。不等待重连、不排队、不 sleep。
3. `msg.QoS > 1` → `fmt.Errorf("mqtt channel: qos %d: %w", msg.QoS, interfaces.ErrUnsupported)`。
4. topic 校验（非空、无 wildcard、无 NUL、UTF-8、≤65535、不以 `$SYS/`、`$share/`、`$queue/` 开头）→ plain error。
5. 复制 `msg.Payload`（paho 可能异步写/重试；调用方可在返回后复用缓冲区）。
6. 调 `transport.Publish(ctx, msg)`：
   - paho 适配层先检查 `client.IsConnected()`；未连接直接映射为 `interfaces.ErrNotConnected`；
   - 已连接时调用 paho `Publish`，然后 `select { <-token.Done(), <-ctx.Done(), <-publishTimer.C() }`；
   - QoS0 在 paho 完成写队列/写出后返回；QoS1 在 PUBACK 后返回；
   - `ctx` 为 nil 时使用 `context.Background()`；不使用 `context.WithTimeout`；
   - `publishTimer` 是 `publishWait=10s` 的 `Clock.NewTimer`（I15），保证无 ctx 的 QoS1 不会无限等待假死连接；
   - **token 完成后的映射**（B3）：
     1. 若通道已 `closed` → `ErrClosed`；
     2. 否则若 transport 的 `lost` 原子标志已置位（`OnConnectionLost` 置位，避免只看 paho status 的更新竞态）、`transport.IsConnected()==false`、或 token error 是 paho `ErrNotConnected` → `ErrNotConnected`（覆盖 paho 断线时给在途 token 的 generic “connection lost before Publish completed” 错误）；
     3. 否则若 `ctx.Err()!=nil` → `ctx.Err()`（`%w`）；
     4. 否则其他错误原样 `%w` 包装（保留网络错误细节，便于日志）。
7. 不因单次 Publish 失败改写 `Status`；连接丢失由 `Lost()` 回调统一更新。若错误是 `ErrNotConnected` 且状态仍显示 Connected，适配层可调用一次 `markDisconnected`（只在状态翻转时更新 `ChangedAt`），避免状态长期滞后。

“不阻塞”的口径（I15）：

- **断线时**：状态检查 + paho `Publish` 的 `ErrNotConnected` 立即返回（本地临时观测约 54 µs，非仓库基准）；不等待重连。
- **已连接但 broker 不 ACK/假死时**：
  - paho `Publish` 调用本身在 outbound 队列满时最多等待 `writeTimeout=5s`；
  - token 等待 PUBACK 最多等待 `publishWait=10s`；
  - 调用方 `ctx` 可随时提前取消；
  - 因此无 ctx 的 QoS1 最坏约 `writeTimeout + publishWait`（≤15 s），之后返回超时错误。这是“可靠发布”与“有界阻塞”的明确边界；05b/16 应传 ctx。
- 不 panic：所有错误路径返回 error；`ctx` 为 nil、通道已关闭、并发 Publish/Close 都有测试。
- 断线 + QoS2 的优先级用例必须断言 `ErrNotConnected`（不是 `ErrUnsupported`）；传输可用 + QoS2 才断言 `ErrUnsupported`。

### 4.8 Subscribe / Subscription / 背压 / 关闭语义

`Subscribe(ctx, filter)`：

1. `closed` → `ErrClosed`。
2. `topics.ValidateFilter(filter)`；非法 → plain error；`ctx` 已取消 → `ctx.Err()`（`%w`），不登记。
3. 重复 filter → 返回错误（一个 filter 一个订阅；避免同一 filter 双订阅造成重复投递/重复 SUBSCRIBE）。调用方应合并自己的 filter 集。
4. 创建 `subscription`：`ch := make(chan interfaces.Message, subscribeBuffer)`（建议 16）、`done chan struct{}`、`sync.Once`、`sendMu sync.RWMutex`；登记到 `subs`。
5. 若当前已连接：在 `subOpMu` 下调用 `transport.Subscribe(ctx, filter, Options.QoS, sub.deliver)`；失败则注销/关闭并返回错误。
6. 若未连接：登记后立即返回订阅对象；连接成功后由 `subscribeRegistered` 建立；SUBACK 失败通过 `Status.LastError`/日志暴露，不阻塞 `Subscribe`。
7. `ctx` 非 nil 时启动一个 watcher goroutine：`select { <-ctx.Done(): sub.Close(); <-sub.done: }`；ctx 为 `Background()` 时 `Done()==nil`，watcher 只等 `sub.done`，不会泄漏。

`Subscription`：

- `C()` 返回只读通道；消费者应用 `msg, ok := <-C()` 判断通道已关闭。
- `Close()` 幂等（**B4 修复后的顺序**）：
  1. `once.Do(close(done))` 先解除阻塞的投递；
  2. 从父 `subs` 删除（短暂持父锁，释放后再做下一步）；
  3. `sendMu.Lock()`；`close(ch)`；`sendMu.Unlock()`；
  4. 返回 nil。
- **B4 竞态证明**：`deliver` 在 `sendMu.RLock()` 持有期间完成 `done` 复查与 send；`Close` 必须拿到 `sendMu.Lock()` 才能 `close(ch)`，因此不可能出现“deliver 已通过 done 检查、Close 随后关 ch、deliver 再发送”的窗口。`close(done)` 会先解除阻塞的 send，使 Close 能拿到写锁。测试用并发阻塞 deliver + Close/Channel.Close 压测。
- 不发送 UNSUBSCRIBE：本地关闭即可满足“关闭后不再投递”；broker 可能继续发送到同一 filter，但 `deliver` 看到 `done` 会丢弃。原因是避免 `Close` 因网络往返而阻塞；05b 的 filter 数量很小，额外流量可接受。若未来需要降低 broker 流量，再单独评审。
- 通道 `Close()` 会关闭所有订阅通道；**I14**：父 `mu` 下只快照订阅列表，释放后逐个 `sub.Close()`。

投递/背压（I7 部分采纳，Q9=A'）：

- paho 的 router 回调调用 `sub.deliver(msg)`；`deliver`：
  1. 复制 payload；
  2. `sendMu.RLock()`；
  3. 非阻塞复查 `done`（`select { <-done: RUnlock; return; default: }`）；
  4. 先做一次非阻塞 `case ch <- msg`；若缓冲已满，才创建 `deliveryBlockTimeout=250ms` 的 `Clock.NewTimer`，再做有界 select：`case ch <- msg` / `case <-done` / `case <-timer.C()`；
  5. `timer.Stop()`；`RUnlock`；
  6. 若退出原因是 timeout，在 **RUnlock 之后**记录 `subscription_overflow` 并 `sub.Close()`（不能在持有 RLock 时调 Close，否则自锁）；消费者看到通道关闭。
- 正常慢消费者可在 250 ms 内被读取，消息不丢；超时才 overflow 关闭，**不静默丢弃、不无限阻塞**。这样 paho router 的最坏停顿被限制在 250 ms，远小于 `PingTimeout=10s`，避免 I7 的“停读 PINGRESP → 判定连接丢失 → 抖动/QoS1 重投”风险。
- paho 的 `AutoAckDisabled=false`（默认）：handler 返回后自动 ACK；有界阻塞即背压。
- **I16 入站映射**：paho 消息 → `interfaces.Message`：
  - `Topic = msg.Topic()`；
  - `Payload = append([]byte(nil), msg.Payload()...)`；
  - `QoS = interfaces.QoS(msg.QoS())`，只接受 0/1；若 broker 仍送 QoS2，丢弃并 warn（正常不会出现，因为订阅 QoS≤1 会降级）；
  - `Retain = msg.Retained()`；
  - `DedupKey` 留空，由 05b/11 决定。
- 入站主题/匹配由 paho router 的订阅回调决定；通道不再做第二套主题匹配，避免重复投递。

### 4.9 Close 语义、幂等与错误优先级

- `Close()`（**B2/B5/I14**）：
  1. `mu` 下若已 closed，跳到等待完成；否则置 closed、`close(closedCh)`、**快照**当前 transport 与订阅列表；释放 `mu`；
  2. 取消连接 ctx（打断 dial/SUBACK）；
  3. 逐个 `sub.Close()`（幂等；不得持有父 `mu`）；
  4. 若 transport 已连接，调 `transport.Close()`：paho `Disconnect(disconnectQuiesce=250ms)`，并等待这次调用返回；若仍在 connecting，走 B5 的有界清理（见 §4.3），不在 connecting 状态直接 `Disconnect(0)`；
  5. 等待 `runDone` 与 `cleanupWG`（每次 `Close` 都等待同一完成信号），然后返回；
  6. 设置 `Status{Connected:false, LastError:"channel closed", ChangedAt: clock.Now()}`。
- **B2**：不使用 `Disconnect(0)` 作为 graceful 路径。paho v1.5.1 在 quiesce=0 时 DISCONNECT 与 stopCommsWorkers 竞争，偶发未写出 DISCONNECT 而触发 LWT（评审实测 20 次 `Disconnect(0)` 出现 1 次；`1/50/250ms` 各 20 次均 0 次）。用非零 `disconnectQuiesce=250ms`（软件常量）并等待其返回。L2-04 以 `-count=20` 重复验证关闭无 LWT。
- 幂等：所有 `Close` 调用都返回 nil（transport 关闭错误只记日志）；并发 `Close` 不会重复关闭/panic。
- **B3 错误优先级**：`closed` > `not connected` > 消息形状 > 其他。`Publish`/`Subscribe` 在 Close 后返回 `ErrClosed`；在途 Publish 在 token 完成后若观察到 closed 返回 `ErrClosed`，否则若 transport 不可用返回 `ErrNotConnected`。
- 在途 `Publish`：`Close` 关闭 transport 后，paho token 返回错误；`Publish` 按上一条优先级映射，不返回裸的 generic error；不等待调用方、不死锁。测试覆盖“在途断线”和“在途 Close”两类。
- **B5**：`Close` 可能等待一次正在进行的 `dial` 及其取消清理；生产由 `connectTimeout=10s` + `disconnectQuiesce=250ms` 封顶；L2 用 silent-CONNACK listener + 短测试超时验证取消后连接被关闭、对端/服务端无残留连接。

### 4.10 Topic 模板与 `internal/topics`

API：

```go
func Render(tmpl string, vars map[string]string) (string, error)
func RenderTopic(tmpl string, vars map[string]string) (string, error)
func RenderFilter(tmpl string, vars map[string]string) (string, error) // I9：替换值禁止 +/#，模板字面量允许
func ValidatePublishTopic(topic string) error
func ValidateFilter(filter string) error
```

规则：

- 占位符语法 `{name}`；`name` 非空，允许字母/数字/`_`/`.`；未知占位符、空 `{}`、不配对 `{`/`}` → error。
- `Render`：替换值原样使用；值必须 UTF-8、非空、无 NUL；用于 client id 等不需要 topic 语义的场景。
- `RenderTopic`：在 `Render` 基础上：
  - 替换值不得含 `/`、`+`、`#`、NUL（防止设备 SN 改变 topic 层级/注入通配符）；
  - 结果必须通过 `ValidatePublishTopic`：非空、UTF-8、≤65535 字节、无 `+`/`#`、无 NUL、无空 level（`//`、首尾 `/`）、不以 `$SYS/`、`$share/`、`$queue/` 开头（N5）。
- **`RenderFilter`（I9）**：用于 05b 的下行 filter：
  - 替换值不得含 `+`、`#`、NUL（值不能注入通配符）；
  - 模板字面量**允许** `+`/`#`（例如 `v1/{product_key}/+/service/invoke`），结果必须通过 `ValidateFilter`；
  - 替换值中的 `/` 允许吗？不允许：filter 的层级应由模板决定，值不得改写层级；与 `RenderTopic` 一致，值禁止 `/`。
- `ValidateFilter`：非空、UTF-8、≤65535；`#` 只能作为最后一级且独占该级；`+` 必须独占一级；无 NUL；拒绝空 level（`//`、首尾 `/`）；拒绝 `$share/`、`$queue/`、`$SYS`（N5：v0.1 不使用共享订阅/系统主题）。
- 模板来源是配置/`Options`，代码中只有默认值文档，不把 `v1/...` 或 `$nodes` 写进通道逻辑。测试用非默认前缀/`product_key` 证明。
- 占位符映射：
  - `product_key` → `ProductKey`
  - `device_sn` → 设备 SN（05b）
  - `node_id` / `node.id` → `NodeID`
  - `event_id` → 事件 ID（05b）
- client id 用 `Render`，publish topic/LWT 用 `RenderTopic`；05b 的 filter 用 `RenderFilter` + `ValidateFilter`，不再用裸 `Render`（I9 修复）。

### 4.11 状态、日志与凭据

- `Status()` 返回 `ChannelStatus` 的副本；`ChangedAt` 全部来自 `Clock.Now()`：
  - 构造：false/""/now；
  - 连接成功：**首轮 `subscribeRegistered` 尝试完成后** true/""/now（I1；不是 CONNACK 一返回就 true）；
  - 连接失败或丢失：false/脱敏后的错误文本/now；
  - 重订阅失败：保持 Connected=true，更新 LastError/ChangedAt（连接仍在，但订阅不完整）；`failedSubs` 由 `subscribeRetry` 重试；
  - Close：false/"channel closed"/now。
- 日志：注入 `*slog.Logger`；nil 时用 `io.Discard` 的 JSON logger（测试安静，不污染 stdout/stderr）。
  - 字段：`component=mqtt`、`event=connect|disconnect|reconnect_scheduled|subscribe|publish_failed|closed`、`broker`（去掉 userinfo）、`client_id`、`attempt`、`backoff_ms`、`reason`；不打印 username/password/token/payload。
  - `broker` 脱敏：`scheme://[REDACTED]@host`（有 userinfo 时）。
  - `Status.LastError` 与日志文本二次替换 `secrets`（Password、broker userinfo password）为 `[REDACTED]`。
  - paho v1.5.1 的全局 logger 默认是 NOOP；不打开 paho debug，避免绕过脱敏。
- `Secret` 类型实现 `String()`/`GoString()` 返回 `[REDACTED]`；测试用 `fmt.Sprintf("%#v", opts)` 断言不泄漏。

### 4.12 资源、goroutine 与生命周期

| 资源 | 数量/生命周期 | 关闭方式 |
|---|---|---|
| `run` goroutine | 每 Channel 1 个 | `Close` 关闭 `closedCh`；等待 `runDone` |
| paho client/transport | 每次连接尝试 1 个 | 成功：断线/Close 时 `Disconnect(250ms)` + `Close`；失败：丢弃；connecting 取消：B5 有界清理 |
| Connect 取消清理 goroutine | 每次取消的 connecting 最多 1 个 | 等待 token 或 `connectTimeout`；成功则 `Disconnect(250ms)`；计入 `cleanupWG`，`Close` 等待 |
| 退避 timer | 同时最多 1 个 | `Close` 取消 select；退出前 `Stop` |
| SUBACK 重试 timer | 连接存续期间最多 1 个 | 无失败 filter 时为 nil；成功/断线/Close 时 `Stop` |
| publish 等待 timer | 每次 Publish 最多 1 个 | token/ctx/timeout 任一路径后 `Stop` |
| delivery 背压 timer | 每次阻塞投递最多 1 个 | 发送/关闭/250 ms 超时后 `Stop` |
| subscription ctx watcher | 每个带有效 ctx 的订阅 1 个 | `sub.Close()`/Channel Close 关闭 `done` 使其退出 |
| 订阅消息缓冲 | 每订阅 `subscribeBuffer=16` 条 | Close 关闭通道；250 ms 满则 overflow 关闭 |
| paho 内部 goroutine | paho 管理 | 断线/Disconnect 后由 paho 停止；connecting 取消由 B5 清理 |

- 不 per-message 起 goroutine；不无界队列。
- `Publish` 不持 `mu` 等待网络；`Close` 不需要等所有调用方，只等 `run` 退出与 B5 清理。
- 测试用 `Close` 返回作为“run 已停止”的证据；不引入 `goleak` 依赖。L1 `-race -count=10/20` 覆盖并发；L2 单独 `-count=3`（见 §7.5）。

### 4.13 软件常量（不是硬件 ASSUMED）

| 常量 | 值 | 理由 |
|---|---|---|
| `connectTimeout` | 10 s | 约束首次 dial、B5 清理与 Close 最坏等待；paho 默认 30 s 太长；测试可 unexported 覆盖为 200–500 ms |
| `writeTimeout` | 5 s | 约束 paho outbound 入队等待 |
| `disconnectQuiesce` | 250 ms | B2：非零 quiesce，确保 DISCONNECT 写出；L2 `-count=20` 验证 |
| `publishWait` | 10 s | I15：无 ctx 的 QoS1 有界等待 PUBACK |
| `subscribeBuffer` | 16 | 有界背压；与服务调用突发量匹配 |
| `deliveryBlockTimeout` | 250 ms | I7：单次投递阻塞上限；超时则 overflow 关闭订阅，避免停读 PINGRESP |
| `subscribeRetry` | 5 s | I8：连接存续期间重试失败的 SUBACK |
| MQTT 最大 topic/字符串长度 | 65535 字节 | 协议限制 |
| MQTT KeepAlive 上限 | 65535 秒 | uint16 协议字段；>65535 构造错误（I10） |
| 退避抖动哈希 | FNV-1a | 确定性、无全局随机状态 |
| LWT retain | 推荐 false | 契约决策，见 Q5；不是硬件值 |

这些是软件安全边界，不写入 `docs/缺口台账.md` 的硬件 `ASSUMED` 表；若用户希望可配置，需新增配置键并走 spec-delta（Q13）。

### 5.3 推荐

**推荐 B：paho + `AutoReconnect=false` + 仓库内显式循环。**

理由：

1. 连接/重连/重订阅是我们必须验收的行为；显式循环让退避、状态、Subscribe 顺序都能用注入 Clock 和假 transport 做确定性 L1，不依赖 paho 内部真实定时器。
2. paho 负责协议正确性（CONNECT/CONNACK、QoS1 PUBACK、PINGREQ/PINGRESP、LWT、TLS），避免自研协议栈在 v0.10 范围内引入不可接受的风险。
3. 本地临时模块实测（2026-11-23）：
   - paho v1.5.1 在 `CGO_ENABLED=0 GOOS=linux GOARCH=arm64/amd64` 下均静态编译成功；
   - `AutoReconnect=false` + `ConnectRetry=false` 时，broker 踢掉连接后 `OnConnectionLost` 触发；断线时 `Publish` 约 54 µs 返回 `not Connected`（本地临时观测，非仓库基准）；同一 client 再次 `Connect` 成功，新建 client 也成功；
   - 对 mochi v2.7.9 实测 LWT：topic/payload/QoS/retain 与 CONNECT 的 will 完全一致（payload 逐字节），异常断开触发；源码核对 graceful DISCONNECT 会清空 Will（`server.go` 的 `cl.Properties.Will = Will{}` 分支）。v2 按 B2 用 `Disconnect(250ms)`，L2-04 用 capture `-count=20` 实测“无 LWT”。
4. A 的自动重连退避在 paho 内部，使用真实时间，无法用假时钟确定性测试，且 `ConnectRetry` 会引入内部 sleep；与 REQ-TIME-01 的精神和 L1 可测性冲突。
5. C 自研需要自己实现 QoS1 重传、会话、KeepAlive、LWT、TLS 边界，测试与维护成本远高于本 ticket；06b 的测试客户端只覆盖测试所需子集，不能当生产实现。
6. D 中 `natiu-mqtt` 是最有价值的备选（MIT、零依赖、3.1.1、可注入 `Nanotime`、context 友好），但它是低层库：需要自己实现读循环、KeepAlive 调度、QoS1 orchestration 与重连；作为 05a 的备选会增加实现面。`gomqtt` 维护停滞且依赖重；`paho.golang` 只支持 MQTT v5，不适配当前 3.1.1 链路。若用户因许可/依赖政策拒绝 paho，建议改用 natiu，并把本计划升级为 v2（工作量明显增加）。

## 6. 需要用户拍板的 A/B

> 推荐项加粗。未拍板前不进入实现。每项给出推荐、理由、影响面。

### 6.0 评审后新增的影响面摘要

- **B1**：LWT 的 L2 断言改走 `/_sim/captured`，因为普通订阅者看不到原始 retain，且会被 `broker_disconnect` 踢掉；L1 仍断言 `SetBinaryWill` 参数。
- **B2**：Close 用 `Disconnect(250ms)`；`Disconnect(0)` 不作为 graceful 路径，L2-04 需 `-count=20`。
- **B3**：在途 Publish/Close 的 typed error 统一优先级；paho 在途 token 的 generic 错误必须映射为 `ErrNotConnected`/`ErrClosed`。
- **B4**：Subscription 的 deliver/Close 用 `sendMu` 写锁关通道 + RLock 复查 `done`，补 panic 压测。
- **B5**：Connect 取消后不能只丢引用；成功晚于取消时必须 `Disconnect(250ms)`，并对清理 goroutine 计 `cleanupWG`。
- **B6**：`InsecureSkipVerify=false` 是零值，TLS 关闭时只有 `CAFile != ""` 或 `InsecureSkipVerify == true` 才报错。

### 6.1 一级决策

**Q1 客户端选型（字母与 §5 的候选一致）— 必须用户拍板**

- **B（推荐）**：paho v1.5.1 + `AutoReconnect=false` + 仓库显式循环。
- A：paho 自动重连，退避交给库。
- C：自研最小 MQTT 3.1.1 客户端。
- D：natiu-mqtt（MIT/零依赖，低层，需自写读循环/KeepAlive/重连）。
- 理由/影响：B 平衡成熟度与可测性；A 不可用假时钟确定性测退避；C 风险/成本最高；D 是 paho 被许可/依赖政策否决时的备选，需计划 v2。选 B 需要用户接受 EPL-2.0/EDL-1.0 与 x/net/x/sync/gorilla 升级；不接受则选 D，本计划重写。

**Q2 首次连接语义**

- **A（推荐）**：`New` 只校验并启动后台 `run`，不等待首次连接；断线时调用方立即得到 `ErrNotConnected`。
- B：`New` 同步连接，失败返回 error。
- 理由/影响：A 支持“云端不可达也要启动并缓存”；B 会让进程在断网时无法进入采集循环。A 要求 05b/16 正确处理启动初期的 `ErrNotConnected`。

**Q3 05a 是否接 `app`/`cmd` 的 `run` — 必须用户拍板**

- **A（推荐）**：不接线；05a 只提供 `New(Options)`，由 05b/07 装配；验收以包级测试 + 包级交叉编译为准。
- B：05a 就在 `run` 构造并启动通道。
- 理由/影响：目前没有消费者（适配器/缓存未就绪），接线会产生无用的连接和未关闭 goroutine；A 的验收在包级测试完成，B 会把 05b/16 的装配问题提前混入本 ticket。若用户要求 `run` 立即连 MQTT，需把 05b/16 的最小消费路径纳入本 ticket，范围扩大。A 还意味着 `make build-linux-*` 不会编译 paho，因此必须加 I4 的包级交叉编译门禁。

**Q4 首次连接前 `Subscribe` 的语义**

- **A（推荐）**：登记 filter 并返回 Subscription；连接成功后自动建立；SUBACK 失败通过 Status/日志暴露。
- B：未连接时 `Subscribe` 返回 `ErrNotConnected`，调用方自行重试。
- 理由/影响：A 允许启动时先注册下行 filter、后连上云；B 需要调用方实现重试并可能与通道的内部重连重复。A 要求调用方接受“已返回订阅但 SUBACK 尚未确认”的窗口。

### 6.2 LWT 与 Topic

**Q5 LWT retain 形态 — 必须用户拍板**

- **A（推荐）**：`retain=false`。严格按 `EXT-LWT-01` 只表达“连接断开”；不新增在线消息。
- B：`retain=true`，并在每次成功连接时向同一 topic 发布 `{"online":true,"node_id":"..."}`（retained）。这会新增契约未定义的在线状态消息，需先开 `spec-delta/lwt-online-state`，更新 `EXT-LWT-01` 后再实现。
- C：`retain=true` 但不发在线消息。**不推荐**：晚订阅者会永久看到离线。
- 理由/影响：A 最小、无需规范变更；B 对云端更友好但需要用户批准契约变更并等 spec-delta 合并；C 会产生错误状态语义。ticket 的“retain 精确断言”在 A/B 下都可测。
- **Q5=A 的明确后果（I6）**：同 client id 的 takeover 会让 broker 为旧连接发 LWT（mochi 行为）；由于 A 不发布在线恢复消息，云端可能在 takeover/网络分区后持续看到“离线”，直到后续属性/事件或人工处理。LWT 只能作为连接断开的 best-effort 提示，**不能**承担节点在线状态对账。若客户要求可靠在线状态，必须选 B + spec-delta；不能默认 A 可满足。

**Q6 LWT QoS 来源**

- **A（推荐）**：使用 `northbound.mqtt.qos`（默认 1）。
- B：LWT 固定 QoS1，忽略配置 qos。
- 理由/影响：A 与配置语义一致；若用户把 qos 设为 0，LWT 也降为 0（可能丢失）。B 更可靠但引入一个与配置不一致的隐式例外。

**Q7 Topic 模板归属**

- **A（推荐）**：新增 `internal/topics` 纯函数小包；05a 用于 LWT/client id，05b 用于上行/下行 topic 与 filter；API 包含 `RenderFilter`（I9）。
- B：渲染器放在 `internal/channels/mqtt`，05b 复用具体通道包（适配器→通道耦合）。
- C：适配器各自渲染，通道只接收已渲染的 LWT topic；05a 仍需渲染 client id/topic，容易重复。
- 理由/影响：A 让模板规则只有一个实现，避免 05b 重复/漂移；新增一个小包，不改变依赖方向，但需要更新 `docs/architecture.md`（I3）。B 破坏适配器与通道的解耦；C 会让 LWT/客户端 ID 的模板逻辑分散。`RenderFilter` 解决 I9 的值注入通配符问题。

**Q8 重连抖动**

- **A（推荐）**：确定性 equal jitter（FNV(clientID+attempt)），范围 `[base/2, base]` 并 clamp 到 `[min,max]`；无全局随机状态。
- B：纯指数退避，无抖动。
- C：`math/rand` 随机抖动，测试注入随机源。
- 理由/影响：A 避免整批节点同时重连，且测试可复现；B 简单但可能造成重连风暴；C 需要额外注入/测试设施。A 的退避永不小于 `min`，首次重试仍是 `min`。

### 6.3 运行时语义与工程

**Q9 订阅投递背压 — 必须用户拍板**

- **A'（推荐）**：每订阅 16 条有界缓冲；满时最多阻塞 `deliveryBlockTimeout=250ms`（`Clock.NewTimer`），期间消费者可读取；超时则记录 `subscription_overflow` 并 `Close` 订阅（消费者看到关闭），不静默丢弃、不无限阻塞。
- B：满时非阻塞丢弃并计数/日志。
- C：无界队列（不允许，违反有界内存）。
- 理由/影响：A' 保护下行服务调用不静默丢失，同时把 paho router 的最坏停顿限制在 250 ms，远小于 `PingTimeout=10s`，避免 I7 的“停读 PINGRESP → 判定连接丢失 → 重连/QoS1 重投”风险。B 简单但可能丢指令；C 违反有界内存。A' 仍要求 05b 的消费者不长期停读，否则订阅会被 overflow 关闭。

**Q10 Clock 注入与静态检查范围**

- **A（推荐）**：`internal/channels/mqtt` 注入 `interfaces.Clock` 用于 `Status.ChangedAt`、退避、SUBACK 重试、publish 等待上限、投递阻塞上限；把 `internal/channels` 加入 `scripts/check-time.sh` 的 roots，静态禁止直接 `time.*`/`context.WithTimeout`/`WithDeadline`（`time.Duration` 常量不受影响）。
- B：注入 Clock，但不扩大 check-time 范围。
- C：通道直接用真实时间（不注入 Clock）。
- 理由/影响：A 把 REQ-TIME-01/ADR-0003 的规则扩展到通道，防止未来回退；协议 KeepAlive 仍在 paho 内用真实时间（明确边界）。B 可测但无静态保障；C 与仓库时间纪律冲突。A 会改变 CI 检查范围（仅新增 `internal/channels`），需更新脚本注释/错误文案（评审已确认不误伤 `time.Duration`）。

**Q11 TLS scheme 处理**

- **A（推荐）**：`tls.enabled=true` 时把 `mqtt://`/`tcp://` 规范化为 `ssl://`；`tls.enabled=false` 时遇到任何 TLS scheme（`ssl`/`tls`/`mqtts`/`mqtt+ssl`/`tcps`）构造错误；`Enabled=false` 时只有 `CAFile==""` 且 `InsecureSkipVerify==false` 的零值合法（B6）；拒绝 ws/wss/unix/未知 scheme（I13）。
- B：要求运维直接写 `ssl://`，通道不改写；scheme 与 enabled 不一致时仍报错。
- C：忽略不一致，按 scheme 决定（可能静默明文）。
- 理由/影响：paho 的 `mqtt` scheme 不应用 TLSConfig（源码事实），A 避免“配置了 TLS 却明文连接”的高危错误；B 更显式但增加配置负担；C 不可接受。A 的零值处理必须按 B6，否则示例配置（无 tls 块）会被误拒。

**Q12 独立测试客户端复用 — 必须用户拍板**

- **A（推荐）**：把 06b 的独立 MQTT 3.1.1 测试客户端抽取为 `internal/testutil/mqttclient`（非 `_test.go`，仅测试 import），06b 与 05a 测试共用；06b 测试做机械 import 调整，行为不变。
- B：在 05a 测试中复制/另写一份最小客户端，不改 06b 测试。
- 理由/影响：A 避免 ~300 行重复，且证明测试依赖不进入生产闭包；会触碰 06b 的测试文件（只是重构，不改行为）。B 零 06b 改动但重复代码，后续两边漂移。A 需要在 `check-deps.sh` 断言 `internal/channels` 生产闭包不含 `internal/testutil`，并更新 `docs/traceability.md` 的 `SIM-SECURITY-01` 证据路径（I5）。
- **N1 更正**：06b 现有客户端没有 DISCONNECT；抽取时保持现有能力（CONNECT/SUBSCRIBE/PUBLISH QoS0/1/PUBACK/read/expectClosed）。只有 graceful close 测试确实需要主动 DISCONNECT 时，才补一个最小写包；不得把它当生产实现。

**Q13 配置校验一致性 — 必须用户拍板**

- **A（推荐）**：05a 只在通道构造器校验 `keepalive_s`/`reconnect`/TLS/模板；`config-check` 维持现状。`run` 在通道构造失败时返回清晰错误并退出。
- B：在 05a 同时给 `internal/config` 增加 V46/V47 规则（keepalive/reconnect），使 `config-check` 与 `run` 一致；需要更新 `rules.go`、`validate.go`、单测/golden，并可能触碰 `docs/contracts/config.md` 的规则分类（普通 feature 分支不得改 contracts）。
- 理由/影响：A 保持 ticket 范围，但用户必须接受“`config-check` 通过、`run` 可能因通道构造失败退出”的不一致；B 更一致但扩大 diff，且若要把新规则写入合同，需要 spec-delta。推荐 A，把 B 记为后续 ticket；不默认通过。

**Q14 重复 filter 的 `Subscribe`**

- **A（推荐）**：一个 filter 一个订阅；重复 `Subscribe` 返回错误。
- B：允许多个订阅对象共享同一 filter，向每个对象 fan-out。
- 理由/影响：A 简单、避免重复 SUBSCRIBE 与重复投递；B 提供更大灵活性但增加路由/关闭复杂度。05b 预期每个 filter 只订阅一次。

### 7.4 假时钟与真实时钟边界

- 假时钟覆盖：`Status.ChangedAt`、退避 timer、重连尝试顺序、SUBACK 重试 timer、publish 等待上限、delivery 250 ms 上限、Close 打断 timer。
- 真实时钟覆盖：paho 的连接/KeepAlive/PUBACK、真实 socket 断线、broker 保持期、`Disconnect(250ms)` 的 quiesce。
- 不尝试把 fakeclock 注入 paho；paho 的 KeepAlive/ConnectTimeout 是其协议实现的一部分。
- fakeclock 的“step, do not jump”文档要求：测试逐步 `Advance` 到下一次预期 dial，并等待假 dialer 记录；不要一次跳大时长。

### 7.5 race、重复与 goroutine 泄漏

## 10. 风险与回退

| 风险 | 影响 | 缓解/回退 |
|---|---|---|
| paho 许可/依赖政策不接受（EPL/EDL、x/net/x/sync） | 可能需要换客户端 | Q1=D natiu（MIT/零依赖），计划 v2；或自研（不推荐）。在实现前由用户拍板 |
| paho 显式重连状态机不如 AutoReconnect 成熟 | 重连回归 | 本地临时观测同 client/新 client 均可重连；L1 假 transport + L2 真实 broker 双覆盖；若发现 paho 状态机问题，改为每次连接新建 client（本计划已倾向新建） |
| **B1** L2 LWT 独立订阅者不可靠 | retain 断言空洞/订阅者被踢 | 改用 `/_sim/captured` inline capture 断言原始 retain/QoS/topic/payload；L1 断言 `SetBinaryWill` 参数 |
| **B2** `Disconnect(0)` 偶发 LWT | 优雅关闭误报离线 | 使用 `Disconnect(250ms)` 并等待；L2-04 `-count=20`；删除 `Disconnect(0)` 的 graceful 断言 |
| **B3** 在途 Publish generic error | 调用方无法 `errors.Is` 分类 | token 完成后按 closed → `IsConnectionOpen()==false`/paho ErrNotConnected → ctx → other 映射；L1/L2 在途断线/在途 Close 用例 |
| **B4** deliver/Close panic | 进程崩溃 | `sendMu` 写锁关 `ch`、RLock 下复查 `done` 并跨 send 持锁；`-race -count=20` 压测 |
| **B5** Connect 取消后 client 泄漏 | broker 认为在线/LWT | ctx 取消后有界清理：等 token，成功则 `Disconnect(250ms)`；`cleanupWG`；L2 silent-CONNACK 用例 |
| **B6** TLS 零值误判 | 所有非 TLS 配置被拒 | 只在 `Enabled=false` 且 `CAFile != ""` 或 `InsecureSkipVerify == true` 时报错；补零值成功用例 |
| **I7** 慢订阅者停读 PINGRESP | 连接抖动/QoS1 重投 | Q9=A'：250 ms 有界阻塞 + overflow 关闭；router 停顿远小于 PingTimeout=10s |
| **I8** SUBACK 失败永不重试 | filter 永久失效 | `subscribeRetry=5s` Clock timer 在连接存续期间重试失败集合 |
| **I15** 无 ctx QoS1 假死 | Publish 长阻塞 | `publishWait=10s` 上限；建议调用方传 ctx；最坏约 writeTimeout+publishWait |
| 配置校验缺口（keepalive/reconnect） | config-check 通过但 run 失败 | 构造器清晰报错；Q13=B 可后续补 V 规则；用户必须接受 Q13=A 的不一致 |
| L2 真实时钟测试抖动/flaky | CI 不稳定 | 临时端口、唯一 client id、有界轮询、较短退避；L1 覆盖确定性部分；L2 `-count=3`，时间敏感 `-count=1` |
| `go mod tidy` 升级 gorilla/websocket | 间接依赖 Diff | 锁定 paho v1.5.1；跑 06b 回归、`make verify-static` 双架构；license 记录 |
| 没有 app 接线 | 生产二进制暂不使用该通道 | 明确非目标；05b/07 装配；包级验收 + I4 包级交叉编译 |
| N4 D3 ClientID 漂移 | 台账与代码不一致 | 05a 以代码为准；PR/走读提示后续核对台账 |
| 04a plan 缺失 | 结构参考不足 | 已用 06b/02b；不阻断 |

回退：

- 代码层：删除 `internal/channels/mqtt`、`internal/topics`，回退 `go.mod`/`go.sum` 与 CI 脚本改动；不影响 06b 生产代码（仅测试设施重构需一并回退）。
- 若 Q12=A 的测试客户端抽取导致 06b 测试问题，回退该重构，改为 Q12=B 的局部副本，不阻塞通道实现。

## 11. 规范/合同影响判断

**推荐方案（各 Q 的推荐项，见 §6；Q1 的推荐是 B）不需要 spec-delta。**

- `REQ-SEAM-01`：通道只依赖 `interfaces`/`topics`/paho；内核不 import 具体实现；装配留给 05b/07。
- 文档影响（非 spec/contracts）：`docs/testing.md` 的 L2 真实时钟例外（I2）、`docs/architecture.md` 增加 `internal/topics`（I3）、`docs/traceability.md` 的 `EXT-LWT-01` covered / `EXT-TOPIC-01` 保持 planned(05b) / `SIM-SECURITY-01` 路径（I5）。这些都允许在 feature 分支修改；不得改 `docs/spec/**`、`docs/contracts/**`。
