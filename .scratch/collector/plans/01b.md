## 0. 01b 的增量边界

01a 已有并保留：

- `yaml.Load(..., WithKnownFields(), WithUniqueKeys())` 严格解析；空文档、多文档、重复键、类型错。
- 必填字段存在性；`Diagnostic{File,Line,Col,RuleID,Message}` 雏形；`Secret` 脱敏。
- `config-check` 只打印一行 `config ok: ...`；`Load(dir, WithEnv(...))`。

01b 新增：

1. 把 01a 已产生的结构/必填诊断纳入 **V01…V63 规则编号**，补全 `file:line:col`。
2. 新写 spec §2 的语义规则：唯一、引用完整、数值、互斥、端口，以及 ticket 点名的未知嵌套键、只读点位写入。
3. YAML 节点位置索引，使语义错误能落到具体键；跨文件引用错误落到**引用字段所在文件**。
4. `config-check` 的完整生效配置摘要（稳定 DTO、密码/Token 脱敏、broker userinfo 脱敏）。
5. `testdata/config/` golden corpus（每条规则一合法一非法 + 排序/聚合/跨文件用例）。

01b 不新增任何运行时行为；`run` 仍只加载 + 校验 + 骨架启动。

## 1. 规则目录

### 1.1 编号与来源口径

- 规则编号连续但不强求无空号：`V01–V07` 结构层，`V10–V16` 必填，`V20–V24` 唯一，`V30–V35` 引用，`V40–V45` 数值，`V50–V53` 枚举/互斥，`V60` 端口，`V61` 凭据，`V62–V63` 日志选项。
- **来源标记**：
  - `spec §2`：spec 明写的校验规则；
  - `ticket`：01b ticket 点名的用例/规则；
  - `01a`：01a 已实现的行为，01b 只补规则号、行列与 golden，不是重复实现；

- **不新增业务规则**：`device.device_type` 与 `profile.device_type` 一致性、`device_type` 枚举、`event.trigger.point` 存在性、`writes[].from` 参数引用、`point.modbus.type/func` 枚举、`payload` 位域范围、串口/TCP 数值范围等，全部不进入本目录；前四项已移出 01b，登记为 `01c` ticket。

### 1.3 规则前置条件与抑制（防止级联误报）

实现时必须按下列守卫执行；golden 的“一条非法用例通常只出一条诊断”依赖这些守卫：

- **结构优先**：任一层出现 V01–V07 或 V61 的 decode 阶段诊断（即 Secret 非标量），跳过 V10–V63 全部语义校验和 env 解析。结构/解码错误会破坏 decode 结果，继续做语义校验只会产生误导性级联。V61 的 resolve 阶段（env 名非法/未设置）发生在语义校验之后，不在此列。
- **必填优先**：字段为空/缺失时，依赖该字段的规则跳过：
  - `driver` 为空 → V50/V51 跳过；无任何传输块 → 只报 V11，不再报 V51。
  - `profile`/`link` 为空 → V30/V31 跳过。
  - point/service/event 的 `key`/`service_id`/`event_id` 为空 → V14/V15/V16 报必填；对应 V22–V24 唯一性跳过（避免空值互相“重复”）。
  - link `id`/device `sn` 为空 → V10–V12 报必填；V20/V21 唯一性跳过。
  - profile 文件缺名（V13）不会被静默补名；引用该 profile 的 device 仍会报 V30，因为该 profile 对引擎不可用。这是两个独立事实，不是误报。
- **枚举优先**：
  - `access` 为非空非法枚举 → 只报 V53；V33/V35 不再报（避免同一字段两条）。
  - `access` 为空 → V53 跳过；若该点被 write 引用则 V33 报不可写，被 verify 引用则 V35 报不可读。
  - `parity` 为空 → V52 跳过（不把“未配置”当成非法值）。
  - `driver` 非法 → V51 跳过。
- **引用链**：point 不存在（V32/V34）时，不再报 V33/V35；verify 块不存在时，不报 V34/V35。V32–V35 的定位一律是**引用键**（`services[i].writes[j].point`、`services[i].writes[j].verify.point`、`services[i].verify.point`），不是点位定义处。
- **可选数值**：`min`/`max` 只有两者都存在才比较；`scale`/`poll_interval_s` 只在非 nil 时检查；显式 `0` 必须被检查（指针已由 01a 保留）。
- **空列表/空容器合法**：`links: []`、`devices: []`、`{}` 本身不报错；只有设备引用缺失 link/profile 时才由 V30/V31 报。
- **address 子字段不在 01b**：V12 只查 `address` 指针存在；`address: {}` 仍通过，`unit_id`/`dev_eui`/`f_port` 的必填与范围归后续 ticket。
- **V60 的 grpc_addr 边界**：`chirpstack.grpc_addr` 为空或非法时**跳过冲突比较**，不新增诊断；其合法性不在 01b。
- **空串是非法枚举值**：V62/V63 不把空串当“未配置”跳过；缺键/null（默认值生效）仍然合法。
- **同一位置同规则同消息去重**：v4 在 anchor/merge 场景可能产生完全重复的构造错误（探针实测），排序后按 `(File,Line,Col,RuleID,Message)` 去重。

### 1.4 明确不纳入本目录的候选规则

以下 spec 未明说或超出 01b，一律不实现；前四项已移出 01b，登记为 `01c` ticket，不在 §11 让用户选择：

## 2. 行列定位机制

### 2.1 方案比较

语义校验在 `yaml.Load(..., &struct)` 之后进行，Go struct 不携带位置信息。可行方案：

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| A. 独立 `yaml.Node` 路径索引（选定） | 01a 已做一次 `yaml.Load(data, &node)`；保留这棵树，按与 struct 同构的路径建 `nodePath -> (key pos, value pos)` 索引；语义校验用路径查位置 | 不改类型、不写自定义 Unmarshaler；一次 parse 两用；可覆盖所有规则；位置由 v4 直接给出 | 需要维护路径与 struct 字段的对应；alias/merge 有局限 |
| B. 直接在 Node 树上校验 | 不 decode 到 struct，直接在 `yaml.Node` 上做全部规则 | 位置天然准确 | 要复制默认值合并、null 语义、类型转换、严格未知键等 01a 已有逻辑；规则实现与 struct 模型脱节；不可取 |
| C. 自定义 `UnmarshalYAML` 记录位置 | 每个类型实现 hook，把字段位置写进 side map | 位置与字段天然绑定 | 侵入全部类型；v4 的 hook 语义、null、alias 都要自己处理；易漏；与“不给容器写 UnmarshalYAML”的 01a 约束冲突 |

**选择 A**。理由：01a 已经为了空文档检测 parse 了一次 Node，01b 只是把结果留下来；语义校验继续基于 decode 后的 `Bundle`（默认值、null、指针语义都已正确），位置只作为旁路查询。

### 2.2 数据结构与函数签名

新增 `internal/config/positions.go`：

```go
type pathStep struct {
    key     string // mapping 字段
    index   int    // sequence 下标
    isIndex bool
}
type nodePath []pathStep

type nodePos struct {
    keyLine, keyCol     int // mapping: 键节点；sequence: 元素节点
    valueLine, valueCol int
}

type positionIndex struct {
    byPath map[string]nodePos   // nodePath.id() -> 位置
    byPos  map[[2]int]string    // (line,col) -> 键名，用于 V03 取未知键
    root   nodePos
}

func buildPositionIndex(doc *yaml.Node) *positionIndex
func (pi *positionIndex) at(p nodePath) (line, col int)
func (pi *positionIndex) keyAt(line, col int) (string, bool)

func fieldPath(parent nodePath, key string) nodePath
func indexPath(parent nodePath, i int) nodePath
```

- `nodePath.id()` 用长度前缀编码，避免参数名里的 `.`/`[` 造成歧义：
  - 字段：`/<len>:<key>`；序列：`[<i>]`；拼接成字符串只用于 map key。
- 建索引：
  - `DocumentNode` → 取 `Content[0]`；根 `MappingNode`/`SequenceNode` 记录 `root`。
  - `MappingNode`：成对遍历 `Content`；`key` 必须是 scalar；记录 `fieldPath` 的 key/value 位置并递归 value。
  - `SequenceNode`：记录 `indexPath` 的元素位置（元素的 `Line/Column`，通常是首键位置而不是 `-`）并递归。
  - `AliasNode`：记录 alias 使用点（父节点已记 value 位置）；递归 `n.Alias`，使 alias 内部字段落在 anchor 定义位置。
  - merge key `<<`：value 是 alias 且 target 是 mapping，或 value 是 sequence 且元素都是 mapping alias（`<<: [*A, *B]`）时，按 YAML merge 规范展开索引到当前路径；**序列中靠前的 mapping 优先于靠后的**（显式键 > 先出现 > 后出现），位置来自各 anchor 定义。非 mapping alias 的元素忽略（回退父节点）。该行为必须由 `positions_test.go` 固定。
- `at(p)`：
  1. 精确查 `byPath`；
  2. 未命中则逐级截断路径，查最近祖先；
  3. 仍未命中用 `root`；
  4. 最后回退 `1,1`。
- `keyAt(line,col)` 用于 V03：v4 的 unknown-field `Mark` 指向键节点；直接查 `byPos` 得到键名，避免解析 v4 消息中的 Go 类型名。

### 2.3 yaml v4 探针结论（实测 `go.yaml.in/yaml/v4 v4.0.0`）

以下结论来自真实运行探针（模块缓存中的 v4.0.0），不是推断：

1. **节点位置**：`MappingNode`/`SequenceNode`/`ScalarNode` 的 `Line/Column` 均可用且 1-based。mapping 的 key 节点指向键起始列，value 节点指向值起始列；sequence 节点指向首个 `-`，元素 `MappingNode` 指向该元素首键（如 `  - id:` 的 `id` 列，而非 `-`）。flow mapping 同样保留键/值列。block scalar 的节点位置在 `|`/`>` 指标处。
2. **`*yaml.LoadErrors`**：unknown field、duplicate key、type mismatch、自定义 Unmarshaler 错误都以 `*yaml.LoadErrors` 聚合，逐项 `le.Mark.Line/Column` 可用；unknown key 的 Mark 指向**键**，type mismatch 指向**值**，duplicate key 指向**重复键**。同一文件多个错误会聚合（实测 3 条）。**分派顺序**：`*yaml.LoadErrors` 自身也能被 `AsType[*yaml.LoadError]` 命中其首条（unknown/type/dup/empty/multi 均实测为真）；因此必须先判 `*yaml.LoadErrors`，只有它不是时才判单条 `*yaml.LoadError`，否则多错误文件会塌缩成一条。
3. **语法错误不是 `LoadErrors`**：scanner/parser/composer 错误是 `*yaml.LoadError`（`yaml.LoadError = libyaml.LoadError` 的导出别名），带 `Stage`、`Message`、`Mark`、`ContextMark`、`ContextMsg`。01a 的 `yamlError` 只处理 `*LoadErrors`，语法错误会退化成无行列的字符串；01b 必须同时 `errors.AsType[*yaml.LoadError]`。**位置以 `Mark` 为主，`ContextMark` 只在 `Mark` 为零时兜底**；实测 bad-flow：`Mark=2:1`、`ContextMark=1:4`；bad-indent：`Mark=3:5`、`ContextMark=0:0`，优先 ContextMark 会把错误指到构造起点而不是实际错误行。message 用 `le.Message`，`ContextMsg` 非空时追加 `({ContextMsg})`，例如 `syntax error: did not find expected ',' or ']' (while parsing a flow sequence)`。
4. **空文档/多文档**：
   - 空流、仅注释：第一遍 parse/decode 返回构造错误 `yaml: no documents in stream`，Mark 为 `0,0`。
   - `---`、`null`：第一遍 parse **成功**（Document + `!!null` 子节点），decode 到 struct 也**不报错**；必须沿用 01a 的 `emptyNode` 在 Node 树上判定为空文档。不能只依赖 decode 错误。
   - `{}`：合法的空 mapping，交给必填检查；`[]` 在根上会报 type 错误。
   - 多文档：返回 `yaml: expected single document, found multiple`，Mark 为 `0,0`。
   - 上述无位置的情况统一回退 `file:1:1`。
5. **alias/merge**：Alias 节点的 `Line/Column` 是**使用点**；`n.Alias` 指向 anchor 节点，anchor 节点保留定义位置。通过 alias 访问的 mapping 内部错误（unknown key/type）会被 v4 报在 **anchor 定义位置**，不是使用点。merge key `<<` 会被正确 decode；`<<: [*A, *B]` 也是合法的序列 merge，v4 按 YAML 规范合并（**靠前的 mapping 优先**；实测 `x:1` 来自 `*A`，不是 `*B` 的 `x:2`）。anchor 内的 unknown key 在 anchor 定义位置报，且可能与直接错误产生**完全相同的重复诊断**（需去重）。01b 明确**支持** mapping alias 与 mapping-alias 序列两种 merge 展开；非 mapping 元素忽略并回退父节点位置，不自作判断。
6. **重复键与部分 decode**：第一遍 `yaml.Load(data, &node)` 不会因重复键失败（重复键由 `WithUniqueKeys()` 在第二遍拒绝）；decode 出错时 struct 可能已被部分填充，01b 绝不使用带错的 decode 结果。v4 的 type 错误会回显反引号值（如 `` `not-int` ``），01a 的 `sanitizeYAMLMessage` 必须继续生效。

### 2.4 缺失字段（无节点）的回退位置

规则定位的是“字段”，因此：

- 字段存在 → 用该字段的**键节点**位置（key 列），不用 value 列。例如 `qos: 2` 定位到 `qos` 的列。
- 字段缺失 → 取最近存在的祖先节点位置：
  - `node.id` 缺失且 `node:` 存在 → `node` 键位置；
  - `node` 整个缺失 → 根 mapping 的 `1:1`；
  - `devices[0].address` 缺失 → `devices[0]` 元素位置（首键，通常是 `sn`）；
  - `links[0].id` 缺失 → `links[0]` 元素位置；
  - profile 的 `profile` 缺失 → profile 文件根 `1:1`。
- 文件级错误（V02/V06/多文档）→ `file:1:1`。
- 序列下标越界（例如引用了 `devices[99]`）→ 回退到该序列的键位置。
- 结果：任何诊断的 `Line >= 1 && Col >= 1`，`Diagnostic.Error()` 永远输出 `file:line:col: rule: message`。

### 2.5 alias / merge 的已知限制

- 配置中不推荐使用 alias/merge；01b 不为其增加专门校验。
- 通过 alias 引用的字段，语义错误会定位到 anchor 定义位置；同一 anchor 被多处引用时，错误可能重复，排序后去重。
- merge `<<` 展开的字段，位置来自 anchor 定义；01b **明确支持**单个 mapping alias 与 `<<: [*A, *B]` 序列两种形式，**靠前的 mapping 优先**；非 mapping 元素忽略并回退父节点位置。不得实现成“看情况”。
- `positions_test.go` 必须包含 `<<: [*A, *B]` 用例（至少断言合并后字段的路径与 anchor 定义行列），以及非 mapping 元素回退父节点的行为。
- 不建议在 golden 中大量使用 alias；只保留 `positions_test.go` 的单元用例即可。

## 3. 诊断聚合与顺序

### 3.1 结构错误 vs 语义错误

`Load` 的执行顺序固定为：

```text
1. 读并解析四层（config.yaml、links.yaml、devices.yaml、profiles/*.yaml）：
   - 缺失/不可读 → V06
   - 第一遍 Node parse：语法错误 → V01；空文档/无文档 → V02
   - 第二遍严格 decode：逐条 LoadError → V03/V04/V05（Secret 的标量错误 → V61）
   - profiles 同名 → V07
2. 若存在任何结构/解码诊断（V01–V07，或 V61 的 decode 阶段 `secret must be a scalar`）：排序、去重、返回；不构建 Bundle、不跑 V10–V63、不解析 env。
3. 构建 Bundle、做 redact_fields null 归一化。
4. 语义校验 V10–V63（V61 此时只处理 decode 阶段的归类；resolve 阶段在步骤 6）：收集全部规则诊断。
5. 若存在语义诊断：排序、去重、返回；不解析 env（避免 env 错误掩盖配置错误）。
6. 解析 env 凭据（V61 的 resolve 阶段）；若有诊断：排序、返回。
7. 成功返回 Bundle。
```

**为什么语法错误时跳过语义校验**：decode 结果可能部分填充（探针实测），继续检查会产生大量伪引用错误（例如 profile 解析失败导致所有 device 都报 profile 不存在）。结构错误本身就是首要修复项；一次只让用户修一层。

**为什么继续读取其他文件**：01a 在第一处解析错误就返回；01b 改为把四层都尝试读取/解析，收集所有结构错误再排序返回。这样一次能看到多个文件的语法/未知键问题，且排序规则统一。文件缺失/不可读同样继续。

### 3.2 排序规则（golden 可复现的唯一口径）

`sortDiagnostics` 比较键依次为：

1. **文件序**：`config.yaml` = 0，`links.yaml` = 1，`devices.yaml` = 2，`profiles/*` = 3，`profiles` 目录本身 = 3；同 rank 内按完整相对路径字典序。
2. `Line` 升序。
3. `Col` 升序。
4. **规则号数值**升序（解析 `V` 后数字，`V10` 在 `V2` 之后，避免字符串序）。
5. `Message` 字典序。

排序后按 `(File,Line,Col,RuleID,Message)` 去重（保留第一条）。

- 不同文件：先 config，再 links，再 devices，最后 profiles（按文件名）。
- 同文件：按行列；同一位置多个规则按规则号；同一位置同规则不同消息按消息字典序。
- 跨文件引用（V30/V31）定位在 `devices.yaml`，因此自然排在 links 之后、profiles 之前。
- profile 内规则按文件内行列排序；多个 profile 文件按文件名排序。
- 重复规则（同一规则多处违反）按位置排序；唯一性规则报“后出现的重复项”，消息里带首次出现位置。

links.yaml:9:9: V20: duplicate link id "sensors-485" (first defined at links.yaml:2:9)

## 4. 文件路径呈现

**选择：配置根相对路径，始终使用 `/`，不带 `./`。**

- `config.yaml`、`links.yaml`、`devices.yaml`、`profiles/<basename>`。
- 缺失文件也报同一相对路径（如 `links.yaml`）；profiles 目录缺失报 `profiles`。
- 跨文件引用错误报**引用字段所在文件**：`device.profile`/`device.link` 报 `devices.yaml`；`writes[].point`/`verify.point` 报对应 `profiles/x.yaml`。

理由：

- golden 可直接复现，不需要把临时目录替换成占位符；runner 还会断言输出中不出现 `t.TempDir()` 路径。
- 现场 UX 与 `--config /etc/collect-code` 一致：`devices.yaml:12:5: ...` 比绝对路径更短，且不会因为部署目录不同导致输出变化。
- 绝对路径会让 golden、日志、工单里的路径随机器变化；只传 dir 拼接的相对路径等价于根相对，但若 `--config` 是相对路径会不稳定。

对现有 01a 测试的影响：

- `TestUnknownKeyReportsLine` 仍包含 `config.yaml:4:`，通过。
- `TestUnknownKeys` 用 `filepath.Base(file)` 检查文件名，仍通过。
- `TestRequiredAggregatedInOrder` 原来断言 `sensor-soil.yaml: profile: required`，将变为 `profiles/sensor-soil.yaml:...: V13: profile: required`，需更新（见 §8.2）。
- `Bundle.ProfileSources` 从 basename 改为 `profiles/<name>`；目前只有 summary 使用，无外部调用，安全。

### 5.2 固定行序与字段

第一行**保留** 01a 的成功行，格式不变：

```text
config ok: node=<id> product_key=<key> links=<N> devices=<N> profiles=<N>
```

其后固定顺序（字符串值统一用 Go `%q` 引号，空值用 `"[unset]"`；可选整数空值用未加引号的 `[unset]`）：

1. `northbound.mqtt:`
   `broker="..." client_id="..." username="..." password="..." qos=N keepalive_s=N tls_enabled=B tls_ca_file="..." tls_insecure_skip_verify=B reconnect_min_backoff_s=N reconnect_max_backoff_s=N`

   `name="..." property_post="..." service_reply="..." event="..." service_invoke="..." node_state="..."`

8. `health:` `enabled=B addr="..."`

   `  - id="..." driver="..." transport="serial" read_deadline_ms=N retry_max=N retry_backoff_ms=N`
   - `read_deadline_ms` 是生效值：link 覆盖值，否则 `timing.read_deadline_ms`。
   - `retry_*` 无全局默认，nil 渲染 `[unset]`。
   - `transport` 由实际存在的块按 `serial,tcp,chirpstack` 固定顺序用逗号连接。
   - 存在 serial 时追加：`serial_device="..." serial_baud=N serial_data_bits=N serial_parity="..." serial_stop_bits=N`
   - 存在 tcp 时追加：`tcp_host="..." tcp_port=N`（port nil → `[unset]`）
   - 存在 chirpstack 时追加：`chirpstack_grpc_addr="..." chirpstack_api_token="..." chirpstack_application_id="..." chirpstack_mqtt_broker="..." chirpstack_topic_filter="..." chirpstack_json=B expected_uplink_interval_s=N enqueue_timeout_s=N`
10. `devices:` 后按 `devices.yaml` 顺序逐条：
    `  - sn="..." device_type="..." profile="..." link="..." address="..." poll_interval_s=N`
    - `address` 为双引号字符串：`address="unit_id=N"` / `address="dev_eui=...,f_port=N"`；无字段时为 `address="[unset]"`。
    - `poll_interval_s` 为生效值：device 覆盖值，否则 profile 的 `poll_interval_s`，都没有则 `[unset]`。
11. `profiles:` 后按 **profile 名字典序**（不是文件顺序，避免 map 迭代）逐条：
    `  - profile="..." source="profiles/x.yaml" device_type="..." poll_interval_s=N points=N services=N events=N payload=B`
    - `source` 来自 `Bundle.ProfileSources`（根相对）。
    - `poll_interval_s` 为 profile 自身的值；nil 渲染 `[unset]`。
    - `payload` 表示 `profile.Payload != nil`。

末尾不加额外空行；`Render()` 返回的字符串不带结尾换行，`app` 用 `fmt.Fprintln` 输出。

### 5.3 脱敏与 broker userinfo

- `password` → `Secret.Masked()`：`"[unset]"` / `"[set]"` / `"[set via env NAME]"`。
- `chirpstack_api_token` → `TokenMasked()`：同上。
- `username` 不是 spec 定义的凭据，原样显示；空则 `"[unset]"`。注意：这是 `northbound.mqtt.username` 字段，不是 broker URL 的 userinfo。
- broker：**不使用 `url.URL.Redacted()`**（它保留 username 与 query）。统一只保留 scheme、host:port 和一个占位 userinfo：
  ```go
  func sanitizeBroker(raw string) string {
      u, err := url.Parse(raw)
      if err != nil || u.Scheme == "" || u.Host == "" {
          return "[unparseable broker]"
      }
      if u.User != nil {
          return u.Scheme + "://[REDACTED]@" + u.Host
      }
      return u.Scheme + "://" + u.Host
  }
  ```
  - 有 userinfo：`mqtt://user:SENTINEL@host:1883?token=SENTINEL` → `mqtt://[REDACTED]@host:1883`；username、password、query 全部不出现。
  - 无 userinfo 但 query 非空：query 直接丢弃（如 `mqtt://host:1883`），不打印 token。
  - path/query/fragment 一律不打印；host:port 保留。
  - `url.Parse("not a url")` 会成功返回 path，因此必须同时检查 `Scheme`/`Host`，否则会把 `not%20a%20url` 当成 broker 打印。
  - 解析失败/无 scheme/host 一律 `"[unparseable broker]"`，不打印原串。
- `chirpstack.mqtt.broker` 同样走 `sanitizeBroker`。
- `state.db_path`、topic 模板、文件名不是凭据，原样 `%q`。
- `config-check` 不打印 `Secret.Reveal()`；sentinel 测试覆盖 stdout+stderr 全文。

### 5.4 摘要样例（base fixture）

### 6.2 `case.yaml` 字段

```go
type caseSpec struct {
    Env    map[string]string `yaml:"env"`    // 仅这些变量可见；不读取 OS env
    Delete []string          `yaml:"delete"` // 删除 base 中的相对路径
    Empty  []string          `yaml:"empty"`  // 将文件写成空内容
    Expect *int              `yaml:"expect"` // 缺省：legal=0，invalid=1
    Forbid []string          `yaml:"forbid"` // 输出中不得出现的 sentinel
}
```

- `Env` 是唯一 env 来源；未列出的变量一律“未设置”，避免 CI 环境污染导致 golden 漂移。
- `Delete` 用于 V06（缺文件）与 V30（缺 profile 文件）。
- `Empty` 用于 V02；空文件在 git 中不易察觉，用声明更清晰。
- `Expect` 只用于少数特殊用例；默认按 `legal/`/`invalid/` 推断。
- `Forbid` 用于密码/Token sentinel、临时目录路径等泄漏检查。

### 6.3 期望输出命名与 runner

每个用例（按需）：

- `want.exit`：一行整数；缺省由目录类型推断。
- `want.stdout`：完整 stdout 精确 golden；合法用例缺省时与 `golden/summary.stdout` 比较（仅当覆盖层不改变摘要可见字段时）。
- `want.stderr`：完整 stderr 精确 golden；合法用例缺省为空；非法用例应必填。
- `golden/summary.stdout`：base 的完整摘要。

runner（`internal/app/golden_test.go`，`package app`）：

```go
func TestGoldenCorpus(t *testing.T) {
    root := filepath.Join("..", "config", "testdata", "config")
    for _, kind := range []string{"legal", "invalid", "ordering"} {
        for _, caseDir := range sortedSubdirs(filepath.Join(root, kind)) {
            t.Run(kind+"/"+filepath.Base(caseDir), func(t *testing.T) {
                work := t.TempDir()
                copyTree(filepath.Join(root, "base"), work)
                spec := loadCaseSpec(caseDir)
                applyOverlay(work, filepath.Join(caseDir, "files"))
                applyDeletesAndEmpties(work, spec)

                lookup := func(name string) (string, bool) {
                    v, ok := spec.Env[name]
                    return v, ok
                }
                code, stdout, stderr := run(t, []string{"config-check", "--config", work}, lookup)

                wantExit := expectedExit(kind, spec)
                if code != wantExit { ... }
                compare("stdout", stdout, wantFile(caseDir, "want.stdout", defaultStdout(kind)))
                compare("stderr", stderr, wantFile(caseDir, "want.stderr", ""))
                assertNotContains(stdout+stderr, work)   // 临时目录绝不出现
                assertNotContains(stdout+stderr, spec.Forbid...)
            })
        }
    }
}
```

- `-update` 标志（`go test ./internal/app -run TestGoldenCorpus -update`）重写 `want.*`；CI 不带该标志。
- 失败信息按行 diff，指出首个不同行；不要只打印整段。
- `TestRuleCatalogCoverage`：测试内 `allRules = []string{"V01",...,"V63"}`；对每个 ID 断言 `legal/<id>-*` 与 `invalid/<id>-*` 存在，且 `invalid` 的 `want.stderr` 含 `: <ID>: `；同时断言没有未知规则目录。
- `TestDiagnosticFormat`：对每个非法用例的 stderr 每一行做正则 `^(.+):(\d+):(\d+): (V\d{2}): (.+)$`，并断言 `Line>=1, Col>=1`。

### 6.4 路径归一化

- 诊断与摘要全部使用配置根相对路径；`want.*` 中不出现临时目录。
- runner 额外断言 `!strings.Contains(stdout+stderr, work)`，防止未来有人把绝对路径写进消息。
- V06 的 `os.PathError` 消息已在实现中归一化（`file not found` 等），不会带出 `/tmp/...`。
- summary 的 `state.db_path` 是配置值（base 用默认 `/var/lib/collect-code/state.db`），不是临时目录；测试用例不得把它改成随机路径。

### 7.2 `Load` 的演进（不破坏签名）

- 签名保持 `func Load(dir string, opts ...Option) (*Bundle, error)`。

- **不新增** `LoadResult`/`ValidationError` 等包装类型；01a 的 `Diagnostic`/`Diagnostics` 已足够，避免无谓 API 扩张。

### 7.4 各层实现要点

- **required**：从 `load.go` 的 `requiredDiagnostics` 移入 `validate.required`；遍历顺序与 01a 相同（config → links → devices → profiles），但最终由全局排序决定输出。新增 V14/V15/V16：`points[i].key`、`services[i].service_id`、`events[i].event_id` 为空即报。V12 只查 `address` 指针存在，`address: {}` 仍通过（实测 v4 对空 mapping 分配非 nil 指针；子字段不在 01b）。
- **unique**：用 `map[string]firstPos`；`firstPos` 记录 `file,line,col`；重复项用 `v.add` 报在**后出现**的键；消息含首次位置；空 `key`/`service_id`/`event_id` 跳过 V22–V24（由 V14–V16 报）。
- **references**：
  - 先建 `linkIDs map[string]bool` 与 profile 点位并集（见 §11 P1）。
  - `profilePointAccess(p *Profile) map[string]pointAccess`：
    - `points[]`：`access=="rw"` → writable+readable；`access=="r"` → readable；空/invalid → 都不置（由 V33/V35/V53 处理）。
    - 若 P1=A：`payload.decode[].key` → readable；`payload.encode[].key` → writable；若同一 key 同时出现，合并。
  - 对每个 profile 的 services：`writes[].point` 查 union；`write.verify.point` 与 `service.verify.point` 查 union 并判 readable。
  - **定位必须是引用键**：V32/V33 用 `services[i].writes[j].point`；V34/V35 的 write 级用 `services[i].writes[j].verify.point`，service 级用 `services[i].verify.point`；不得定位到点位定义处或文件根。device 引用继续用 `devices[i].profile/link`。
- **numeric**（P8=A，覆盖面固定）：
  - `min <= max` 与 `scale > 0` 覆盖 `points[].modbus.{min,max,scale}`、`services[].params.*.{min,max}`、`payload.decode/encode[].scale`。
  - `checkMinMax(file, path, min, max)`：先判 `math.IsNaN/IsInf`（任一非有限 → V40 非有限消息），再判 `min > max`；`min` 位置用于报错。
  - `checkScale(file, path, scale)`：先判 `math.IsNaN/IsInf`，再判 `scale <= 0`；两者都用 V41 消息 `scale must be finite and > 0`。
  - `poll_interval_s` 检查 profile 与 device 覆盖值；`freshness_window_s`、`offline_after_intervals`、`qos` 检查 config。
  - 数值消息用 `strconv.FormatFloat(v, 'g', -1, 64)` / `%d`，保证 golden 稳定。
- **enums**：
  - `driver`: 精确小写四值；非法 → V50，跳过 V51。
  - `access`: 非空时精确 `r`/`rw`；非法 → V53；空 access 本身不报。
  - `parity`: 非空时精确 `none`/`even`/`odd`；非法 → V52（P5=A）。
  - `log.level`: 空串也报 V62；非空时 `strings.ToLower` 后匹配 debug/info/warn/error，与 `logging.parseLevel` 一致；`log.format` 空串或非 `json` 都报 V63。
  - V51 只在 driver 合法且至少一个传输块存在时执行（否则 V11 已报）；P9=A 下额外块忽略。
- **ports**（P7=A）：
  - 若 `health.enabled == false && health.addr == ""` → 跳过；其余情况都检查。
  - `net.SplitHostPort`；失败 → V60 invalid。
  - 端口 8080/1700 → V60 reserved（无条件）。
  - 只遍历 `driver=="lorawan"` 且 `Chirpstack != nil` 的 link 的 `GRPCAddr`：为空或 `SplitHostPort` 失败时**跳过冲突比较**，不新增诊断；合法时规范化 `host:port` 与 health 精确比较，相等 → V60 conflict（消息带 link id）。
  - 位置：`config.yaml` 的 `health.addr` 键。
- **credentials**：
  - decode 阶段 `secret must be a scalar` → V61，位置用 `LoadError.Mark`。
  - resolve 阶段：非法 env 名 → V61（不回显名）；变量未设置 → V61（显示变量名，可接受）；`api_token_env` 消息保留 `link {id}:` 前缀以兼容 01a 测试。
  - 位置：`northbound.mqtt.password` / `links[i].chirpstack.api_token_env` 键。
- **logOptions**：V62/V63 在 config 内先报；空串不跳过。`logging.ParseOptions` 保留为第二道防线，两者接受集合（含 `""`）必须一致（见测试）。

### 7.5 为什么不为 39 条规则引入注册框架

- 规则集合是编译期固定的 39 条，不存在运行时增删；接口/注册表只会增加间接层。
- 输出顺序由全局排序决定，与规则求值顺序无关，因此不需要“规则优先级”注册机制。
- 规则之间只有少量前置条件（§1.3），用显式 `if` 守卫比框架更可读。
- 唯一需要“清单”的地方是测试：在 `golden_test.go` 放一个 `allRules []string`，只用于断言 golden 覆盖；它不进入生产代码。
- 若未来规则超过 ~50 条或需要用户自定义规则，再评估注册/描述符结构；当前不做。

## 11. 评审结论与已定决策

> 2026-11-19 用户评审通过：当前规则目录 39 条；摘要采用 A（完整 22 行）；
> `device_type` 一致性/枚举、`event.trigger.point`、`writes[].from` 参数引用
> 移出 01b，登记为新的 `01c` ticket；spec §1 valve-lora 的 `verify.point`
> 由 `target_opening` 修正为 `opening`。01b 无剩余待决策项。

### 已定决策（不再询问）

- **P4=B**：`profile.points[].access` 不新增必填；非空时校验 `r`/`rw`，空 access 由 V33/V35 在引用处兜底。
- **P5=A**：`serial.parity` ∈ `none`/`even`/`odd`，精确小写。
- **P7=A**：`health.addr` 非空或 enabled=true 时校验；端口 8080/1700 无条件拒绝；只与**合法非空** `chirpstack.grpc_addr` 做精确 host:port 比较；enabled=false 且 addr 为空时跳过；grpc_addr 合法性不在 01b。
- **P8=A**：`min<=max`/`scale>0` 覆盖 `points[].modbus`、`services[].params.*`、`payload.decode/encode[].scale`；NaN/±Inf 一律非法（V40/V41 都用 `math.IsNaN/IsInf`）。
- **P9=A**：只要求 driver 对应的传输块存在，额外块忽略。

### P1（已确认：A）LoRa profile 的点位引用口径

spec §2 写“`service.writes[].point` 在 `profile.points` 中且 `access=rw`”，但 spec §1 与 `configs/example/profiles/valve-lora.yaml` 的 LoRa profile **没有 `points`**；`set_opening` 的 `target_opening` 只在 `payload.encode`，`opening` 只在 `payload.decode`。字面执行会让 base 与 `configs/example` 全部失败。

- **A（推荐）**：为每个 profile 建“点位集合”：
  - `points[]`：按 `access` 判定可读/可写（`r` 可读、`rw` 可读可写）；
  - `payload.decode[].key`：隐式可读；
  - `payload.encode[].key`：隐式可写；
  - 同一 key 多处出现时合并能力。
  - V32 查 union；V33 要求 union 中可写；V34 查 union；V35 要求 union 中可读。
  - 好处：spec 示例自洽；LoRa 只读/只写点位仍能被 V33/V35 拦住；base/example 不改。
- **B（字面）**：只认 `profile.points`。则必须二选一：B1 对含 `payload` 的 profile 跳过 V32–V35（LoRa 引用不校验）；B2 要求 LoRa profile 也写 `points` 并改示例。B2 与 spec 示例冲突。
- 推荐 A。若选 B1，把 §1.3 的引用规则守卫写成“payload profile 跳过”，并在文档标注；若选 B2，需改 base/example 与 README。

**用户已选 A，并在 2026-11-19 计划评审中批准连带修订。** spec §1 的 valve-lora 示例把 `verify.point` 写成 `target_opening`（仅 encode，按 A 不可读），修正为 `opening`（decode 中的实际开度）；base 与 `configs/example` 本来就是 `opening`。这不是代码偏离，而是原示例与 A 口径不自洽。该修订已随计划评审落地到 spec。
