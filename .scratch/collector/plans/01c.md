> 所有诊断由现有 `v.add` 生成，最终经 `sortDiagnostics` 排序、`dedupeDiagnostics` 去重。规则求值顺序不影响输出顺序。

### 2.1 V70 细节

- 比较对象是 `devices[i].device_type` 与 `v.b.Profiles[devices[i].profile].device_type`。
- 定位选择 `devices.yaml` 的 `device_type` 键，理由：冲突是“实例声明 vs 模板声明”，用户需要先判断改设备还是改模板；`devices.yaml` 是实例入口，且 V30 已把 profile 引用错误定位在 `devices.yaml`。
- 不比较大小写、不去空白，精确字符串比较；大小写/空白导致的非法值先由 V71 拦截，V70 不再重复。
- 不新增 profile 侧诊断，避免同一事实两处报。

### 2.2 V71 细节

- 枚举权威来自 `GLOSSARY.md`：`valve`（电动调节阀）、`sensor`（RS485 传感器）、`gateway`（边缘节点自身）。
- `device.device_type` 空串由 V12 报必填，V71 跳过。
- `profile.device_type` 空串合法，V71 跳过；非空非法才报。
- 推荐同时校验 profile（见 §3.1），因此定位可能是 profile 文件的 `device_type` 键。

### 2.3 V72 细节

- 只处理 `event.trigger.type` 精确等于 `point_changed` 的事件。其他值（包括空串、`device_offline`、拼写错误）本 ticket 不校验，原因是 `trigger.type` 枚举不在范围内。
- 点位集合沿用 01b P1=A 的唯一口径：
  - `profile.points[]`：`access=r` 可读，`access=rw` 可读可写；
  - `payload.decode[].key`：可读；
  - `payload.encode[].key`：可写但不可读；
  - 同一 key 多处出现时合并能力。
- 复用 `pointCaps(p)`，不重新实现点位并集。
- `trigger.point` 为空时只报“required”消息，不再报 `"" not found`。
- 非空但不存在：报“not found”，不再报不可读。
- 存在但 `cap.invalid == true`（access 非法）：跳过 V72，由 V53 报，避免同一字段两条。
- 存在但不可读：按 `pointCap.access` 选择消息变体，与 V35 的措辞保持一致。

### 2.4 V73 细节

- 对每个 `services[i].writes[j]` 独立检查。
- 推荐只接受字面小写前缀 `params.`，且前缀后 `<name>` 非空；不接受 `params`、`Params.x`、`params[0]`、`params-`、前导空白、`$params.x`。
- 不 trim：尾随空白会成为 `<name>` 的一部分，通常落到“未声明”而不是“格式错误”；只有前导空白/缺前缀才走格式错误。测试要分别覆盖这两种结果。
- 推荐把 `<name>` 原样作为 `service.params` 的 map key 精确查找（允许 `<name>` 含点，只要该 key 已声明）；这样不会对合法的带点参数名做额外限制。
- 空 `from`、格式错、`<name>` 为空统一走格式消息；只有格式合法且未声明时才走未声明消息。每条 write 最多一条 V73。
- 与 V32/V33 不互相抑制：`point` 与 `from` 是两个字段，可以各自报错；golden 非法用例通过只改一个字段来保证只出现目标规则。

### 2.5 与现有规则的抑制关系汇总

- **结构优先**：存在 V01–V07 或 V61 decode 阶段诊断时，`Load` 直接返回，不进入语义校验；V70–V73 自动跳过。
- **必填优先**：
  - `device.device_type` 为空 → 只报 V12，不报 V70/V71；
  - `device.profile` 为空或 profile 不存在 → 只报 V12/V30，不报 V70；
  - `profile.device_type` 为空 → 不报 V70/V71（非必填）。
- **枚举优先**：任一侧 `device_type` 非法 → 只报 V71，不报 V70；`access` 非法 → 只报 V53，不报 V72。
- **引用互斥**：V72 的“为空 / 不存在 / 不可读”三选一；V73 的“格式错 / 未声明”二选一。
- **去重**：同一 `(File,Line,Col,RuleID,Message)` 由现有 `dedupeDiagnostics` 去掉。

## 3. 需要拍板的边界（A/B 与推荐）

### 3.1 V71 是否同时校验 `profile.device_type`

- **A（ticket 字面）**：只校验 `device.device_type`。
- **B（推荐）**：同时校验 `device.device_type` 与 `profile.device_type` 的非空值。

**推荐 B。理由：**

1. `profile.device_type` 是 V70 的比较对象；只校验 device 会让非法 profile 值静默通过，V70 又无法在有非法值时给出可信结论。
2. 现有 base 与 `configs/example` 的 profile 类型全部合法，B 不引入任何兼容性变化。
3. ticket 的“不新增 `profile.device_type` 必填”仍被严格遵守：空串跳过，只有非空非法值才报。

**需要同步的文档**：spec §1 的 `device_type: valve # valve|sensor` 注释建议改为 `# valve|sensor|gateway`，与 GLOSSARY 对齐；这是文档一致性修正，不影响规则。

**若用户选 A 的耦合**：V71 只查 device 后，V70 不得在 profile 类型非法时静默跳过，否则非法 `profile.device_type` 会完全漏报。选 A 时必须同步修改 V70 的跳过条件（只跳过 profile 缺失/空值，并对非法 profile 类型给出诊断），或仍让 V71 覆盖 profile。推荐 B，避免这个自相矛盾的组合。

### 3.2 `trigger.type == point_changed` 但 `trigger.point` 为空

- **A**：复用“不存在”消息，输出 `trigger point "" not found in profile "x"`。
- **B（推荐）**：专用消息 `trigger point is required when trigger.type is "point_changed"`。

**推荐 B。理由：** 空值是“缺少必填引用”，不是“引用了一个不存在的名字”；专用消息对用户更直接。定位仍用 `events[i].trigger.point` 键（键存在但值为空时精确到键；键完全缺失时按现有 `positions.go` 回退到最近的 `trigger` 键）。

**非 `point_changed` 时是否完全不检查**：是。包括 `trigger.type` 为空、为其他未知值、为 `device_offline` 等，都不检查 `trigger.point`，也不校验 `trigger.type` 枚举（不在本 ticket 范围）。

### 3.3 V73 的 message 拆分与前缀规则

- **一条规则多 message**：推荐 V73 一条规则，两个消息模板：
  1. 空 / 格式错 / `<name>` 为空：`from must be params.<name> (got %q)`；
  2. 格式合法但未声明：`from param %q is not declared in service params`。
- **不拆分**为 V73/V74/V75。理由：ticket 只给了 V73 一个编号；三个条件共享“from 引用参数”这一语义，拆分只会增加规则目录与 golden 维护成本。

前缀规则二选一：

- **A（严格单段）**：`params.<name>` 中 `<name>` 不允许再含点，`params.a.b` 视为格式错。
- **B（推荐，精确 map key）**：只要求字面前缀 `params.` 且剩余部分非空；剩余部分原样作为 `service.params` 的 key 精确查找，允许含点（若已声明）。

**推荐 B。理由：** `params` 是 Go `map[string]ParamSpec`，key 是任意字符串；B 与“已在 `service.params` 声明”这一语义完全一致，不会对合法的带点参数名做无依据的限制。A 更严格，但会引入一条 spec 未写的命名约束。两者都不影响现有 base/example。

### 3.4 V70 的跳过与 V71 优先级

- **profile 不存在时**：推荐**跳过 V70**。`V30` 已经给出可操作诊断；此时没有可信的 `profile.device_type`，继续报 V70 只会产生“和空值比较”的误导。A（同时报 V30+V70）不推荐。
- **两侧一致但类型非法时**：推荐**只报 V71**，不报 V70。A（V70+V71 双报）不推荐：类型非法时“一致性”结论没有意义，且会让同一字段出现两条诊断。
- **任一侧非法、另一侧合法时**：同样只报 V71。
- **两侧都为空**：device 侧由 V12 报；profile 侧不报；V70 跳过。
- **若用户在 §3.1 选择 A**：V70 不能以“profile 类型非法”为由跳过，否则非法 profile 值会静默通过；选 A 时必须重新定义 V70 的跳过条件。推荐 B。

5. **V72**：在 `references()` 的 profile 循环内，`caps := pointCaps(p)` 之后遍历 `p.Events`：

6. **V73**：在 `references()` 的 profile 循环内遍历 `p.Services` / `svc.Writes`：

7. **不修改** `required()` / `unique()` / `numeric()` / `ports()` / `logOptions()` 的现有行为；不改 `load.go`、`positions.go`、`summary.go`、`types.go`。

### 4.3 `checkCapability` 重构方案（保持 message 不变）

推荐的最小重构：

- 定义 `pointUse` 描述符，字段包括：
  - `noun`：`"write point"` / `"verify point"` / `"trigger point"`；
  - `missingRule`：存在性诊断规则号；
  - `capabilityRule`：可写/可读诊断规则号；
  - `writable`：要求可写还是可读。
- 预置 `writeUse`、`verifyUse`、`triggerUse`。
- 新函数 `checkPointUse(file, path, profile, caps, point, use)` 复刻现有 `checkCapability` 的全部分支与消息：
  - 不存在：`%s %q not found in profile %q`；
  - `cap.invalid` 或能力满足：返回；
  - `access == ""`：`%s %q is %s (access is unset)`；
  - 写且 `payload.decode`：`%s %q is not writable (only present in payload.decode)`；
  - 读且 `payload.encode`：`%s %q is not readable (only present in payload.encode)`；
  - 其他：`%s %q is %s (access=%q)`。
- 现有 `checkCapability(..., write bool)` 只做 `use := verifyUse; if write { use = writeUse }`，然后调用 `checkPointUse`。这样 V32–V35 的 message 逐字节不变，golden 不应有任何 diff。
- 验证方式：在重构提交前后各跑一次 `go test ./internal/app -run TestGoldenCorpus -count=1`，并检查 `git diff -- internal/config/testdata/config/invalid` 只出现新增目录。

### 4.4 位置索引

- 不需要改 `positions.go`。现有 `nodePath` / `fieldPath` / `indexPath` 已能表示：
  - `devices[i].device_type`
  - `profiles/<file>` 的 `device_type`
  - `events[i].trigger.point`
  - `services[i].writes[j].from`
- 字段键存在时 `positionIndex.at` 精确返回键的行列；字段完全缺失时按既有语义回退到最近祖先（`trigger` 键或 `writes[j]` 元素）。验收 golden 都使用存在的键，因此断言的是字段键位置，不是数组元素。
- 不新增任何“按值定位”逻辑。

## 5. spec §2 改动（精确文本）

先把 §2 现有的“引用完整”条目按 01b 已实现的 P1=A 口径修正（当前文本仍写 `profile.points` + `access=rw`，与 V32/V33 和本 ticket 的 V72 冲突）：

```markdown
- 引用完整：device.profile 文件存在；device.link 存在；service.writes[].point 在 profile 点位集合中存在（`points` ∪ `payload.decode` ∪ `payload.encode`）且可写（`points` 的 `access=rw`，或 `payload.encode`）；verify.point 在 profile 点位集合中存在（并集）且可读（`points` 的 `access=r/rw`，或 `payload.decode`）。
```

然后在这条之后、“数值”之前插入以下四条：

```markdown
- 语义一致（V70）：`device.device_type` 与它引用的 profile 的 `device_type` 都非空时必须一致；任一为空串时不参与比较，`profile.device_type` 仍不是必填项。
- 枚举（V71）：`device_type` 只允许 `valve`、`sensor`、`gateway`（定义见 `GLOSSARY.md`）；`device.device_type` 与 `profile.device_type` 的非空值都要校验，空串跳过。
- 事件引用（V72）：`event.trigger.type == "point_changed"` 时，`trigger.point` 必须存在且可读；点位集合沿用 `profile.points` ∪ `payload.decode`（可读）∪ `payload.encode`（可写）的口径。其他 `trigger.type`（含空串）不检查 `trigger.point`。
- 服务参数引用（V73）：`service.writes[].from` 必须写成 `params.<name>`，且 `<name>` 必须已在同一个 service 的 `params` 中声明；空串、缺少 `params.` 前缀或 `<name>` 为空都算非法。
```

同时做一处**非规则性**文档修正并并入 spec 提交：§1 的 valve-modbus 示例注释 `device_type: valve              # valve|sensor` 改为 `# valve|sensor|gateway`，与 GLOSSARY 对齐。此修正不影响任何测试或摘要。

摘要与 `golden/summary.stdout` **不修改**：新规则只读取已有字段，不新增摘要 DTO 字段。
